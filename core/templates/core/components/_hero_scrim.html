{% comment %} 压在 hero 照片上的两层遮罩。**首页和内页共用这一份**（2026-08-06 抽出来）。 ⚠️ 抽出来的理由就是这次的要求本身：内页的背景要「和首页压暗的强度一样」。 而「一样」如果靠在两个模板里各写一遍 class 串来维持，它就一定会分叉 —— 哪一天有人调了首页的 45%，内页不会跟着动，而那时候两处各自看都没问题。 这和顶栏、菜单抽成组件是同一条规矩（见 base.html 里那段）。 两层，不是装饰，是**可读性的唯一保障**： 一层全屏的轻压暗（顶栏那几个字要读得清） 一层集中在下三分之一的强压暗（首页的经文在那里） ⚠️ 用的时候必须放在一个 **`relative` 或 `fixed` 的定位父级**里面 —— 这两个 div 是 `absolute inset-0`，父级不定位它们就会拿初始包含块当参照， 铺到整个文档上去。首页放在 hero 容器里，内页放在那张 fixed 照片里。 🔴 **对比度上的代价，如实记在这里**（2026-08-06 拍板，做了取舍）： 这两层在屏幕 15% 和 33% 处只到 **4.02:1 / 4.44:1**，低于 AA 的 4.5。 首页不受影响 —— 那两个位置没有正文，经文在底部（8～10:1）。 但内页的卡片**外**有小字正好落在那一带（列表的条数行、区块的说明行）。 这是**知情的选择**：原来内页用的是照片自己的 `filter` 压暗，过线很多， 但代价是照片的高光阴影糊成一团。选了好看。 ⚠️ 大标题不受影响（大字判据是 3:1，4.02 过得很宽）。 ⚠️ 更要紧的是：**换一张更亮的照片会让这个数继续往下掉，而且不报错。** 纯白照片下 15% 那一带只剩 1.3:1。基金会换首页照片时必须重看这一条。 记进 phase-c.md 的已知缺口。守卫只能盯住「这两层还在、数值没被人悄悄改」， 盯不住「上传了什么照片」—— 见 core.tests.GlassMaterialContrastTests。 {% endcomment %}{% spaceless %}
