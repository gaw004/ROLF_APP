# 从零开始：非营利基金会志愿者 & 资源管理系统

> 目标：第一次写全栈应用，帮基金会管理志愿者、追踪资源（money / people / event）。
> 本文档帮你建立地图——不写代码，先理清思路。

---

## 一、技术栈：Django + PostgreSQL 好不好？

**好，而且对你这个场景几乎是最优解。** 理由：

- Django 自带 ORM、Admin 后台、用户认证、权限系统。对非营利组织管理系统来说，
  **Django Admin 本身就能当半个 MVP** —— 你几乎不用写前端就能增删改查志愿者、活动、捐款记录。
  这对"第一次写、想快速看到东西"的人是巨大优势。
- PostgreSQL 是关系型数据库里最稳的选择。你的数据本质是高度关系化的
  （志愿者 ↔ 活动 ↔ 工时 ↔ 捐款），关系型数据库天生适合，别去碰 NoSQL。
- 这套组合的教程、Stack Overflow 答案、招人难度都最友好。

**唯一要提醒**：不要一开始就上花哨的前端框架（React/Vue）。先用 Django 自带的模板（HTML）
或者干脆只用 Admin。前后端分离是你 MVP 跑通、真正需要好看的用户界面之后才考虑的事。

## 二、心态转变：现在最该扔掉的想法

> "我要根据成熟 app 搭一个最小 MVP"

这句话里藏着一个陷阱：**ERPNext 和 CiviCRM 是"抄框架"的错误对象。**
它们是几百人年做出来的通用产品，为了适配全世界所有非营利组织，抽象层极其复杂。
你去读它们的代码会被淹没。

正确的用法是：**把它们当"需求清单"和"数据模型字典"来读，而不是当"代码模板"来抄。**

- 看 CiviCRM 有哪些模块（Contacts、Contributions、Events、Membership、Activities）
  → 这告诉你**一个成熟的组织管理系统应该覆盖哪些概念**。
- 看它一个"联系人"表有哪些字段 → 这告诉你**你自己建表时别漏了什么**。
- 但**代码实现一行都别抄**。你自己用 Django 从零写，反而更简单、更懂。

## 三、核心方法：从"领域建模"开始，而不是从代码开始

你不知道从哪开始，是因为你想直接开始写代码。但大型应用真正的起点是
**画清楚"你的世界里有哪些东西，它们怎么关联"**（数据模型 / domain model）。

对你的基金会，核心实体大概是这些：

| 实体 | 说明 | 关键关系 |
|------|------|---------|
| **Volunteer（志愿者）** | 人的档案：姓名、联系方式、技能、状态 | 参与多个 Event |
| **Event（活动）** | 一次志愿活动/项目 | 有多个 Volunteer 参与 |
| **Participation（参与记录）** | 谁在哪个活动做了多久 —— 连接志愿者和活动 | 关联一个 Volunteer + 一个 Event，记录工时 |
| **Donation（捐款）** | 一笔钱进来 | 关联捐款人 |
| **Donor（捐款人）** | 出钱的人/机构 | 有多笔 Donation |

注意 **Participation** 这张"中间表"——它是新手最容易漏、但最关键的东西。
"志愿者"和"活动"是多对多关系，你需要一张表专门记录"某人在某活动做了 3 小时"。
想清楚这类关系，比写代码重要 10 倍。

**你的第一个作业（不用写代码，用纸或文档）**：
画出你基金会里所有"东西"和它们的连线。这一步做对了，Django 的 model 几乎是照着抄。

## 四、分阶段路线图（每一阶段都能跑起来看到成果）

### Phase 0 — 学习与建模（不写业务代码，1~2 周）
- 跑完官方 Django Tutorial（那个投票 app），把 model / view / template / admin 四件套跑通一遍。
  这是你唯一必须完整做的教程。
- 浏览 CiviCRM 的功能模块列表，列出你基金会**真正需要**的功能（大概率只需要 CiviCRM 的 10%）。
- 画出上面说的领域模型图。

### Phase 1 — 纯 Admin 的 MVP（你的第一个"能用的东西"）
- 用 Django 定义 Volunteer / Event / Participation 三张表。
- **什么前端都不写**，直接用 Django Admin 管理它们。
- 目标：你能在浏览器里录入志愿者、创建活动、登记谁参加了。
  **这一步就已经比很多小基金会的 Excel 强了。**

### Phase 2 — 加入资金追踪
- 加 Donor / Donation。
- 做几个简单的统计页面（本月捐款总额、某活动的总工时）。
  这是你第一次写"自己的页面"而不只是 Admin。

### Phase 3 — 给真实用户用的界面
- 这时才考虑好看的前端、权限（志愿者只能看自己的、管理员看全部）、报表导出等。

> **关键原则**：每个 Phase 结束都必须是"能给基金会的人看、能真实录一条数据"的状态。
> 永远不要憋一个大版本。

## 五、成熟 app 里"值得抄"和"该自己定制"的分界

- **值得学（概念层）**：数据模型的字段设计、状态流转（志愿者的 active/inactive、
  捐款的 pending/received）、软删除而非硬删除、审计日志（谁改了什么）。
- **该你自己定制**：具体的业务流程、界面、报表——因为这些正是"你这个基金会和别人不一样"
  的地方，也是通用产品做得臃肿难用的地方。
- **别碰**：它们的插件系统、多租户、国际化、复杂权限引擎——这些是产品化的负担，
  你一个组织不需要。

## 六、下一步：先回答这几个问题

想清楚了，你的模型就清楚了一大半：

1. 一个志愿者，你需要记录他哪些信息？（除了姓名电话，还有技能？可服务时间段？背景审查状态？）
2. "资源"里的 people、money、event 三者，眼下**最痛**的是哪个？先只做那一个。
3. 谁会用这个系统？只有你一个管理员，还是志愿者自己也要登录？
4. 现在这些数据是记在哪的——Excel？纸质？
   （你的第一版目标就是"比现在这个稍微好一点"，不是比 CiviCRM 好。）

> 想清楚这些，下一步就可以一起把领域模型图敲定，然后再开始建 Django 项目。
