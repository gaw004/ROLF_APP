## 2026-08-14 修订：`kind` 收窄成 `staff | board`，报酬拆成独立字段

**本文正文里所有写着 `kind = employee | volunteer | board` 的地方都已经过时**，
现在是 `kind = staff | board` + `compensation = paid | unpaid | stipend`。
全文见 [D32](D32-worker-axes-schedule-and-assignment.md)。

结构一个字节没动 —— `Position` / `Assignment` 的分层、汇报线挂编制、
一人多岗、空缺可表达，四条全部照旧。变的只是 `kind` 这一个字段扛了两件事：
「他在组织里是什么」和「拿不拿钱」。基金会出现了「像员工一样有固定岗位和
固定开会时间、但不拿钱」的一类成员，那个字段就说不出来了。

**本文有一句话反而是这次修订的判据**，原样成立、不需要改：

> 空缺编制必须说得出自己是有薪岗还是志愿岗（招人的时候正是要知道这些）。

它决定了 `compensation` 必须挂 `Position` 而不是 `Assignment`。

跟着作废的两处：

- 末尾那条 `employment_type` 只对 `kind=employee` 有意义的 `clean()` 提示**已删除**。
  无薪的人一样分「每周来两天」和「每周来五天」，那个信息交给新的
  `Assignment.fte`，`employment_type` 回到它字面的意思（合同形态）；
- **「`EmployeeProfile` 因此不建」的结论维持，但理由要更新**：现在多了
  `service_start_date` 和 `employee_number` 两个人级字段，它们放在 `Contact` 上。
  本文当时的理由是"只剩员工编号之类的零碎"，字段数为 2 时那句话仍然成立 ——
  重新考虑的条件写在 [D37](D37-hris-fields-and-credentials.md)。

**薪酬暂不入库那一节不变**，`payroll` 独立 app 的位置也不变。

## 第一次修订：为什么 `EmployeeProfile` 不行

<details>
<summary>展开（已被后续修订取代，保留作记录）</summary>

1. 把汇报线挂在人身上，就归属不到某个身份。 张三是项目部兼职员工（上级 Alice）、
   同时是食物银行的志愿者协调员（上级 Bob） —— 问"张三作为员工向谁汇报"答不出来。
   注意这不是存不下，是**说不清哪条线属于哪个身份**（歧义，而非表达力不足）。
2. 1:1 的 `EmployeeProfile` 压根装不下一人多岗。 张三如果同时是项目部兼职 +
   财务部兼职，两个职务、两个部门、两个上级 —— 一对一表只有一个 title 一个 department。

**根因**：把"岗位"信息塞进了"角色"表，混淆了 D10 里的两个层次。

</details>

## 第二次修订：为什么 `reports_to` 不能指向 `Assignment`

<details>
<summary>展开（已被后续修订取代，保留作记录）</summary>

第一次修订把 `reports_to` 挂到了 `Assignment` 行上，理由是"你向的是**岗位**，不是 Alice 这个人"。
**方向对了，但落点错了** —— `Assignment` 带 `start_date` / `end_date`，它表达的是
"张三 **2024–2026 年**担任项目总监"，也就是一段**任职期**，不是一个岗位。
让下属指向它，等于把汇报线绑在了某个人的某一段任期上。四个后果：

1. 换人 = 重写所有下属。 张三离任、李四接任 → 李四是一行**新的** `Assignment`，
   于是所有下属的 `reports_to` 必须逐个改指过去。
2. 改完之后历史就是错的。 小明那一行从 2024 年起没动过，`reports_to` 却已经指向李四 ——
   这行现在在声称"小明从 2024 年起就向李四汇报"。要保住历史只能给小明也截断日期、
   新建一行，**而小明的工作根本没变**。
   > 准确的历史确实还在（`Assignment` 挂了 simple-history），但**只在历史表里** ——
   > 主表答不出"2025 年小明向谁汇报"。这是"可追溯但不可查询"，不是"丢了"，严重性别夸大。
   > 但它仍然违反了本文档对「`is_active` 挨着 `end_date`」判死刑时用的同一条标准：
   > 主表不许存出自相矛盾的行。
3. 空缺根本表达不了 —— 这一条是决定性的。 张三走了、李四还没到位，
   这个编制客观存在（它有下属、有预算、正在招人），但系统里**没有任何一行代表它**，
   下属的 `reports_to` 只能指向 `null`。自引用到任职行，在数据层面就没有"位置"这个东西可以指。
4. **原文有一句话是假的**（已删除）："执行总监向的是'理事长这个职位'，
   理事长换人时组织结构本身没变"。组织结构确实没变，但**数据必须改** ——
   那是 `Position` 才有的性质，被拿来论证了一个不具备该性质的设计。

**根因（和第一次修订是同一种错）**：第一次修订把"岗位"从"角色"里拆出来了，
但**没有把"编制"从"任职"里拆出来** —— 一行 `Assignment` 同时在回答
"这是哪个格子"和"谁在什么时候占着它"两个问题。**一张表承担两个层次**，
正是第一次修订批评 `EmployeeProfile` 的那条罪名。

> **留下的教训**：拆层拆到一半比不拆更危险 —— 因为它看上去已经解决了问题。
> 判据是 D10 新加的那句口诀：换个人来做还成立的，就属于编制。

</details>

## 修订后的方案

```python
Position(                                # 编制：组织结构里的一个格子，与人无关
    code,                                # 唯一·不可改（D5 通则）
    name,                                # "项目总监"
    kind         = employee | volunteer | board,
    ministry     → Ministry (可空),       # 服务单元；理事不属于任何 ministry
    reports_to   → Position (可空),       # 上级编制，自引用
    is_leader,                           # 布尔，给代码查；name 是给人看的
    is_active,                           # 编制还设不设；≠「有没有人在任」
)

Assignment(                              # 任职：谁在什么时候占了哪个格子
    contact      → Contact,
    position     → Position,
    employment_type (可空),               # 全职/兼职/合同/实习，仅有薪编制
    start_date, end_date,                # 没有 is_active —— 在职状态由日期派生
)
```

**四个问题一次解决：**

| 问题 | 靠什么解决 |
|---|---|
| 换人不动下属 | 汇报线在 `Position` 上；李四接任只是多一行 `Assignment`，下属一行不改 |
| 历史是对的 | 下属那一行从没被改过，`(position, start_date, end_date)` 三个字段自洽 |
| 空缺可表达 | 有 `Position` 行、没有在职 `Assignment` = 空缺，**而且它照样带着 kind / ministry / 下属** |
| 一人多岗 | 两行 `Assignment` 指向两个 `Position`，各自的上级由各自的 `Position` 决定 |

为什么 `kind` / `ministry` / `is_leader` 都挂在 `Position` 而不是 `Assignment`：
空缺编制必须说得出自己是有薪岗还是志愿岗、属于哪个 ministry、是不是个 leader 位
（招人的时候正是要知道这些）。挂在 `Assignment` 上的话，空缺编制**这些全都没有** ——
而"能完整描述一个空缺"正是这次修订的全部目的。
连带的好处：**只看 `Position` 一张表就能画出完整的组织架构图**，不 join 任何任职数据。

一个 `Position` 可以有多个在职 `Assignment`。 `Position` 是**编制类型**，不是"座位" ——
三个食物银行志愿者 = 一个 `Position` + 三行 `Assignment`，不是三个 `Position`。
这是这张表能保持在几十行量级、不膨胀成几百行的原因。
**因此不加"一个编制同时只能有一个在职任职"的约束** —— 它既挡不住合法的多人共岗，
也挡不住合法的交接期重叠。

**汇报线只存在 `Position` 上**，`manages` / `managed by` 关系类型**不再用于组织架构**
（见 D6 的适用范围补充）。这一点很重要：初版批评"加 manager FK"的理由正是
"同一件事记两个地方"，所以修订后的方案不能自己犯同样的错 —— 不是两处都能记，是只有一处能记。

`EmployeeProfile` 因此不建。 职务 / 部门 / 上级去了 `Position`，
雇佣类型 / 起止去了 `Assignment` 之后，它只剩员工编号之类的零碎，MVP 阶段不值得一张表。
**`VolunteerProfile` 保留**，因为它装的是真正的人级事实（技能、背景审查），见 D10 的四层标准。

**代价（三条，都要如实说）：**

1. 多一张表、多一步录入。 给人建 `Assignment` 之前必须先有 `Position` 行。
   缓解就是上面那条"一个编制多人在任" —— 几十行的表，不是每人一行。
2. 同名的有薪岗和志愿岗是两个 `Position` 行。 "ESL 教师"如果既有志愿者也有受薪的，
   就是两行。HR 语义上这是对的（不同编制、不同预算线），但录入时会觉得啰嗦。
3. `Position.reports_to` 本身仍然是无日期的可变字段。
   组织重组（"项目总监改为向 COO 汇报"）时覆盖它，**旧的组织架构一样丢**，只剩 simple-history。
   这次修订解决的是"**换人**"（常发生），没解决"**重组**"（少发生）。
   真要解决得给编制层级本身加起止日期（双时态建模），**现在不做**，见推迟清单。
   **这是一个已知的不完美，不粉饰** —— 同 `clean()` 挡不住 `bulk_create`。

已知限制：一个编制只能有一个上级。 实线 + 虚线的矩阵式双上级存不了。
真需要的话要把 `Position.reports_to` 改成多对多 —— 小基金会极少有矩阵汇报，现在不做（见推迟清单）。

**约束**：`Position.reports_to` 不能指向自己那一行（`CheckConstraint`）。
跨行环路（A→B→A）数据库拦不住，防线见 Phase B 的「汇报线的环」。

**`employment_type` 只对 `kind=employee` 的编制有意义** —— 但那是跨表判断
（`employment_type` 在 `Assignment` 上、`kind` 在 `Position` 上），
`CheckConstraint` 表达不了，只能落在 `clean()` 提示层。按 D14 的标准记一笔，不假装它是强制的。

**薪酬数据暂不入库**。工资是本系统里敏感度最高的数据，一旦入库就要处理字段级权限、
加密、审计、以及"谁能看到谁的工资"这类问题，而 MVP 阶段没有任何功能需要它。
**何时重新考虑**：真的要在系统里算人力成本或做预算报表时 —— 那时要连同权限方案一起设计，
不能顺手加个字段了事。

**理事会席位用 `kind=board` 的 `Position`**（已确认）。理事长 / 财务负责人 / 秘书 /
普通理事都是编制，有任期的是**占着它的人**（`Assignment` 的起止日期）—— 和其它岗位完全同形。
好处是"这个人在基金会的所有身份"永远只查一张表 —— 理事同时捐款、或先做志愿者后进理事会，
都是同一个 Contact 下多加一行 `Assignment`。

由此产生的两个字段影响：

- **`Position.ministry` 必须可空** —— 理事席位不属于任何 ministry。
  （`employment_type` 本来就可空，理事无薪。）
- **汇报方向可以反过来**：执行总监这个 `Position` 的 `reports_to` 指向**理事长那个 `Position`**。
  **这次这句话是真的了**：理事长换人 = 多一行 `Assignment`，
  `Position` 一个字节不动，执行总监的汇报线也一个字节不动。
  这正是第二次修订要买的东西（对比「第二次修订」第 4 条被删掉的那句假话）。
