# D23 · 界面统一用英文；中英双语（gettext）推迟（2026-07-31 改口）

结论：界面文案**统一写成英文**，不做双语，不引 `gettext`。
Phase C 的模板重写只做一件事 —— 上 Tailwind、把文案改成英文。
`LocaleMiddleware` / `LANGUAGES` / `.po` / `compilemessages` 这一整套**一律不进本阶段**。

> 这条决策**当天改过一次口**。早上定的是「上完整中英双语，只翻界面」，
> 下午推翻。原结论和它的推理保留在下面[改口之前定的是什么](#改口之前定的是什么以及为什么推翻)，
> 一个字没删 —— 本项目的规矩是改口要留说明。

## 为什么是英文单语

基金会在 Santa Clara，志愿者读英文。而 Phase B 写出来的 16 个模板文案**全是中文** ——
所以「改成英文」不是新增工作，是把本来就要重写一遍的文案换一种语言写。
Phase C 本来就要逐个模板上 Tailwind，**同一趟里改掉，边际成本接近零**。

而双语要付的是另一笔账：`.po` 文件、`compilemessages` 进构建、每改一句文案动两处、
以及下面代价那一节里那个**不报错**的坑。**为一批读英文的用户付这笔账，买不到东西。**

按 [`goal.md` 的判定规则](../goal.md#零当前优先级2026-07-29-定)（「是不是那 14 条需求的前置条件」）：
双语不是，**英文单语是** —— 用户读不懂界面，P3「普通 account 能看到已发布的 event，能报名」
就不成立。同一条规则，两个相反的结论，这正是它有用的地方。

## 代价，如实说

1. 中文使用者看英文界面。基金会内部沟通如果是中文，这一条要**先跟他们确认**再上线；
2. 现有 16 个模板 + 约 34 处 `label` / `help_text` + 20 处 `messages` / `ValidationError`
   的中文文案要逐个改成英文。这是一趟**必须逐文件读一遍**的活，和上 Tailwind 同一趟做；
3. 以后真要双语时，`gettext` 要从零补一遍 —— 但那时改的是**同一批文件**，
   不会更贵，只是不会更便宜。

## 什么时候重新考虑

基金会明确说要中文界面，或者出现读不懂英文的志愿者报不上名的实际情况时。
那时按早上那份方案做（[改口之前定的是什么](#改口之前定的是什么以及为什么推翻)里写的
`gettext` + `set_language` + cookie，不上 `i18n_patterns`，不引第三方多语言库），
**并且不要改成中文单语** —— 那只是把同一个问题换个人承受。

重启条件同时写进 [`../deferred.md`](../deferred.md)。

## 改口之前定的是什么，以及为什么推翻

<details>
<summary>2026-07-31 早：上完整中英双语，只翻界面（已推翻）</summary>

原结论：**上完整的中英双语，但翻译的边界划在「代码里的字面量」上 ——
界面文案全翻，数据库里的值一个不翻。技术上用 Django 自带的 `gettext` +
`set_language`（cookie），不上 `i18n_patterns`，不引第三方多语言库。**

### 当时的理由

基金会在 Santa Clara，志愿者大概率读英文；而 Phase B 写出来的 16 个模板文案全是中文。

成本随时间涨得很快：当时是 16 个模板、约 34 处 `label` / `help_text`、
20 处 `messages` 和 `ValidationError`。每加一个页面这个数字就涨一次，
而且补翻译是一件必须回头逐个文件重读的事。

更实际的一条：Phase C 本来就要把 16 个模板逐个重写一遍上 Tailwind，
同一趟里把 `{% trans %}` 包上，边际成本接近零。

### 边界：为什么是「代码里的字面量」

`gettext` 只能翻**源码里写死的字符串**。而这些是**数据库里的值**：

| 例子 | 它在哪 |
|---|---|
| `Ministry.name` = "食物银行" | `org_ministry` 表的一行 |
| `EventType.name` / `ParticipationRole.name` = "搬运" | 字典表的行（[D5](D05-lookup-tables-not-enums.md)） |
| `Event.name` = "周六食物发放" | 用户录进去的 |

`makemessages` 扫不到它们，这不是疏忽，是原理。

### 当时考虑过的另两条路

**① 字典表加 `name_en` / `name_zh` 两列。** 要改四张字典表 + 迁移 +
admin 表单 + 所有显示处，而基金会自己录入时
完全可以写「Food Bank 食物银行」一行解决。

**② 上 `django-modeltranslation`。** 它会改模型元数据、动态给字段加列。
撞[方法论](../goal.md#一终极目标)里「不自造框架、标准 Django 写法」和
「一个人能读完全部代码」两条。

### 当时的技术选择：不用 `i18n_patterns`

| | URL 前缀（`i18n_patterns`） | cookie / session（`set_language`） |
|---|---|---|
| URL 长什么样 | `/en/events/`、`/zh-hans/events/` | `/events/`（不变） |
| 现有测试 | 334 个测试里写死的 URL 要全部改 | 一个都不用改 |
| 分享链接带语言 | 带 | 不带 |
| SEO | 更好（每种语言一个 URL） | 一般 |

选后者：本系统是登录后使用的内部工具，SEO 无关；而「改 334 个测试」
是一笔纯粹的、不产生任何价值的开销。**这一段在重启时仍然成立，照抄即可。**

### 当时如实写下的代价（其中第 1 条正是推翻它的原因之一）

1. ⚠️ **漏包一处 `{% trans %}` 不报任何错**，那句话就永远保持原样。
   缓解是一条 grep 守卫（模板里不许有未包裹的中日韩字符），
   但守卫只管模板，**Python 侧漏包只能靠 review**；
2. 切成英文界面后，活动名和 ministry 名仍是录入时那种语言，必须跟基金会说清楚；
3. 每改一句文案要动两处（源码 + `.po`），并记得跑 `compilemessages`；
4. 两倍的文案维护面。

</details>

### 推翻的理由

一句话：**双语的成本是真的，收益是猜的**。

- 收益那一侧的假设是「有人需要中文界面」—— 而基金会在 Santa Clara，
  这个假设**没有任何人验证过**。为一个未经验证的假设付固定成本，
  和[「这张表会出现在哪条需求的查询里」](../goal.md#已实现但暂时用不上的留着不删)
  那条自查是同一个病；
- 成本那一侧则全是确定的：`.po` 进仓库、`compilemessages` 进构建、
  文案两处维护、以及上面代价第 1 条那个**不报错**的坑；
- 而**改口几乎不产生浪费** —— 早上那份方案还没写一行代码
  （`03-roadmap.md` 里的 C1.1 / C2.5 / C2.6 / C2.7 都只是计划）。
  真正的工作量（16 个模板逐个重写）两个方案里都要做，只是文案写成英文而不是包 `{% trans %}`。
