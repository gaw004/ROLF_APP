## 为什么不是 React

理由**不是** React 不好，而是**分离想买的东西，这个项目已经买到了，而且没付钱**。
完整论证在 [`../phase-c.md` 的「考虑过并否决的：全量 React SPA」](../phase-c.md#考虑过并否决的全量-react-spa)，
不在这里重复。一句话版本：分离的核心好处是「换前端时后端不用动」，
而这靠的是业务逻辑不在界面层 —— [D18 的落点规矩](D18-admin-boundary.md)
已经强制了这件事，并且有 grep 守卫盯着。

而分离最贵的代价正好打在 [D20](D20-ministry-role.md) 上：**权限判断会变成两份**。
服务端那份是安全边界必须留；前端还要再判断一次才知道该不该显示「签到」按钮，
而它够不到 `org/permissions.py`。D20 存在的全部理由就是「散落的权限判断迟早有一处忘了
`.active()`，而漏掉的权限检查是静默的」。

**颜值和这个选择无关。** 「媲美顶级大厂的现代视觉」要的是设计系统和 CSS，
那是 Tailwind + [`../design-system.md`](../design-system.md) 的活，
和渲染发生在哪一端没有关系。

## 三层的分工

这一节是本条决策的可执行部分。判据都是**能当场做的动作**。

| 层 | 只管什么 | 判据 |
|---|---|---|
| Tailwind | 长什么样 | 把 `static/css/app.css` 删掉，**页面必须仍然可用** —— 难看但每个按钮都在、每条信息都读得到（沿用 [`../phase-c.md` 的样式落点](../phase-c.md#样式的落点css-只许出现在两个地方)） |
| HTMX | 服务端片段交换：局部刷新、表单内联提交、轮询 | ⭐ **每一个写操作都必须有一条完整的服务端表单路径，HTMX 只是它的快路**。见下面「渐进增强的口径」 |
| Alpine | 纯客户端 UI 状态：展开 / 收起 / 选中 / 模态 / 主题切换 | 把模板里所有 `x-` 属性删掉，**每个写操作必须仍然能完成**。见下面「Alpine 的落点」 |

### 渐进增强的口径：只管写操作

**写操作**（报名、取消、签到、签退、发通知、改活动、授权 / 撤销 admin、
改资料、增删紧急联系人）**必须各有一条不依赖 JavaScript 的完整表单路径**。
HTMX 端点是同一个视图的另一种响应，不是另一条逻辑。

**读操作不受这条约束** —— 筛选、排序、展开详情可以只有 HTMX 那一条路。

两个理由：

1. **它保住了现有的 404 个端到端测试。** 那批测试直接打 URL、断言 HTML 和 403，
   靠的正是「每个动作都有一个能 POST 的 URL」。这条口径一破，
   测试就退化成只覆盖片段端点那一半 —— 而那恰恰是[否决 React 时列出的代价之一](../phase-c.md#考虑过并否决的全量-react-spa)，
   换个技术栈把它请回来，等于白否决；
2. 它和样式那条判据是**同一个句式**：删掉一层增强，核心功能仍然成立。
   本项目已经有一条这样的规矩，第二条照抄形状，不用另学。

### Alpine 的落点：只有 UI 状态，没有业务判断

`x-data` 写在模板里，所以它是**最容易把业务逻辑偷偷搬进界面层**的地方 ——
这正是 [D18](D18-admin-boundary.md) 和那 12 条 grep 守卫一直在防的事。

**不许出现在 `x-` 属性里的**：权限判断（谁能看见这个按钮）、
工时 / 金额的计算、日期运算、以及任何「服务端已经算过一遍」的数字。

具体规矩和守卫的实现写在 [`../design-system.md`](../design-system.md)，
执行方式是两层：本地 `.pre-commit-config.yaml` + CI 里的强制 workflow。

## 代价，如实说

1. **多两个运行时依赖**（htmx、alpine），且它们进了 `package.json` ——
   而在此之前这个仓库**没有任何前端构建**。构建链本身要维护；
2. **写操作要写两种响应**（整页 + 片段）。这是渐进增强口径的直接账单，
   主动付的，换回来的是那 404 个测试一行不改；
3. ⚠️ **Alpine 的越界不会报错**。把一个权限判断写进 `x-show`，页面照常渲染、
   测试照常绿，只是那个按钮对不该看见它的人也画出来了 ——
   服务端仍然会 403，所以**它泄露的是信息不是权限**，但那也是泄露。
   守卫测试就是为这一条存在的。

## 什么时候重新考虑

沿用 [`../deferred.md`](../deferred.md) 里 React 那一行的重启条件，**不变**：
真的要做手机 App（多客户端喂同一套后端），或者真的有第二个人专职做前端时。
那时加一层 DRF 是几天的事，**因为业务逻辑早就不在模板里**。

本条决策不改变那个条件，只是把「在那之前用什么」写清楚了。
