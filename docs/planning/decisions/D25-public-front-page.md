# D25 · `/` 是一张公开的门面页，不是按角色分流的调度页（2026-08-05）

结论：`/` 对**所有人**开放，登录与否看到的是**同一页** —— 一张满幅的图或视频、
一段经文、一条平时藏起来的顶栏、一个左侧滑出的菜单。
形制参照 Louis Vuitton 的首页。

这条决策**推翻了 [`../03-roadmap.md` 的 C3.1](../03-roadmap.md#c31-首页-)
原来的设计**，改口说明已就地写进那一步，不是只写在这里
（[`README.md` 加一条新决策时](README.md#加一条新决策时)的第 3 条）。

## 推翻了什么

| | C3.1 原计划 | 现在 |
|---|---|---|
| 谁看得到 | 未登录看介绍，登录的**各自跳到自己的列表** | 所有人**同一页** |
| 是什么 | 一个调度器 | 一张门面 |
| 成本 | 约一小时 | 几天 |
| 归属 | 硬前置（判据：分享出去的链接不能是 404） | 仍然解决那个 404，但**不再是一小时的事** |

> **为什么推翻**：那个调度器有用，但它不是首页。
> 把链接发给一个从没听过这个基金会的人，他打开看到的是一张登录表单 ——
> 而「分享出去的链接是 404」和「分享出去的链接是一张登录表单」
> 是同一个问题的两种形态。

⚠️ **代价如实说**：这是一块**不阻塞试点**的门面工程，而真正卡着试点的四件事
（[C3.0](../03-roadmap.md#c30-域名--发信服务--最先做因为它靠别人) 域名+SES、
[C3.4](../03-roadmap.md#c34-生产加固) 生产加固、
[C3.6](../03-roadmap.md#c36-备份--恢复演练) 备份演练、
[C3.7](../03-roadmap.md#c37-权限复核) 权限复核）当时一件都还没开始。
2026-08-05 明确接受了这个排序。

## 裁切：存一个焦点，不存一个裁好的框（2026-08-13）

起因是一句话：「截的图位置我不喜欢」。照片是满幅铺的（`object-cover`），
多出来的部分从四边切掉，而**浏览器默认永远以正中心为准** —— 主体不在中间的
照片就会被切得不是地方。

| 考虑过的 | 为什么不是它 |
|---|---|
| 后台拖一个框、服务端裁好存起来 | ⚠️ **它解决不了这个问题**：满幅要填的那个洞，形状在每台设备上都不一样（竖着的手机留一条窄高的，笔记本留一条宽扁的）。裁成 16:9 存下来，手机上还会被再切一次 |
| 宽屏一张、窄屏一张 | 效果最好，但基金会每次要准备两张，还要懂哪张给手机。留给真的有人抱怨时 |
| **存一个焦点** ✅ | 说的是「这一块必须留住」，而不是「留住这一块」—— 一句指令对所有屏幕都成立 |

落成 `HomePage.hero_focus_x` / `hero_focus_y`（0–100，默认 50/50，也就是原来的行为），
`hero_focus` 这个属性把它们拼成 CSS 认的 `"50% 50%"`。

⚠️ **两个使用者，一个来源**：首页用 `object-position`，其余每一页深色模式下的
背景照片用 `background-position`，而那是**同一张照片**。各自拼一次字符串，
就是「首页和内页把同一张照片裁成两个样子，而两边各自看都说得通」——
`_hero_backdrop.html` 早就写着这句警告了。所以 `bg-center` 从那份片段里拿掉了。

⚠️ 范围落在**数据库约束**上，不只是表单（[D9](D09-rules-in-db-constraints.md) /
[D14](D14-constraint-is-the-only-rule.md)）：`object-position: 300% 50%` 是**合法的
CSS**，它会把照片推出自己的框，页面出来基本是空的，而没有任何地方报错。

⚠️ 原图一个像素不动 —— 裁切发生在浏览器里。所以改这两个数是免费且可逆的，
哪天想换个取景，原图还在。

### 后台里怎么改：点图片，不是填数字（同日）

「0=最左边、100=最右边」是给程序员看的说法，人用起来要在脑子里翻译一遍。
所以 admin 里画出**整张照片**（`object-fit: contain` —— 选点的时候必须看得见
四条边，按站点那样裁着显示就是在一张看不到边缘的照片上选点），点哪里焦点就到哪里。

⚠️ **那两个数字输入框没有被替换掉，只是被脚本降级成一行读数。** 它们仍然是表单
里唯一被提交的东西，控件只是往里写值 —— 所以脚本没跑起来时取景依然改得了。
⚠️ 降级是**脚本做的，不是样式表做的**：写进 CSS 的话，脚本挂掉的那次它们
也一起被藏起来，而那正是唯一需要它们的时候。同 [D24](D24-htmx-alpine-tailwind.md)
「每个写操作都要有一条不依赖 JS 的完整路径」。

⚠️ 视频也画预览（`preload="metadata"`，只取一帧）。焦点对图和视频都生效，
只给其中一个做控件，会在换成视频那天读成 bug。

## 公开与登录的分界线，动了一格

在此之前只有 `login` 和 `register` 是公开的。现在多一个 `/`。

> **判据**：**这一页是不是要发给一个还没有账号的人看的？**
> 是 → 公开。不是 → 要登录。

⚠️ 分界线**只移动了这一格**。活动列表、报名、我的资料、所有管理页
一如既往需要会话 —— 首页上那些链接点进去仍然会跳登录。
这是有意的：门面是给外人看的，数据不是。

## 首页的内容归谁改

`core.HomePage` 是一个**单例**模型（`HomePage.load()` 是唯一的读法，
第一次用时自己创建）。四个字段：背景图、背景视频、经文正文、经文出处。

**只有 foundation tier 能改**，靠 `core.change_homepage` 权限授予
`foundation_admin` 组实现，见 [`../../../org/permissions.py`](../../../org/permissions.py)。

> **为什么是这一档**：「改基金会的门面」这句话里**没有「某个 ministry 的」**——
> 那正是 [D20](D20-ministry-role.md) 判断一件事属于 Group 还是 MinistryRole 的
> 测试。ministry admin 发布活动；他们不代表整个基金会说话。

⚠️ **单例是被强制的，不是约定的**：`save()` 里写死 `pk`，`delete()` 直接拒绝。
一个能存两行的模型早晚会存两行，而那之后「哪一行是线上那个」
就变成了一个得有人在半夜回答的问题。

## 媒体文件：和活动图片同一条规矩，不同一套参数

| | 活动图片 | 首页背景 |
|---|---|---|
| 尺寸 | 最长边 900px | 满屏，2000px 起 |
| 寿命 | 活动结束即删 | 永久 |
| 数量 | 每场活动一张 | 全站一张 |
| 进不进备份 | ❌ | ❌ |

⚠️ **首页背景同样不进任何备份** —— `pg_dump` 覆盖的是列，而这是文件。
一张图加一段经文，人工恢复是一分钟的事，所以这个代价是**接受**而不是解决。
⚠️ 但**经文本身是列，是进备份的** —— 丢的只会是那张图。

⚠️ **视频不转码**。传上来什么就发什么，所以**上传者选的文件大小，
就是每个访客要下载的大小**。`help_text` 里写了 10MB 的建议值，
但没有任何东西强制它 —— 这一条靠人，不靠代码。

### 换新图时，旧对象跟着走（2026-08-14 补）

⚠️ **在此之前不走。**Django 把新上传写在新 key 上、忘掉旧的，所以每换一次首页图，
公开桶里就多一个没有任何行指着的对象。上面那张表里「数量：全站一张」说的是
**行**，而桶里躺着的是**每一张传过的**。

⚠️ **这一格是全项目漏文件最贵的地方**，理由就在这张表里：活动图片和 Memories
进来都要重编码，首页那一栏「尺寸：满屏、2000px 起」是**原样存的原图**。

删除挂在 `HomePage.save()`（不是 admin —— [D18](D18-admin-boundary.md)：shell 和脚本走不到那条路），
比对的是**数据库里那一行**而不是内存里的实例，并且在 `transaction.on_commit`
之后才执行：当场删的话，一次回滚会留下「行指着一个不存在的文件」，
表现是首页一张碎图而**全程没有任何报错**。删失败只记日志 ——
这时候保存已经提交，图确实换成功了，报 500 只会让人再按一次保存。

⚠️ **清空字段也算换。**留在**公开**桶里的文件仍然是一条打得开的 URL。

历史遗留的那些由 `python manage.py purge_orphaned_home_media` 列出来，
⚠️ **默认只打印，`--delete` 才真删，而且不上定时任务** ——
它的判据是「数据库里没人提到你」，而一个正在上传到一半的文件、
一次滚动部署中新旧 worker 各持一行的瞬间，长得和孤儿一模一样。

## 三件为可达性守住的事，不是可选项

1. ⚠️ **窄屏顶栏常驻显示。** 触屏**没有 hover** —— 一条只在悬停时出现的栏，
   在手机上等于永远不出现，也就是首页对手机用户**没有任何入口**；
2. ⚠️ **`:focus-within` 也要让顶栏浮出来。** 键盘用户 Tab 进来时看不见它的话，
   首页对他们同样是一张没有入口的图；
3. ⚠️ **菜单面板用 `translateX` 移出视口，不用 `display: none`。**
   后者会让里面的链接对读屏软件**根本不存在**，而它们是这一页唯一的导航。

## 白字压在一张没见过的照片上

⚠️ 背景是基金会自己传的，**内容不可预知**。所以对比度不能指望照片，要自己造：
一层全屏的轻压暗，外加一层集中在下三分之一的强压暗（经文在那里）。

第一版只有一层温和的渐变。拿一张带白色云团的测试图一试，经文中间两行直接糊掉。
加强之后**量出来的实测值**：顶栏区 9.94:1、经文区 5.57:1，都过 4.5。

> **这条的一般形式**：**任何压在用户上传内容上的文字，对比度都必须由我们自己保证。**
> 「我传的图都挺暗的」不是一个能写进代码的前提。

## 滚动时的呼吸感

活动列表的卡片在进出视口时轻微位移和缩放，参照 iOS Messages 的手感。

⚠️ **只动 `transform` 和 `opacity`，绝不动间距。** 滚动中改 `margin` 会改变页面
总高度，浏览器要不断重排、滚动位置和手指打架 —— 结果不是呼吸感，是页面在抖。
视觉上两者是同一件事，代价差一个数量级。

⚠️ 实现是**纯 CSS 的滚动驱动动画**（`animation-timeline: view()`），零 JS。
Firefox 目前不支持，那里就是「没有动画」，列表照常可用 ——
`@supports` 保证不支持的浏览器连规则都不会应用。
`prefers-reduced-motion` 下整段不生效。

> 选 CSS 不选 JS 的理由是**性能**：要求原文是「尽可能在实现滚动效果下
> 不改变原本的流畅」。逐帧 JS 物理更接近 iOS 的手感，但它要在每个滚动帧里
> 算一遍，而这正是那句要求排除掉的东西。
