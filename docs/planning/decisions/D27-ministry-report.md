# D27 · 管理列表旁边的 ministry 报表，以及 absent 状态终于有了写入路径（2026-08-05）

结论：`/events/manage/` 加上和志愿者两页一样的时间段筛选，右边挂一块报表面板 ——
**九个数字 + 五张图**，按需生成。列表在报表开着的时候让出 Ministry 和 Ends 两列。

同一天补上了一条从项目开始就缺着的写入路径：`Participation.Status.ABSENT`。

## ⭐ 唯一的不变量：报表描述的是**这一次筛选**

`ministry_report()` 收的是一个**已经筛过、已经按权限收窄的 Event queryset**，
不是一个 ministry id。

这一条决定了三件事，而且是免费得到的：

| | 为什么 |
|---|---|
| 两种身份共用一段代码 | ministry admin 的列表本来就只含自己那几个 ministry，foundation tier 的含全部。报表照抄，不需要第二套权限判断 |
| 报表不可能比页面宽 | 它没有能力去查列表之外的东西 —— 传 `ministry_id` 的写法就有 |
| 筛选自动生效 | 时间窗和 ministry 已经在那个 queryset 里了 |

⚠️ 这是**结构上**排除，不是靠测试盯着。传 id 的版本需要在报表里再判一次权限，
而那一处判断迟早会和列表那一处走散。

## 十三个指标，以及为什么是这十三个

用户从一份更长的候选清单里挑的（2026-08-05）。没选上的那些不是不好，是
**一次上二十个指标的结果通常是没人看任何一个**。

**数字**：活动场次 · 报名人次 · 独立志愿者数 · 已记录工时 · 人均工时 ·
回头率 · 满员率 · **缺勤率**（当天追加，见下）· 未成年无同意记录

**图**：每月活动数 · 每月已记录工时 · 各工种要几人/来了几人 · 工时排行 top 10 ·
按工种的工时

### 四个数字带着自己的注脚出页面

不是补充说明，是它们能不能用的前提：

| 数字 | 注脚 | 如果不写会怎样 |
|---|---|---|
| 已记录工时 | 「基于 N 条记录，M 条报名没有工时」 | 一个只记了三条工时的月份，和一个认真记满的月份，长得一模一样 |
| 回头率 | 「N / M，在这个时间段里」 | 会被读成「这个人是不是老志愿者」，而它答的是「这个时间段有没有养成习惯」 |
| 满员率 | 「N / M 个提了人数要求的活动」 | 分母混进没开工种的活动，比率会因为**量不出来**而变低，读起来像缺人 |
| 缺勤率 | 「N / M 场每条报名都处理过的活动」 | 没人记考勤的时间段会显示 0% 缺勤，和「真的没人缺席」长得一模一样。[分母那一节](#缺勤率分母是这一条里唯一难的地方同日追加)专门讲它 |

⚠️ 工时的偏低**不是随机误差**，它跟着「哪个 admin 记得点签退」走。
用户 2026-08-05 明确接受了这个偏差；不能接受的是**只印总数**。

### 未成年无同意记录：唯一的风险指标

整张表别的数字答的是「做得怎么样」，这一个答的是「有没有出事」。

所以它**为 0 时也画出来，而且只有它是红的** —— 藏起来的话，「没有」和「没算」
在页面上长得一模一样。同 P6 那个「联系不上」组的规矩。

⚠️ 它问的问题必须和 `consent_required_for()` 一字不差：活动要求同意 **且**
（未成年 **或** 没有生日）**且** 没有同意记录。问法一旦不同，
这个数字就在替一条它其实没检查的规则打包票。

## absent：一个存在了几个月、没有任何地方能写入的状态

`Participation.Status.ABSENT` 从建表起就在 choices 里，而全项目**没有一处写它**。

⚠️ 这比没有这个状态更糟：任何「缺勤率」都会**恒等于 0**，每个 ministry、
每个时间段都一样 —— 一个看起来是好消息、不报错、也永远不对的数。

补的是一条写入路径，不是一个字段（所以没有迁移）：

- **谁**：签到页每行的「No-show」按钮，只有 ministry admin 能按；foundation tier 只读；
- **拒绝的两种情况**：已记工时（用户拍板），以及已签到 —— 后者是我加的，
  同一个理由：留着会印出「checked in 3:44 p.m. · No-show」这样一行；
- **回头路**：`check_in()` / `record_hours()` 照常把状态盖回 attended，
  不需要先撤销缺勤。要求先撤销，结果是没人再标缺勤。

⚠️ **已知缺口**：签到点错了行仍然没有撤销的办法。以前也没有，这个按钮
**故意不兼任** —— 「撤销我点错的」和「记录他没来」是两件不同的事实，
一个按钮同时干这两件会让第二件变得没法读。

### 缺勤率：分母是这一条里唯一难的地方（同日追加）

第一版没放进报表，理由是「它只在有人真的去标的活动上有意义」。
用户当天要求加上，并且带上「基于 N 场有人标注过的活动」的注脚。
落地的时候发现，**按字面实现会得到一个系统性偏高的数**。

⚠️ 「有人标注过」查不到。唯一的正面证据是**存在一条缺勤记录** ——
于是那个分母里**每一场都至少有一个人缺席**，算出来的比率永远低不下来。
这和不加注脚一样不诚实，只是方向反了。

所以问的是数据答得出来的那个问题：**这场活动还有没有报名停在 `registered`？**

活动结束后还挂着 `registered` 的行，意思就是没人处理过它。

| 场景 | 进分母 | 为什么对 |
|---|---|---|
| 10 人全签到、0 缺勤 | ✅ | 这场真的没人缺席，贡献一个诚实的 0% |
| 8 人签到、2 人标了缺勤 | ✅ | — |
| 8 人签到、2 人没人碰过 | ❌ | 那两个人我们**不知道** |
| 一个人都没处理 | ❌ | — |
| 一个人都没报名 | ❌ | 它不可能有缺勤，算进分母只会让认真的 ministry 显得懈怠 —— 同满员率排除「没开工种的活动」 |

第二行那个「10 人全签到」的场景，正是天真的分母会**丢掉**的一格 ——
而那恰恰是唯一能把比率拉低的证据。

## 图表：五张全是横条，而且没有引图表库

原方案说过要画服务端渲染的 SVG。真写下来五张图**全部是条形图**，
于是 SVG 的那点好处没有一样用得上，而 CSS 的条子反而更好：

- 它继承主题色 —— [D26](D26-palette-from-the-hero.md) 那套从照片推出来的 `brand-500`，
  SVG 里要另外把色值灌进去；
- 它自己会重排，不用管 viewBox；
- 不用引 ~200KB 的 Chart.js，也不用让读操作依赖 JS。

⚠️ **五张全是横的，包括两张按月的。** 这个面板在宽屏上只有半个屏，
十二根竖条各 20px 宽，底下还要塞「Aug 2026」。横过来每个标签独占一行，
而且五张图共用一个组件 —— 这一页上不可能出现两张长得不一样的图。

三条画图的规矩，都写在组件的注释里：

| 规矩 | 不遵守会怎样 |
|---|---|
| 按**最大值**缩放，不按总和 | 最长的条只画到三分之一，会被读成「占某个东西的三分之一」，而页面上没说那是什么 |
| 少于三根退回文字 | 一根柱子的柱状图看起来像在比较，但没有可比的对象 |
| 数字**始终**以文字写在条子旁 | 读屏软件读不出一个 div 的宽度 |

⚠️ 百分比在 `services.py` 里算好，模板只负责画 —— 模板里不许有算术（D18），
而 SVG 的坐标是算术。这一条是选 CSS 条子的附带好处。

## 列：让位是**临时的**

用户原话是舍掉三列。最后定成：

| | Event | Ministry | Starts | Ends | Status | Go to |
|---|---|---|---|---|---|---|
| 开着报表 | ✅ | — | 只有日期 | — | ✅ | ✅ |
| 关掉报表 | ✅ | ✅ | 带时间 | ✅ | ✅ | ✅ |

⚠️ **关掉报表，两列回来，Starts 也带回时间** —— 就是原来那一页，一点不差。
「少了两列、第三列还是缩过的」比「完全恢复原样」难记，
而这一页大多数时候是不开报表用的。

⚠️ Starts 在开着报表时**留着**。三列全舍的话，筛完「八月」之后，
页面上没有任何东西告诉你这些活动是八月的。

## 面板跟左边齐平，出口在一个链接之外

工种一多，报表会变成一长串 —— 我原来的方案是每张图加一个「Show all」。
**用户换掉了它**，而且换得更好：面板**不装下全部**，宽屏下高度跟左边的列表齐平、
超出部分自己滚；要看全的去**完整版**，那一份可以存成 PDF。

⭐ 这个设计正好解掉我当初反对图内滚动的理由（「滚动条里的图没人会滚到底」）——
**因为现在有出口了**。所以面板底部那两个链接不是装饰，是这个设计成立的前提，
而且它们在滚动区外面，永远看得见。

实现上「齐平」是纯 CSS 的：

⚠️ 宽屏下把面板那张卡片**绝对定位**撑满外壳。绝对定位的元素不贡献高度，
于是这一行的高度只由左边的列表决定，面板再高也只是自己内部滚。
外层的 flex 因此**不能有 `items-start`** —— 要靠默认的 stretch 把外壳拉到同高。

⚠️ 外壳有 `lg:min-h-[28rem]`。筛出三场活动时列表只有两百像素高，
齐平会把面板压成一条缝，什么都看不见 —— 所以「齐平」只在列表比它长时才生效。

⚠️ 窄屏整段不生效。那时是上下堆叠，没有「齐平」这回事。

## 完整版报表页与 PDF

`/events/manage/report/`，同一套筛选参数，**不分页**，末尾附活动清单 ——
用户要的是「董事会看的那种：这个季度我们办了这些活动，数据如下，一份文件自足」。

⭐ 数字和图和面板**共用 `_report_body.html`**。两份拷贝迟早有一份漏掉新指标，
而漏掉的那一份不会报错，只是少一格。

⚠️ 权限走 `_scoped_events()`，和列表页同一个函数。
**一份报表是被读一次就相信的东西**，没人会拿一个总数去对一个他看不见的列表 ——
所以「这个账号能看哪些活动」在这里绝对不能有第二份拷贝。

### PDF 走浏览器打印，不是服务端渲染

**代价如实说**：它不是一键下载，是弹出打印对话框、用户再选「另存为 PDF」。

换来的是 **PDF 和网页是同一份渲染** —— 没有第二套排版要维护。
以后真要换成服务端生成（WeasyPrint 能原样吃下这些 CSS 条形图），
改的只是「谁来光栅化这份 HTML」，报表本身一行不动。

⚠️ 当时还没部署过（C3.5 未做），WeasyPrint 要 pango / cairo 这类系统库 ——
在一个没验证过的平台上先加系统级依赖，是把部署风险提前吃掉。

面板上的「Save as PDF」跳到完整版并带 `print=1`，那一页 `load` 之后自动调打印框 ——
从面板到 PDF 一次点击，而印出来的是完整的那一份，不是被截断的面板。

⚠️ 关掉 JS 只是不自动弹框，页面和按钮都还在（D24 的渐进增强口径）。

## 分页：20 / 20 / 50

三个活动列表都分页。志愿者两页 20（卡片带图，一张挺高），管理列表 50
（表格行矮，而且看这一页的人在扫全局）。

⭐ **报表算的是筛选选出来的全部活动，不是当前这一页。** 这一条把本文开头那个
不变量改了措辞 —— 从「描述旁边那个列表」改成「描述这个筛选」。
翻页时跟着变的数字没有任何意义。

⚠️ **排序必须以唯一列结尾。** `-start_time` 不唯一 —— 同一分钟开始的两场活动
之间没有确定顺序，Postgres 可以在第 1 页和第 2 页给出不同的顺序，
表现是某一行出现两次、或者整个消失，**而不会有任何东西报告它**。加 `-pk` 兜底。

⚠️ 翻页链接用 Django 5.1 起内置的 `{% querystring %}`，它**保留当前所有查询参数**。
手写 `?page=2` 会把筛选条件和 `report=1` 一起丢掉 —— 症状是「翻一页，筛选没了」。

⚠️ 条数显示的是**筛选出来的总数**，不是这一页的长度。

## Generate report 是第二个 submit，不是实时计算

十三个指标是十来条聚合查询，挂在每一次改日期上会让**筛选本身**变慢，
而大多数时候人只是在翻列表。

⚠️ 它和筛选在**同一个表单**里，靠 `name=report` 区分。于是筛选条件和
「要不要报表」一起进 URL —— 这一份报表可以被收藏、被转发、被刷新。
另开一个表单的话两边的日期会各填各的。

⚠️ 反过来：点「Filter」不带 `report`，报表就消失。一份算给旧筛选的报表
贴在新列表旁边，是会**主动误导**人的 —— 那两个东西看起来属于同一页。

## 排版

宽屏左列表右报表；窄屏上下堆叠，**报表在上**。

DOM 顺序是「报表在前、列表在后」，宽屏靠 `lg:flex-row-reverse` 把列表摆回左边 ——
这样窄屏的堆叠顺序是自然得到的，不需要 order 工具类互相打架。

⚠️ 列表那一侧要 `min-w-0`。它是一张会横向滚动的表，而 flex 项的 `min-width`
默认是 `auto`（「不许缩到比内容窄」），少了它整页会横向滚动。
和筛选栏当初在 375px 下那个 bug 是同一个。

## 踩到的三个坑，都是「不报错的错」

### ① 显式 order_by 会混进 GROUP BY

管理列表交出来的是 `…order_by("-start_time")`。按月分组的时候，
那个排序**也进了 GROUP BY** —— 于是按「月 + 精确时间戳」分组，一场活动一组，
每组都是 1。

页面上左边列表列着十一场八月的活动，右边图上写着「Aug 2026 — 1 event」。

⚠️ Django 只会忽略 `Meta.ordering`，**不会忽略谁写的 `order_by()`**。
修法是在每一处 `values().annotate()` 之前 `.order_by()` 清掉。

⚠️ **这个是截图发现的，不是测试发现的。** 当时二十个测试全绿 ——
因为它们都自己造了一个没排序的 queryset。现在有一条专门传排序过的 queryset 的回归测试。

### ② 打印时 `column-count` 对 grid 容器完全无效

完整版报表印出来，**第一页只放下一张图，剩下大半页空白**。

图表容器在屏幕上是 `md:grid-cols-2`，而 A4 的打印视口够不到 `md`（768px），
于是每张图独占一整行。加了 `column-count: 2` 之后没有任何变化 ——
因为那个容器还是 `display: grid`，而**分栏属性对 grid 容器不生效，且不报错**。

打印规则里补一句 `display: block !important` 才成立。

⚠️ 顺带两条同类的：`body` 的浅灰底色印在纸上是整页铺一层灰墨；
条形图的底色默认会被浏览器「省」掉，于是所有条子变成空槽 ——
图还在，数据没了。两条都靠 `print-color-adjust: exact` 和强制白底解决。

### ③ 多表连接会把 Sum 放大

`Sum("needed_count")` 和数报名人数写在同一条查询里，EventRole 会连到 Participation，
那个 5 就按报名人数重复一次 —— 一个要 5 人、来了 3 人的工种报出「要 15 人」。

不报错，数字只是错了，而且**错的方向是让这个 ministry 看起来严重缺人**。
所以 `_role_gap()` 是两条查询在 Python 里合的。

## 顺带改的一处：`Contact.short_label`

工时排行原来用 `str(contact)`，而 `Contact.__str__` 会把邮箱或电话缀在名字后面 ——
它需要这么做，因为下拉框里选错一个「王强」是一次静默的数据错误。

**但排行榜不是选择器**，没有任何东西从它里面被选走。那个邮箱买不到任何东西，
只是被印在了一块人们会截图转发的面板上。

`short_label` 用 id 消歧，不用联系方式。⚠️ 仍然消歧 —— 两个同名的人在排行榜上
会被读成一个人上榜两次。
