# D28 · 现场扫码自助签到：动态二维码、到场凭据、以及它到底买到了什么（2026-08-07）

结论：活动现场 admin 在平板上开一个页面，**二维码里是一条带签名 token 的打卡 URL，
每 20 秒换一次**。志愿者用自己的手机扫，落到一个确认页，按一下完成 check-in 或
check-out，结果出现在他自己的 **My Signups** 那一行上。

这一条要解决的是一件很具体的事：**一场一百人的活动，让一个 admin 挨个点四十次
签到、四十次签退，是不可能被真的执行的**。不执行的后果不是「少一列数据」——
是 D27 那张报表里的已记录工时和缺勤率**同时失真**，而且失真的方向跟着「哪个 admin
比较负责」走，不是随机的。

---

## ⭐ 唯一的不变量：这是一个减少录入的工具，不是一个防作弊的机制

这一节放在最前面，因为原始需求把动态二维码称作「防作弊核心」，而**那句话是不成立的**，
后面所有的取舍都从这里推出来。

要防的是「有人拍下二维码发到群里，没来的人远程打卡」。轮换 token 对它的作用是：

| | 轮换前 | 轮换后 |
|---|---|---|
| 拍照发群，当天晚上再打卡 | ✅ 能 | ❌ 不能 |
| 现场的人实时把链接转发给朋友 | ✅ 能 | ✅ **还是能** |

也就是说，它把攻击成本从「零」抬到「**需要一个现场的活人当中继**」，仅此而已。
90 秒也好、30 秒也好，只要还有一个人站在那儿，转发就永远来得及 ——
微信转发一条链接是三秒钟的事。

⚠️ **没有任何加密手段能关掉这个洞**，因为服务器无法区分「这部手机在现场」和
「这部手机收到了现场发来的链接」。GPS 考虑过并否决（见下）。

所以这个功能的定位写死在这里：

> **权威仍然是 admin 的 attendance 页。** 自助签到是让那一页上大部分行**已经填好了**，
> admin 只需要看一眼、改掉不对的几行。它不承诺任何行是真的。

这条定位推出了三个具体设计：

1. **加 `checked_in_method` 字段** —— 让 admin 在 attendance 页上看得见哪些行是自助打的。
   这是这个洞唯一真实的缓解，也是唯一一个「出事时想看的那一列」。
2. **不做 token 一次性化**（原需求的可选项三）。理由见[下面专门一节](#三token-一次性化是一个-bug不是一个加固)。
3. **不追求更长的有效期换取更好的体验** —— 90 秒是在「转发窗口」和「扫到的码手里还剩多久」
   之间取的，不是拍脑袋。

### 考虑过并否决的：GPS / 蓝牙信标

要求手机上报定位来证明「人在现场」。否决理由两条，任一条都够：

- **室内不准**。教堂大厅、地下室食物银行，GPS 误差经常上百米，
  结果是**真来的人被拒**，而这比漏掉几个作弊的严重得多；
- **它要的是位置权限**。这个系统里已经存着未成年人的生日、地址、紧急联系人，
  再向志愿者要一次定位权限，换来的是一个上面刚说过挡不住的东西。

蓝牙信标准，但要买硬件、要 App（浏览器拿不到），而这个项目连 React 都没上。

## 一、机制：三段，以及为什么必须切成三段

```
① iPad（admin）        每 20 秒 fetch 一次 → {url, expires_at}
                       浏览器本地把 url 画成二维码

② 手机扫码             GET /events/checkin/<token>/
                       ├ 验签 + 验时效（90 秒）
                       ├ 写 session：{event, mode, verified_at}
                       └ 未登录 → 正常 login_required 跳转

③ 确认页               GET /events/checkin/confirm/
                       ├ 读 session 凭据（10 分钟内有效）
                       ├ 多个工种 → 让他选
                       └ POST → check_in() / check_out()
                                 └ redirect → My Signups + 一条 success
```

### 为什么 ② 和 ③ 一定要分开：两个理由，各自都是硬的

#### 理由一：GET 不能写

原需求写的是「打开 `/checkin?event_id=X&token=Y`，接收请求后记录 check-in 时间」——
那是一个 GET 写操作。微信 / iMessage / WhatsApp 的链接预览抓取器、浏览器预取、
企业网关的 URL 扫描，**都会替人打卡**。这不是理论风险，是把链接发进任何一个聊天窗口
就会发生的事。

#### 理由二：手机上多半没登录，而登录要打字

第一次用的志愿者：扫码 → 未登录 → 跳登录页 → 在手机键盘上敲密码 → 回来 token 过期
→ 报错 → 再去 iPad 前面重扫。**每一个新志愿者的第一次都会踩这个坑**，
而第一次的体验决定了这个功能会不会有人用。

分成两段之后，「**你人在现场**」和「**你是谁**」变成两件独立的事：

| | 谁来证明 | 有效期 | 慢了会怎样 |
|---|---|---|---|
| 你人在现场 | 签名 token | 90 秒 | 重扫一次，两秒钟的事 |
| 你是谁 | 正常登录 | session 凭据 10 分钟 | 慢慢打密码，不受 token 影响 |

⚠️ 所以**确认页的表单里不带 token**。POST 校验的是 session 里的凭据。
带 token 的写法会诱使人把 token 从表单里读出来重新验一次，
那就等于把 90 秒的窗口又套回到「打完密码之后」，白分了。

### 为什么二维码里不放 `event_id`

原需求是 `/checkin?event_id=X&token=Y`。event id 在 URL 里一份、在签名 payload 里
又一份 —— **两者不一致时听谁的？** 这是一整类 bug 的入口，而它是可以从结构上消掉的。

改成 `/events/checkin/<token>/`，event id **只存在于签名过的 payload 里**。
顺带 URL 更短 → 二维码更稀疏 → 在教堂大厅的灯光下、隔着两米更好扫。

## 二、Token：`salted_hmac` + 签发时刻写进 payload

```
payload   = f"{event_id}:{mode}:{issued_at_epoch}"
signature = salted_hmac("events.checkin", payload).hexdigest()[:20]
token     = urlsafe_b64encode(payload) + "." + signature
```

验证：`constant_time_compare` 比签名 → 再看 `now - issued_at <= 90`。

### 为什么不是「时间分桶」的 TOTP

原需求的写法是「当前时间戳每 30 秒一个周期」，然后**为了补救**再允许前后浮动 1~2 个周期。
分桶这个写法自己制造了它想补救的问题：

| 扫码的时刻落在桶里的位置 | 剩余有效期 |
|---|---|
| 桶头 | 30 秒（+ 容差） |
| 桶尾 | **0.1 秒**（+ 容差） |

也就是说**有效期是浮动的**，同一场活动里有人能用 89 秒，有人「刚扫完就过期」——
而后者恰恰是加容差想避免的现象。

把签发时刻写进 payload 之后，有效期是**平的**：每一个 token 都恰好活 90 秒，
从它被签发的那一刻算起。规则一句话说得完，也没有边界情况。

### 时钟误差（原需求注意事项 ①）：这一条基于一个误解

> 「服务器时间、Admin 手机时间和志愿者手机时间可能差几秒。」

**志愿者的手机时钟和 admin 平板的时钟从来不参与计算。** token 由同一个 Django 进程
签发、由同一个进程验证，进入公式的只有服务器自己的 `local_now()`，而服务器只有一台。

真正要容忍的是**扫码到提交之间的物理延迟** —— 掏手机、对焦、走两步、点一下。
那是 `max_age` 的问题，不是时钟同步的问题，而 90 秒对它绰绰有余。

⚠️ 所以**不需要 ±1 周期的算术**。那段代码如果写出来，它防的是一个不存在的问题，
而它引入的浮动有效期是一个真的问题。

### 为什么不用 `TimestampSigner`

Django 自带的 `TimestampSigner(...).unsign_object(max_age=90)` 语义上完全对得上，
而且是久经考验的实现。否决它的唯一理由是**它的时钟注不进去**：
`sign()` 内部直接调 `time.time()`，测「刚好 90 秒」「刚好 91 秒」这两个边界就得 mock。

而本项目所有跟时间有关的写路径都是注入时钟的（`check_in(participation, *, at=None)`、
`upcoming(now=None)`、`in_period(start, end)`），D16 的整个口径建立在这上面。
为一个新模块开一个 mock 的先例，代价比自己拼一个 payload 大。

⚠️ 这**不是**在自己发明密码学构造：HMAC 来自 `django.utils.crypto.salted_hmac`，
比较来自 `constant_time_compare`。自己写的只有「把三个字段拼成一个规范字符串」。

⚠️ `key_salt="events.checkin"` 不能省。`salted_hmac` 的 salt 是**命名空间** ——
直接拿 `SECRET_KEY` 裸签，意味着这个 token 和 session、密码重置链接、
`signing.dumps()` 共用同一个密钥域，任何一处的构造缺陷会横向传染。

### 签发的时间窗：`start - 2h` 到 `end + 4h`

窗外 token 端点直接拒签，页面画一句 `Check-in opens 2 hours before the event`。

⚠️ 这一条防的是**一个被忘在办公室屏幕上的标签页**。没有它，那个页面就是一台
长期有效的打卡机，而它看起来完全正常 —— 又是这个项目反复定罪的那个形状：
**不报错、也永远不对**。

常量写在 `events/tokens.py` 里，不进 settings：它不是部署差异，是一条业务规则。

### `status` 也要看

`draft` / `cancelled` 的活动一律拒签。draft 是还没发布的东西，cancelled 是已经不办了的
——给它们发打卡码没有任何意义，而它们能发就意味着**有一条路径能给一场取消掉的活动
造出出席记录**。

## 三、`token` 一次性化：是一个 bug，不是一个加固

原需求的可选项三：「Token 验证成功后，在 Redis/数据库中将其标记为已失效，
确保一个 Token 只能被使用一次。」

⚠️ **这个 token 是这 20 秒里所有人共用的。** 第一个人扫完就烧掉，
排在他后面的所有人**全部失败**，而失败的原因在界面上无法解释 ——
他们扫的是屏幕上同一个、看起来完全正常的码。

一百人的签到队伍，这个改动会让**九十九个人打不上卡**。

而「按 (token, contact) 烧」拦不住任何东西：转发给朋友，朋友是另一个 contact。

真正免费拿到的防重放是另一件事，而且它已经在数据模型里了：

> **一个 Participation 只能被 check-in 一次。** 第二次扫就是幂等的
> 「You checked in at 9:03」，不是错误。

⚠️ 附带的第二个理由：本项目的 cache 是 `DatabaseCache`（`config/settings/base.py`），
它的 `incr` 在竞争下可能少数。对限流这种软闸可以接受，
对「保证只用一次」这种要求**完全不能接受** —— 而这个方案没有 Redis，也不打算为此引入。

## 四、`checked_in_method`：一次迁移，一列，出事时想看的那一列

`Participation` 加一列：

```python
class CheckInMethod(models.TextChoices):
    ADMIN   = "admin",   "Recorded by an admin"
    SELF_QR = "self_qr", "Self check-in by QR"
```

⚠️ **`blank=True`，没有 default。** 空字符串表示「这条记录早于这个功能」，
和「admin 录的」是两件不同的事。给它一个 `default="admin"` 会把历史上所有行
**追认成**「admin 录的」—— 那是在替一件没人查证过的事打包票，
和 D27 缺勤率分母那一节是同一条规矩。

三个写入口（`check_in()` / `check_out()` / `record_hours()`）各自接一个
`method=` 参数，默认 `ADMIN`。⚠️ 三个都要接：`_mark_attended()` 的注释里已经写过
「一个规则三个入口一个守卫，等于两条绕路」，来源字段是同一个形状。

它买到三样东西：

| | |
|---|---|
| attendance 页多一个 `self check-in` 小标记 | admin 一眼看出哪些行不是他填的 |
| D27 报表能答「这个 ministry 多少考勤是自助记的」 | 自助率低 = 这个功能没推开，是运营信号不是技术信号 |
| 出事时能分辨 | 「这三个人的签到在同一分钟内，全是自助」是一句能查的话 |

⚠️ 它**不**买到「防住转发」。它只是让那件事**在页面上看得见**，
而看不见的问题没有人能处理。

## 五、一个人报了两个工种：让他选

`participation_unique_per_event_role` 允许一个 contact 在同一场活动里持有多行
（既搬运又接待）。自助路径必须回答「打给哪一行」。

只有一行时（95% 的情况）**直接打，一次点击不变**；多于一行才多一个选择页。

否决的两个方案，和它们各自在报表里的表现：

| 方案 | 出勤/缺勤率 | 总工时 | 问题 |
|---|---|---|---|
| 全部一起打 | ✅ 对 | ❌ **翻倍** | 一个人干 3 小时，报表里 6 小时。人均工时、工时排行全部虚高 |
| 全部签到，工时只写第一行 | ✅ 对 | ✅ 对 | 「Welcome desk：attended，0 小时」读起来像「她在接待台什么也没干」。报表里多出一批说谎的 0 |
| 让他选 ⭐ | ✅ 对 | ✅ 对 | 罕见路径多一次点击 |

⚠️ 第二个方案的毛病值得单独记：它产生的是**一个语法合法、语义为假的 0**。
04-roadmap.md 里已经有一节讲过「记了 0」和「没记过」是两件不同的事，
这里是同一个坑的另一面 —— 一个**代码写进去的**假 0，比模板显示错更难发现。

而「让他选」是唯一不编造数字的方案：他确实在两个工种上各花了一段时间，
由他自己说。

## 六、admin 端的平板页

### 模式：纯手动切，但进页面的默认值看时间

```
┌──────────────────────────────┐
│  [ CHECK IN ]   Check out    │  ← 大标签，当前模式高亮
│                              │
│        ████████              │
│        ██ QR ██              │
│        ████████              │
│                              │
│  Refreshes in 12s  ▓▓▓░░     │
└──────────────────────────────┘
```

模式写进 token 的 payload，服务端要求它和这一行的状态对得上，对不上给人话
（"You checked in at 9:03" / "Check in first"）。

**进页面时的默认值**由服务端算：`now` 在活动中点之前 → `in`，之后 → `out`。
之后**完全听 admin 的，永不自动跳**。

⚠️ 自动跳的后果是：活动进行到一半，**正在排队签到的那几个人突然全部变成签退**，
而屏幕上没有任何东西提示模式变了。默认值只在打开页面的那一刻算一次。

### 一码两用（服务端按状态推断）为什么否决

`checked_in_at` 为空 → 签到，否则 → 签退。admin 零操作，很诱人。

但页面加载慢的时候志愿者会连扫两下，第二下把自己签退了，而 `check_out()`
**会照时钟往库里写一个 `hours`**（0.01 小时）。之后：

- `mark_absent()` 从此拒绝这一行（有 hours）；
- `undo_attendance()` 能修，但它**会连带删掉 hours**；
- 这个 0.01 进了 D27 的已记录工时。

要靠「距上次操作 N 分钟内的重复扫一律幂等」来兜，而那条规则比「admin 切一下」难解释得多。

### 时间参数：90 / 20 / 10min

| 参数 | 值 | 它在换什么 |
|---|---|---|
| token 有效期 | 90 秒 | 转发窗口 |
| 二维码刷新 | 20 秒 | 扫到的码**手里还剩多久** |
| session 凭据 | 10 分钟 | 手机上打密码的时间 |

⚠️ 关键是**后两个的差**：刷新 20 秒意味着屏幕上那个码最多已经活了 20 秒，
所以**扫到它的人手里至少还有 70 秒**。这个数字才是志愿者体验到的东西，
而 90 秒本身不是。改其中任何一个都要重算这个差。

### `setInterval` 单独用，当天一定翻车

iPad 息屏或切到别的 App，浏览器会把定时器降频甚至冻结。醒过来屏幕上挂着一个
早就过期的码，**而它和有效的码长得一模一样**。志愿者扫、失败、再扫、再失败，
现场没有任何人知道为什么。

⚠️ 这是这个功能最可能在真实活动当天出的事故，而且它**不报错**。

四条对策，缺一不可：

1. 服务端返回 **`expires_at`（绝对时刻）**，前端按它算剩余秒数，
   而不是「我上次刷新是几秒前」；
2. 监听 `visibilitychange` / `focus`，回到前台**立刻重取**；
3. fetch 失败时**把二维码盖掉**，显示 `Reconnecting…`
   —— 绝不在屏幕上留一个看不出死活的码；
4. 倒计时进度条读的就是 `expires_at`，于是它天然反映真相，
   而不是另一个可能说谎的计时器。

⚠️ 第 3 条是这四条里唯一反直觉的：**盖掉二维码是正确的失败**。
留着它，失败会静默地转移到志愿者身上（他扫了、他失败了、他以为是自己手机的问题）。

### qrcode 库从 npm 来，不从 CDN

原需求要求 `<script src="cdn...">`。改掉，三条理由，任一条都够：

- **prod.py 明写了这个部署前面没有 CDN** —— whitenoise 直接喂 gunicorn，
  整个部署是一个 service。为一个页面引入一个外部 host 是在给它开一条新的失败路径；
- **现场是教堂大厅的 wifi**。CDN 慢一拍、DNS 抽风、被墙，iPad 上就是一片空白，
  而它是当天唯一的签到入口；
- **供应链**：这个脚本决定往二维码里画哪个 URL。被投毒 = 全场打卡指向别处，
  而页面看起来完全正常。

而项目**已经有** npm + esbuild 链路（C1.1），加一个依赖是 `npm i qrcode`
加一行 `import`，产物照样进 `ManifestStorage` 带 hash。bundle 大约 +10KB。

⚠️ 客户端渲染这一半**保留**（原需求是对的）：一场活动只有一台 iPad，
但省下的是服务端一个二维码库依赖，而不是流量 —— 4KB × 3 次/分钟从来不是稀缺资源。
真正的理由是**服务端不需要知道二维码长什么样**。

## 七、志愿者端：拒绝的四种情况，每一种都要有人话

| 情况 | 页面说什么 | ⚠️ |
|---|---|---|
| token 过期 | "That code has expired — scan the one on the screen again." | 最常见，措辞要指向屏幕 |
| 没报名这场活动 | "You are not signed up for this event." + 报名链接 | **绝不**顺手建 Participation |
| 未成年缺同意记录 | 一句话 + 去补资料的链接 | 不能是 500 |
| 已经打过了 | "You checked in at 9:03." | 幂等，不是错误 |

### 「没报名的人扫码」为什么不能自动报名

顺手建一行 Participation 会**绕开 `sign_up()` 的两道闸门**：未成年同意，
以及紧急联系人。结果是一个**没有任何人可联系的未成年被记成出席**，
而这正是 P3 整条规则存在的原因。

`_mark_attended()` 那道闸门会拦住 attended，但那时人已经在现场了，
拦住的是一条记录，不是一个风险。

### 未成年那条链路是自动生效的

`check_in()` → `_mark_attended()` 对没有 `consent_at` 的未成年会 raise
`ConsentRequired`。自助路径不需要重写这条规则 —— 它需要的是**把这个异常
渲染成手机上看得懂的一句话**。这是必须有测试的一条：没有测试的话，
它在生产上的表现是一个 500，而踩到它的人恰好是最不该被卡在门外的那一个。

## 八、并发：一百人同时扫

### 先给数量级：这不是一个规模问题

真实到场是几分钟内陆续扫，不是同一秒。就算最坏假设一百人全挤在 10 秒里：

| | 量 |
|---|---|
| 打卡请求 | GET + POST 各约 10 rps，合计约 20 rps |
| 每次 POST 干的活 | session 查一次 + participation 查一次 + UPDATE 一条 + history INSERT 一条 |
| token 端点 | **一场活动只有一台 iPad**，20 秒一次 = 0.05 rps，而且签发是纯 HMAC，**零 DB** |

这比这个站上已经在跑的 ministry 报表页（一堆聚合 + 五张横条图）轻得多。

> **所以不上队列、不上 Redis、不上 Celery。** 无状态 token 最大的好处正在这里：
> 签发不写库，于是「一百人同时扫」在 token 这一侧**根本不产生并发**。

⚠️ 这一段的价值不在于它的结论，而在于**它把数量级摆出来了**。
「一百人同时」听起来像一个架构问题，算完是 20 rps —— 而为 20 rps 引入一个消息队列，
代价是从此每次部署多一个会挂的东西。

### 真正要处理的四件事

**(a) 同一行的重复写** —— 双击、两台设备、网络重试。

`transaction.atomic()` + `select_for_update()` 锁住那一行，
**锁内重新读一次状态**，已经打过就返回幂等提示。

- 锁只在**同一个人的重复请求之间**产生竞争，那正是要串行化的东西；不同人之间零竞争，
  锁持续几微秒。
- ⚠️ 锁里面**不许有任何 I/O** —— 发通知、写外部日志、发邮件。
  一个开着事务去等网络的请求会把连接池拖垮，而这是本节 (b) 的那面墙。
- ⚠️ **不用** `Participation.objects.filter(...).update(...)` 这种无锁条件更新。
  它一条 SQL 就原子了，很诱人，但它**绕过 `full_clean()` 和 simple-history 的 signal
  —— 不会留 history 行**。而这个项目里 `Participation` 是唯一一张「人可以手改的权威表」，
  它的 history 是 `undo_attendance()` 敢删 hours 的**前提**。

**(b) 数据库连接数** —— 这才是一百人真可能撞到的墙。

Render 托管 Postgres 有连接上限。`gunicorn workers × threads`
（加上 `CONN_MAX_AGE` 常驻的话）必须留在上限之下。

⚠️ CPU 不会是瓶颈，连接数会。而它的失败样子是 `OperationalError: too many connections`
—— 一个跟签到毫无关系的报错，出现在活动现场。算式要进 C3 的部署核对清单。

**(c) 限流走 `DatabaseCache`** —— 它比看起来贵，而且必须限得很松。

`django-ratelimit` 已经在依赖里（注册页在用），但本项目的 cache 是 `DatabaseCache`，
每个被限流的请求多两次 DB 往返。20 rps 扛得住，但要知道它在那儿。

限的对象：token 端点（防一个 admin 开二十个标签页）、打卡 POST。

⚠️ **两处都按 `user` 计，不按 IP**（2026-08-07 实现时改的，原计划写的是按 IP）。
现场一百个人共用一个 wifi 出口，按 IP 的话要么松到没有意义，
要么**拦掉的正是真志愿者** —— 而这个功能一旦在活动当天拦人，
它就再也不会被用第二次。按登录账号计既是有意义的口径
（一个人一分钟不该点三十次），又完全绕开了共用出口这个问题。
`core/ratelimit.py` 上写过的教训是「限流量错了对象就是在测量别的东西」，
这里是同一条。

**(d) 现场网络才是真瓶颈**

教堂大厅的 wifi 会比数据库先跪。所以：

- 打卡页**极轻** —— 无图、无 HTMX、一个按钮；
- 失败必须给人话 + 「去找现场管理员」的兜底；
- **admin 的 attendance 页永远是兜底通道**，它已经在了，不需要新建任何东西。

### 验收方式

对 staging 打 200 个并发 POST，断言三件事：

1. 同一个人只产生**一次** `check_in`（这一条是 (a) 的执行形式）；
2. p95 延迟；
3. 零 500。

⚠️ 单元测试里测不了真并发（sqlite 上 `select_for_update` 近乎无操作），
所以这条走 staging 的脚本，而**测试里断言的是幂等**：连打两次，
`checked_in_at` 不变、history 只多一行。

## 代价 / 何时重新考虑

## 实现时改口的两处（2026-08-07 写完代码后补）

按本项目的规矩，改口要就地写说明，不能悄悄改。

**① 限流按 `user` 而不是按 IP** —— 见上面第八节 (c)。

**② POST 接受的行**从「只有 pending」放宽成「pending + done」。

原计划只允许提交「这个方向还能动的行」。写完之后它自己的测试红了，而那个红是对的：

> 第二次 POST 最常见的来源是**一个第一次成功时就已经开着的页面** ——
> 网络慢、手指急。而那时这一行已经从 pending 挪到 done 了。
> 只收 pending 的话，这个人得到的是一个 **404**，
> 而他的签到其实**已经成功了**。

404 在手机上读起来是「这个站坏了」，出现的时机恰好是签到刚刚生效的那一刻。
放宽之后 `apply_scan()` 照常返回 `changed=False`，页面说「你 9:03 已经签到了」。

⚠️ `needs_check_in` 那一组**没有**放进去。它们也是 no-op，但对它们诚实的回答是
「先签到」，不是「你已经签退过了」。

---

**已经付的代价，如实列出来：**

1. **它挡不住现场实时转发**，而且没有加密方案能挡。接受这一条是这个功能能存在的前提。
2. **自助签退会写一个权威的 `hours`**。志愿者手滑早签退，写进去一个偏小的数字，
   而 `mark_absent()` 从此拒绝那一行。admin 能在 attendance 页改，history 留痕，
   但**这个偏差是系统性的**（往低了偏），跟原来「admin 忘了点签退」的偏差方向相同。
   ⚠️ D27 已经接受过一次这个方向的偏差，这里是第二次 —— 报表上「已记录工时」
   那个注脚的重要性因此上升了一级。
3. **多一个 npm 依赖**（约 10KB）。
4. **一次迁移**（`checked_in_method`）。

**什么时候回来重新考虑：**

- 如果自助率长期低于三成 → 问题多半不在技术上（没人知道有这个功能 / 现场没人举着 iPad），
  先别加功能；
- 如果出现了真实的作弊争议 → 那时才谈信标或人脸，而不是现在预防性地上；
- 如果活动规模长到几百人同时到 → 才需要重看第八节的数量级，
  而那时先看的是连接数，不是 token。
