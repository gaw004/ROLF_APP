# D29 · Memories：照片墙自成一个 app，一个桶，一次每日抽签（2026-08-06 起）

结论：照片墙是**一个独立的 app（`gallery`）**，挂在 `/memories/`，
有**自己的对象存储桶**，页面上是**每天抽一次、当天不再变**的 60 张照片。
上传时原图**不保留** —— 转成两份衍生图之后丢掉。

⚠️ 这条决策是**补写的**（2026-08-09）。功能 2026-08-06 起就在跑，一路只记在
[`revisions.md`](../revisions.md) 和 [`design-system.md`](../design-system.md)
里，从来没有拿到编号。补它的直接原因就是本文件夹 README 末尾那三步的第 2 步 ——
而**漏掉的那一步恰恰是"回到那张表加一行"**，于是一个带着自己的桶、自己的 URL
区域和 107 条测试的 app，在决策索引里根本不存在。记在这里，因为这正是 D20
吃过的那种亏：**做过的事没进索引，等于下一轮没做过。**

## 一、为什么是一个 app，不是 `core` 里的一个模型

按 [D17](D17-app-layout.md) 的判据走，三条都指向独立：

| D17 的判据 | Memories 的答案 |
|---|---|
| 它有自己的名词吗 | 有。`GalleryPhoto`，和 `Event` / `Contact` 都不是一回事 |
| 谁依赖谁 | 它依赖 `org`（→ Ministry）和 `accounts`（→ uploaded_by），**没有任何东西依赖它** |
| 拿掉它，别的还站得住吗 | 站得住。删掉这个 app，其余功能一行都不用改 |

⚠️ 第三条是它排在 `INSTALLED_APPS` **最后**的原因，那份名单上就是这么注的。
一个谁都不依赖的 app 是最容易删的 app，而"以后能不能删掉"是这个项目反复在问的问题。

## 二、⭐ 唯一的不变量：这一页描述的是**今天**

`strips_for(day)` 用 `Random(f"strip|{day}")` 抽签 —— **种子是日期**，不是请求。

| 这一条免费带来的 | 为什么 |
|---|---|
| 页面不会在人眼皮底下重排 | 刷新一次、从灯箱退回来，看到的是同一批照片。按请求抽的话，页面会在你没动它的时候变样，而那读起来是 bug，不是"有变化" |
| 旧照片还有机会 | 本地午夜换一批，所以第 61 张不是永远不见天日 |
| 测试能断言 | 传一个固定的 `day` 进去，结果完全可复现 |

⚠️ **不许用 `hash()` 做种子。** Python 对字符串哈希每进程加盐，于是同一天、
同一个请求，两个 worker 会抽出两批不同的照片 —— 而这个 bug 在本机单进程下
**永远复现不出来**。`_seeded()` 存在的全部理由就是这一句。

⚠️ 60 是**页面**的上限，不是基金会能存多少的上限。没有这个上限，页面会一直
好用到某一天突然不好用，而那天是悄悄到的。

## 三、桶：为什么 Memories 不和活动图片共用一个

因为两者对"什么东西有权删掉它"的要求**正好相反**，而一个桶只能有一个答案。

| 别名 | 装什么 | 谁能删它 | 理由 |
|---|---|---|---|
| `default` | 活动图片 | `purge_event_images` 每天扫，将来加一条 lifecycle 规则也是合理的 | "活动结束就没了"是它的需求 |
| `memories` | 照片墙 | 🔴 **只有人手动删**，任何自动删除路径都不许够得到它 | 这些文件是全系统**唯一备份救不回来的东西**。pg_dump 只管列，而这些是桶里的对象 |
| `public` | 首页图/视频 | — | 匿名可读，另外两个都不是 |

⚠️ 所以「共用一个桶省事」这个选项**不存在**：给 `default` 挂的任何自动清理，
挂上去的那天就同时挂在了照片墙上。

### 2026-08-12 改口：R2 没有 object versioning

**这一节原来是靠 versioning 立论的**：`default` 必须关（开着的话
`purge_event_images` 的删除只是个标记，"活动结束就没了"会以看起来成功的方式失败）、
`memories` 必须开（"桶自己的版本历史就是安全网的全部"），
**一个桶不能同时开和关**，所以必须分。

去 R2 控制台上找那个开关的时候发现**它不存在** —— R2 有 bucket lock（保留策略）
和 object lifecycle 规则，**没有版本控制**。于是：

- `default` 那一条**天然成立**，不用做任何事（⚠️ 但换到 S3 / B2 就又是一个要守住的开关）；
- `memories` 那一条**做不到**。当天定的处置是**主动接受没有安全网**：
  照片误删一次就是永久没了。⚠️ **没有拿 bucket lock 顶替** ——
  保留策略会连**正当的撤下请求**（"请把我孩子那张删掉"）一起挡住，
  而 [C3.10](../03-roadmap.md#c310-一页隐私说明) 的隐私说明正要承诺"怎么要求删除"。
  挡在误删中间的只剩 `gallery/manage.html` 上那句二次确认，
  而它写的 "The file is deleted for good" 现在是字面意义上的真话；
- **分桶这个结论没变，理由换成了上面那张表**（自动删除够不够得到它）。

> **这一条值得记的不是结论，是它怎么活下来的**：整节论证的承重墙是一个
> **谁都没有去控制台上点开看过**的平台功能。判据下次直接用：
> **一条设计如果全靠某个平台功能撑着，那个功能要在拍板当天就亲眼看一次** ——
> 和本项目"备份要真的恢复一次才算数"是同一个形状。
> 代价记进 [`phase-c.md` 的已知缺口](../phase-c.md#五已知缺口与处置)。

## 四、原图不保留 —— 以及这句话的代价

上传的照片转成两份（灯箱用 1600px、带子用 700px）之后，**原文件丢掉**。

理由和活动图片同一条：手机拍的照片带 GPS，而**一张在志愿者家里拍的照片会把
他家住址发布出去**。EXIF 在 `normalise_gallery_image` 里剥掉。

⚠️ 代价如实写在这里，不藏着：**1600px 是任何人以后能再看到的最大尺寸**。
基金会必须自己留原件 —— 这个系统不是照片的归档处。

⚠️ 顺序有且只有一次机会：**年份要在剥 EXIF 之前读出来**。剥完了就只剩"今天"，
而对一张从鞋盒里翻出来扫描的老照片，"今天"是错的。

⚠️ 扫描件的局限也写下来：扫描仪写的是扫描那天，没有任何办法分辨。
1975 年的照片去年扫的，标出来就是去年。这是"读元数据"相对"让上传者手填"
（2026-08-06 选的前者）付出的代价。

## 五、两份衍生图，不是一份

| | 为什么不能省 |
|---|---|
| 只留大的 | 带子上是 60 张，手机上等于加载 60 张全尺寸图 |
| 只留小的 | 灯箱 —— **点开它的全部意义** —— 显示的是一张 700px 放大糊掉的图 |

⚠️ `GALLERY_THUMB_MAX_EDGE = 700` **同时是版面的分母**，不只是一个存储尺寸：
照片按 `带高 × (自己的存储高 ÷ 700)` 画。改它会改变页面上每张照片的大小。

⚠️ `thumb_width` / `thumb_height` 是**列**，不是 `thumb.width`。读属性会**打开文件**，
在对象存储上就是一次网络往返 —— 每页 60 次的差别是"页面能开"和"页面超时"。
列同时让模板在图到达之前就把位置留好，于是带子不会随着加载往下抖。

## 六、去重只到"同一份字节"为止

`image_digest` 是**重编码之后**那份大图的 SHA-256，全墙唯一（不分 ministry）。

⚠️ 取重编码之后的，才有用：同一张照片发两次、一次 JPEG 一次 PNG，或者过一趟
聊天软件再传回来，进来时字节不同，出 `normalise_gallery_image` 之后完全一致。

⚠️ **它只挡得住字节一致的图，别的一概挡不住** —— 重新裁一次、换个质量存一次、
对着屏幕截个图，都是不同的文件，都进得来。说明白，是因为"去重"这个词听起来
比它实际做到的多。

## 六之二、一批里坏掉一张，只丢那一张（2026-08-13）

一次提交里有四种"这张传不了"：**过大**、**读不了**、**已经在墙上**、
**超出一次十张**。四种一律**踢掉那一张、其余照传**，事后在消息里点名说明原因；
只有"一张都没活下来"才是错误，留在表单上。

⚠️ 在此之前只有"已经在墙上"是这么做的，另外三种整批拒掉。而 POST 被拒会清空
文件框 —— 十张里有一张 12MB，代价是另外九张要重新挑一遍。

⚠️ **"超出十张"改成取前十张，是推翻了 2026-08-07 的决定。** 当时的理由是
"静默丢弃比整批拒绝更糟：没人知道十一张变成了哪十张"。承重的词是**静默**；
现在会点名，理由就不成立了。

🔴 **踢掉不等于"解开了再扔"**：尺寸检查必须留在 `normalise_gallery_image`
**前面**，超出十张的那些在循环**之前**就切掉。解码才是吃内存的地方
（6000×4000 是 72MB 像素、源文件 3MB），而那正是 2026-08-13 打挂生产的东西。
守卫用 spy 断言那个函数没被调用，不是断言行数 —— 后者两种写法都会绿。

⚠️ 原因翻成人话只有一处（`gallery/forms.py::describe_skipped`），成功消息和错误
共用它。MB 的数字一律从 `settings.EVENT_IMAGE_MAX_UPLOAD_BYTES` 推出来，
帮助文字也是（所以它在 `__init__` 里赋值，不在字段声明里 —— 后者会在导入时
把设置冻住）。

## 六之三、批量删除：确认页，不是确认框（2026-08-14）

一次勾若干张、一次删掉。形状是每张卡一个复选框 + 顶部一条「Remove selected」。

⚠️ **确认走一整页服务端页面（`gallery/remove_selected.html`），不走 `confirm()`。**
判据是这个 app 从头到尾那一条：**这些文件没有任何备份能捞回来**（见上面三、四节）。
一个装着数字的确认框答不了「我到底勾中了哪几张」，而批量把一次手滑的代价从一张
放大到六十张。确认页把真正要删的那几张的**缩略图**列出来 —— 认脸是它唯一的功能。

⚠️ 顺带的、也是要紧的：确认页**不依赖 JS**。于是批量这条路的防线比单张那条**硬**
（单张仍然是 `confirm()`，关掉 JS 就没有了）。这个不对称是有意的。

⚠️ **确认页不携带任何权限。**它只装 id，回来之后 `resolve_removal()` 从头重判一遍
（照样问 `can_delete_gallery_photo`）。所以这一页放多久、被谁转发，都不改变谁能删掉
什么 —— 这是敢把 id 放进 hidden input 的全部理由。

⚠️ **上限 60（= `STRIP_SIZE`），而它是在勾选那一刻就挡住的** ——
勾满 60 张之后，剩下没勾的复选框全部灰掉，旁边写出为什么（已勾的照旧能取消，
否则连反悔都做不到）。「全选」也吃这个上限，勾中的是前 60 张。
⚠️ 那个数字**由服务端交给模板**（`views.manage` 的 `removal_cap`），模板里不写死 ——
写死一份的话，改上限的人只会改到其中一处，而不一致的那一半是浏览器这半：
页面让你勾一百张，服务端把整批退回来。

⚠️ 服务端那条「超了整批拒绝」**留着，但降级成兜底**：灰掉是 Alpine 干的，
而没有 JS 的那条路照样能提交任意多个。有浏览器在跑的时候没人到得了它。

⚠️ 整批拒绝而不是取前 60 张 —— 和上传那条路正好相反，
而这正是[六之二](#六之二一批里坏掉一张只丢那一张2026-08-13)那条判据的第二次应用：
上传悄悄留下十二张里的十张，补发另外两张就完事；删除悄悄干掉两百张里的六十张，
已经做了一件撤不回、事后也说不出是哪六十张的事。承重的词还是「悄悄」，
但这一次点名解决不了问题，因为**点名之后照片也回不来**。

⚠️ 无权删的、已经不在的：**跳过并计数，但不报名字**。报名字等于把这张表单变成
「照片 412 存在吗、是谁的」的查询接口，而墙本身不回答这个。

## 七、被删掉的那一半（2026-08-07）

抽签那半边原来做得多得多：两条带子反向漂移、每张照片按实测分布随机取高、
还有一趟把部分照片裁成别的形状好让带子不单调的重组。**全部删掉了，不是关掉。**

⚠️ 判据写在 `services.py` 顶上：**没有东西在跑的规则，比没有规则更糟**。
留着开关和常数，就留下了一份"看起来还在管事"的死代码。

⚠️ 同期定死一条：**不放大、不裁剪**。等高版本必须把小于带高的照片放大，
而那正是「有些照片为了做成等高的照片都糊了」。现在每张照片按同一个比例画
自己的尺寸，于是照片之间的差别就是照片本身的差别。

## 八、权限：`@login_required` 是小的那一半

上传和删除都先过 `org.permissions`（`can_upload_gallery_photo` /
`can_delete_gallery_photo`），ministry admin 只能动自己 ministry 的，
foundation tier 才能传全基金会的（`ministry` 留空那一档）。

⚠️ 判断**不在 `gallery` 里重写一遍**。D20 的那条教训：权限抄第二份，
抄出来的那份迟早和真的那份不一致，而不一致的表现是「菜单里有个链接，点进去 403」
或者更糟的反面。

⚠️ `Ministry` 用 `PROTECT`（同 `Event.ministry`），`uploaded_by` 用 `SET_NULL`：
删掉一个离职员工的登录账号**不该顺手删掉基金会的照片**。
