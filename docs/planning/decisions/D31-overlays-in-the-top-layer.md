# D31 · 覆盖层一律走原生 `<dialog>` + `showModal()`（2026-08-09）

结论：这个站上**任何盖在页面之上的东西**（弹窗、悬浮窗、以后的确认框、抽屉）
都必须是 `<dialog>`，并且**只能用 `showModal()` 打开**，于是它进 **top layer**。

不许再用 `position: fixed; inset: 0` 的 div 手搓覆盖层。

## ⭐ 唯一的不变量：覆盖层的包含块必须是视口，而这件事只有 top layer 保证得了

> `position: fixed` **不等于**「相对视口」。祖先只要有
> `transform` / `filter` / `contain` / `backdrop-filter` 中的任何一个，
> 它就成为后代的包含块，`inset: 0` 铺满的是**那个祖先**。

⚠️ `z-index` 在这里完全无关 —— 换多大的值都没用。这不是层叠顺序问题，
是包含块被换掉了。第一反应去调 z-index 会浪费掉整个排查时间。

而本项目**到处都是 `backdrop-filter`**（深色模式的玻璃材质，D26），
所以这不是一条理论上的风险，是一条必然会踩的路。

## 它已经咬了两次，而两次的发现方式完全不同

| 覆盖层 | 被谁抓住 | 症状 |
|---|---|---|
| 改密码弹窗 | `.dark.has-hero .card` | 深色下被关进 Login Information 卡片里，表单下半截被裁掉。浅色正常 |
| Memories 悬浮窗 | `.dark.has-hero .wall` | 一个症状都**没有** |

**第一个是用户报的**，而且报的是「有时候」—— 因为它只在深色模式犯，
而玻璃那条规则是 `.dark.has-hero` 才命中的。

🔴 **第二个才是这条决策存在的理由。** 它同样被抓住了，却**一直看起来是对的**：
`.wall` 恰好是 `height: 100dvh` 且满宽，两个盒子正好重合。
把 `.wall` 临时改成 600×400，悬浮窗当场跟着变成 600×400 —— 它从写下来那天起
就是错的，只是巧合替它遮了三天。而 `.wall` 还带着 `overflow: hidden`，
给它加个页头或一点 padding，悬浮窗就会**悄悄**缩水或被裁。

## 为什么不是「以后注意别把弹窗放进卡片里」

因为第二个例子已经证明这条纪律靠不住，而且理由是结构性的：

- **调用方那一行一个字都没写错。** `profile.html` 里只是
  `{% include "core/components/modal.html" %}`；
- 错在**它外面第几层有什么**，而那是另一个文件、另一个人写的 CSS；
- 而且**只在一个主题下成立** —— 写的人在浅色下验，永远撞不到。

⚠️ 一个「组件放错地方就坏，且坏得没有提示」的组件，等于把陷阱留着并附一张纸条。
组件该给的保证是「放哪都对」，而 top layer 是平台唯一能兑现这句话的地方。

## 顺带交回浏览器的五件事

改完之后**代码更少**，而且多了两条以前没有的无障碍行为：

| | 原来 | 现在 |
|---|---|---|
| Esc 关闭 | 手写 `x-on:keydown.escape.window` | 原生 |
| 焦点送进窗口 | 手写 `x-effect` + `$nextTick` | 原生（`autofocus`） |
| Tab 关在窗口里 | 手写 `trap()`，**只有悬浮窗写了** | 原生 |
| 关掉后焦点复位 | 以前**根本没做** | 原生 |
| 背景不可点 | 以前**根本没做** | 原生（inert） |

## ⚠️ 最尖的那个坑：`<dialog open>`

`open` 属性把元素显示出来，但**留在原地、不进 top layer** ——
也就是原封不动把上面的 bug 请回来。

而它**看起来是对的**：元素确实显示了，review 的人看见 `<dialog>` 就过了。
所以这一条是守卫盯着的重点，而不是写在文档里就算了。

## 渐进增强（D24）不受影响，而且更好了

`<dialog>` 不带 `open` 时 UA 样式就是 `display: none`，所以没 JS 时它自动不显示，
按钮退回成一条真链接跳到那一页（`button.html` 的 `opens` 参数）。
⚠️ 连 `x-cloak` 都不需要了 —— 防闪是浏览器给的。

## 守卫（`core.tests.OverlaysLiveInTheTopLayerGuardTests`）

五条，且**逐条做过反向验证**（故意改坏，确认它真的会红）：

1. 两个覆盖层是 `<dialog>` 且走 `x-dialog`；
2. 任何模板里的 `<dialog>` 都不许带 `open` 属性；
3. `app.js` 只许 `showModal()`，不许 `show()` / `setAttribute("open")` /
   给元素赋 `.open`；
4. 模板里不许再出现新的非 `<dialog>` 满屏覆盖层；
5. 不许给 `html` / `body` 加那四个属性中的任何一个。

⚠️ 第 5 条是**侧滑菜单那个例外的安全条件**。菜单仍然是 `fixed` 的 div，
因为它是 `<body>` 的直接子元素（祖先只有 body 和 html），而且它带着入场动画，
为一个今天不存在的 bug 去动那段动画不划算。
**但例外的安全条件必须自己上守卫** —— 哪天有人给 body 加个 `filter`
（整页压暗、抖动提示、缩放），菜单就会悄悄开始相对它定位，而第 5 条是唯一站在那里的东西。
⚠️ 如果将来出现第三个想要这个豁免的覆盖层：**别豁免，去把菜单也改成 `<dialog>`。**

⚠️ 写这几条守卫时它们自己先误报了两次，值得记：模板里
`x-dialog="open"`、JS 里 `this.open = true` —— 悬浮窗的 Alpine 状态**就叫 `open`**，
于是「找 `open` 属性」和「找给 `.open` 赋值」都命中了完全正确的代码。
**一个分不清属性名和属性值的守卫，会把对的代码报成坏的**，而那种守卫最后一定会被人注释掉。
