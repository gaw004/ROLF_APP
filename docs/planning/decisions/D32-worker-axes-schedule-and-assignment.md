# D32 · 编制拆轴（`kind` / `compensation`）、班表与请假，以及活动的指派路径（2026-08-14）

结论：`Position.kind` 从「员工 / 志愿者 / 理事」三档**收窄成 `staff | board`**，
把「拿不拿钱」拆成一个独立字段 `compensation`（`paid` / `unpaid` / `stipend`）。
新增 `WorkPattern` + `Shift` 两张表表达工作时间，`Leave` 表达请假，
`Participation` 加两档状态让 admin 能把在编人员**指派**进活动。

起因是一个提不出口的需求：**「有一类 ministry 的成员全是志愿者，但他们像员工一样 ——
有固定开会时间、每个人有固定岗位。我想把他们当成 employees，但写成 unpaid。」**

那句话本身就是诊断：需要同时说出「他属于员工那一类」和「他不拿钱」，
而当时只有一个字段可以说。

## ⭐ 唯一的不变量：一个人在基金会里只有一条在编路径

**`Position` + `Assignment`。** 拿不拿钱、排不排班、是不是理事，
全都是挂在这条路径上的字段，**不是另一条路径**。

这一条排除掉的是本轮最容易走的那条歪路：给「像员工的志愿者」建第二套结构。
一旦建了，下面这些立刻分裂成两份，而且每一份都会各自漂移：

| 分裂的东西 | 后果 |
|---|---|
| 组织架构图 | 一半的人不在图上，而图看起来是完整的 |
| R6 / R7 的工时口径 | 两套算法，D27 那张报表要么漏人要么重算 |
| `.active()` / `.serving()` 的时间口径 | 第二份实现，迟早和第一份走散 |
| 权限判断 | `org/permissions.py` 之外的第二处判断 |

⚠️ 这不是靠测试盯着的，是**结构上**排除：没有第二张表，就没有第二套口径。
同 [D27](D27-ministry-report.md) 那条「报表收筛过的 queryset 而不是 ministry id」。

## 一、诊断：一个字段扛了三个轴

真正独立的是三个轴，而当时它们全挤在 `kind` 里：

| 轴 | 问的问题 | 改之前存在哪 |
|---|---|---|
| 编制轴 | 他在组织架构里有没有一个格子（有上级、有职责、有固定承诺）？ | ✅ **本来就对** —— 有没有 `Position` 行就是答案。外部志愿者没有编制，只有 `Participation` |
| 报酬轴 | 拿不拿钱？ | 挤在 `kind` 里（`employee`=拿钱，`volunteer`=不拿钱，`board`=不拿钱） |
| 时间组织轴 | 他的时间怎么安排 —— 排班，还是自己按场报名？ | 改之前**完全不存在** |

**「unpaid employee」不是一个新类型**，它是「有编制（已有）+ 不拿钱（轴二）+ 有班表（轴三）」。

而它当时塞不进去的真正原因是**轴三根本没建** —— 系统里唯一的"安排时间"机制是活动自助报名。
这一条有一个很硬的旁证：**带薪员工当时也一样无处安放**，他们同样没有班表、
同样只能自己去活动页报名。所以这不是志愿者的特殊情况，
是一个**对所有在编人员都缺失的层**。

## 二、`compensation` 挂 `Position` 不挂 `Assignment`

这一条没有第二个选项，而理由不是这次想出来的，是 [D11](D11-position-and-assignment.md) 自己写的：

> 空缺编制必须说得出自己是有薪岗还是志愿岗（招人的时候正是要知道这些）。

挂在 `Assignment` 上，空缺编制就答不出这个问题 —— 而"能完整描述一个空缺"
正是 D11 第二次修订的全部目的。判据口诀同样在 [D10](D10-person-role-position-assignment.md)：
**换个人来做这条信息还成立的，属于编制**。一个岗位有没有预算，换谁来干都成立。

### 考虑过并否决的：给 `kind` 加第四档 `unpaid_staff`

迁移最小（改一行 `choices`），但它是**把两个轴继续塞在一个字段里**。
D10 和 D11 各为这个病付过一次学费，D11 第二次修订留下的那句话正好是判据：

> 拆层拆到一半比不拆更危险 —— 因为它看上去已经解决了问题。

而且第五档（带津贴的实习生？带薪的志愿者协调员？）来的时候还要再来一次。

### 考虑过并否决的：`kind` 改成字典表

看起来符合 [D5](D05-lookup-tables-not-enums.md)「会变的东西做成数据」，
但 D5 自己的判定规则说**有代码 branch 就该用 `TextChoices`** ——
而 `kind` 被 R8 的查询（`events/services.py` 的 `ministry_staff_participation()`）
和报表分组直接 branch。这是反方向。

### `stipend` 这一档要注意的

领津贴的人在 FLSA 眼里**通常就是员工**，不是志愿者。
所以报表上 `stipend` 跟 `paid` 归堆算工时，不跟 `unpaid` 归堆。
建模上没有额外成本，是使用上的一条提醒。

## 三、R8 的语义变了（这一条会静默改变报表）

需求原文是「开设这个 event 的 ministry 下面的 **employee** 谁参与了、分别负责什么」。
拆轴之后 `employee` 这个词在库里不再有对应的值，必须重新定：

**R8 = 所有在编的人，不看拿不拿钱。** 查询从

```python
position__kind=Position.Kind.EMPLOYEE
```

改成

```python
position__kind=Position.Kind.STAFF          # paid / unpaid / stipend 全算
```

理由：基金会问这个问题的动机是**「我们自己人 vs 外面来的志愿者」**，
不是「拿钱的 vs 不拿钱的」。按字面只算带薪的，那批无薪核心成员
即使实际负责了整场活动也不会出现在 R8 里。

⚠️ 这是一次**语义变更，不是重构**：同一场活动、同一份数据，改之前和改之后
R8 会返回不同的名单，而且两次都不报错。所以它在 roadmap 里是单独一步，
配一条固定住新口径的测试。

## 四、班表：为什么是稠密的 `Shift`

### 两种实现，差别在"没有偏离的班次要不要落行"

| | 稀疏（模板 + 例外） | 稠密（每个班一行） |
|---|---|---|
| 行数 | 5–20 行 / 人 / 年 | ~250 行 / 人 / 年 |
| 读「3/19 谁在班」 | 模板 ⊖ 请假 ⊖ 例外 ⊕ 额外，合成 | 一个 `filter` |
| 班次不规则的人 | **装不下** —— 没有模板可以"偏离"，每天都是例外 | 天然装得下 |

**选稠密**，决定性的是最后一行：**稀疏方案预设了"存在一个模板"**。
基金会不见得每个在编人员都有固定班次，而对一个没有固定班次的人，
稀疏方案退化成稠密，还多背了一套合成逻辑。

另一条：**稠密 → 稀疏是投影，稀疏 → 稠密要靠模板。**
政府要的那份例外记录表，随时能从稠密行里导出来；反过来不行。
所以稠密是严格更通用的表示。

### 但它是两张表，不是一张

没有模板层的 `Shift` 没法录入 —— 谁也不会手工敲 250 行。
Deputy、When I Work、Planning Center Services 全都是**周模式 → 生成 → 具体班次**：

```
WorkPattern   周模式（assignment + weekday + 起止时刻 + 生效起止日期）
     ↓ 生成
Shift         具体某天（assignment + date + 起止时刻 + status + 实际起止 + source）
```

### ⚠️ 重新生成只许动未来，且只许动没被人碰过的行

改了模板之后，已经生成的行怎么办 —— 这是整个设计里唯一会**静默出错**的地方。

**过去的 `Shift` 行一个字节都不许动。** 它们就是那份工时记录，
重新生成它等于**静默改写考勤史**：不报错、测试全绿，
而政府要的那份记录已经和当时发生的事对不上了。
这正是 D11 第二次修订判死刑时用的同一条标准（主表不许存出自相矛盾的行）。

由此产生一个必需字段：`Shift.source`（`generated` / `manual` / `edited`）。
没有它就分不清哪一行能被生成器覆盖。生成器的规则是一句话：

> 只覆盖 `date > today` 且 `source == generated` 的行。

### 生成到哪天为止

滚动窗口：模板保存时向前生成 26 周，一个 cron 每周往前推一格。

⚠️ 不在读取时按需生成 —— 那是**在 GET 里写库**，
[D28](D28-qr-checkin.md) 已经为这件事拆过一次两段式设计，不再走回去。

好消息是形状是现成的：`render.yaml` 里已经跑着两个 cron，
`events/management/commands/purge_event_images.py` 就是模板。加第三个不是新东西。

### 例会记出勤 —— 推翻同日早些时候的「不记」

当天先定的是**例会不记出勤**，理由是"做成 `Event` 太贵"（要给 `Event` 加内部可见性档，
一年 50 场例会会淹没活动列表）。**那个成本是按错误的实现估的。**

选了稠密之后，例会已经每周真的落出一行 `Shift`。所以"记出勤"不是新建任何东西，
是把**已经存在的那些行翻一下状态**：

```
本周二例会 · Food Pantry · 排班 8 人
    [ 全部到齐 ]      或者勾掉缺席的那几个
```

一周一次、一屏、一次点击。所以结论改成**记**，做法是批量翻状态，不做成 `Event`。

三条要记住的：

1. ⚠️ **接受 ≠ 出席。** 承诺是对未来的，工时是对过去的观测。
   一个人接受了每周二的例会然后连着三周没来，自动转工时会给他记满，而且不报错。
   Planning Center 的分工正好印证：Services 管排班和接受 / 拒绝，
   **Check-Ins 是另一个产品**管到没到；
2. ⚠️ **不要用 invite / accept 流程包例会。** 一年 50 场，让人每次点"接受"，
   两周之内就没人点了。**指派进标准岗位（`Assignment`）本身就是那个承诺** ——
   接受 / 拒绝是给一次性活动用的（第六节），不是给常规排班用的；
3. ⚠️ **没人翻的行会永远停在 `scheduled`。** 那时它既不是实到也不是缺席，
   是"没人看过"，必须单独显示成「未确认」，不能算实到也不能算 0。见第八节。

#### 这两条分别是什么：一条是边界，一条是代价 + 解

**它们不是同一种东西**，混着写会让人以为两条都得忍着。

**第 2 条是边界，不是代价。** 唯一失去的是"例会没有事前 RSVP" ——
周二翻状态的时候才知道谁来了，而不是周一就知道。
对每周例会这不重要（那些人是被岗位约定住的，不是每周重新招募的）。
**逃生口**：季度务虚会、年度培训这种真的需要事前人数的，
**那一场单独做成一个 `Event`**，走第六节的指派 + 接受 / 拒绝。
不改任何结构 —— 边界画在"这一场需不需要事前知道人数"上。

第 3 条是**代价 + 解，两半要分开看**。

| | |
|---|---|
| 代价（消不掉） | 一定会有一批小时处于「没人看过」的状态 |
| 解（本决策已含） | 把它做成第三个数，**永远不能伪装成实到，也永远不能伪装成 0** |

⚠️ 代价那一半消不掉，而且理由是结构性的：**唯一能消掉它的办法是要求每个班次都有一次观测 ——
那就是打卡**，而第七节明确选了不打卡。例外记录法的定义就是"默认按班表算、只在偏离时记一笔"，
所以「没人记」和「没有偏离」在数据上本来就是同一个状态。
这是为"不打卡"付的钱，不是实现没做好。

解那一半做的事，是把它从**不报错的错**变成**诚实的缺口**：
算进实到就虚高、算成 0 就虚低，两种都不报错；单独显示则页面上写的是
「我们不知道这 8 小时」—— 那是真话。

三条让它变小的，一起做：

1. **默认全到齐**：那一屏默认全勾，只需要**取消勾**缺席的人。摩擦降到接近零 ——
   同 [D27](D27-ministry-report.md) 那条「让 admin 点四十次签到不会被真的执行」，方向反过来用；
2. **上周没确认就提示**：ministry admin 页面上显示「上周有 8 小时未确认」，
   同 D27 里那个未成年无同意记录的红色指标 —— 把风险画出来，别等它累积；
3. 🔴 **绝对不要做「超过两周自动确认」。** 有人一定会提，它听起来很贴心，
   而它**把假定值伪装成观测值** —— 比现在更糟，因为现在页面上至少写着"未确认"，
   自动确认之后它变成一个看起来有人核实过的数字。

### 和推迟清单里那条「不建 `Shift` 表」的关系

[`../deferred.md`](../deferred.md) 里 2026-07-28 否决过一个叫 `Shift` 的东西 ——
**那是活动内部的班次**（Salesforce V4S 的 Job → Shift → Hours 那一层），
结论是「多班次一律拆成多个 `Event`」。

**本条建的是岗位的排班，两件事同名而已。** 那条否决不撤销。
写在这里免得以后被当成自相矛盾。

## 五、请假独立成表

专业系统在这件事上是收敛的：**没有一个用 N 行班次表达请假。**

| 系统 | 做法 |
|---|---|
| Workday | Absence / Time Off 是独立域，和排班分开 |
| BambooHR | Time Off Request + 政策 + 余额 |
| ERPNext | `Leave Application` + `Leave Type` + `Leave Allocation`，**由请假去标记考勤记录** |
| Deputy / When I Work | 请假申请**阻止**排班 |

四条理由：

1. 一次请假是一个**可审批的单元** —— 有起止、理由、状态。摊成 10 行班次之后，"这一件事"就不存在了；
2. 假期**跨非工作日** —— 两周假包含周末，而周末在班次表里没有行；
3. **余额 / 累计**需要一个独立实体挂；
4. 请假对**人**成立，而有些人根本没有班次（exempt 的牧职人员、只来开会的无薪成员）。

⚠️ 选了稠密之后这条更硬：**两周假手工去翻 10 行班次的状态，没有人会真的执行。**
同 [D27](D27-ministry-report.md) 里「让 admin 点四十次签到不会被真的执行」，
后果也一样 —— 数据看起来在，但跟着"哪个 admin 比较负责"走。

落地边界（对齐 ERPNext 那条「请假是权威、班次状态派生」）：

```
现在做：  Leave(assignment, start_date, end_date, reason)
          + end_date >= start_date 约束 + simple-history
          保存时把区间内的 Shift 翻成 on_leave

推迟：    假期类型字典表、余额 / 累计、审批工作流
```

**代价，如实记一笔**：`Leave` 挂 `assignment` 而不是 `contact`
（沿用推迟清单里已定的形状），所以**一个人两个岗位休同一次假 = 两行**。
小基金会里罕见，但记下来免得以后当 bug 讨论。

## 六、活动的指派路径（R8 现在是半瘫的）

`events/services.py` 的 `sign_up()` 注释里写着「an admin entering somebody from a
paper list reaches this function too」—— **服务层早就为替人录入写好了，
但没有任何 URL 能走到它**。`events/views.py:event_signup` 只能给自己报名。

于是在编人员要出现在 R8 的名单里，只能自己去公开活动页报名。
这是本项目诊断过两次的同一种病（「没有 URL 的功能，测试也没有 URL 可打」）。

补两条写入路径，**都落在 `Participation` 上，不新建表**：

| 路径 | 落地状态 | 什么时候用 |
|---|---|---|
| 指派 | `INVITED` | admin 把本 ministry 的在编人员放进某个 `EventRole`，对方要答复 |
| 代录 | `REGISTERED` | 纸质名单 / 当面已经答应了，admin 直接录入 |

```
Participation.Status  加两档：INVITED（已邀请未答复）· DECLINED（拒绝）
Participation.source  新字段：self_signup | assigned
```

**为什么是加两档而不是加一张表**：`invited → registered → attended` 是同一条生命线上的位置，
和 `registered / attended / absent / cancelled` 同维。
对照推迟清单里被否决的 `needs_reconfirmation` —— 那个是「这个人和**某一次改动**的关系」，
确实是另一个维度，所以那条要用表。这条不是。

### ⚠️ 统计口径：不定就会自己变，而且不报错

R5（每个工种多少 volunteer）、满员率、缺勤率分母现在都在数 `Participation` 行。
加两档之后如果不定口径，这些数字会自己变。

**口径**：`INVITED` 和 `DECLINED` **不算报名**。满员率、R5、缺勤率分母
只数 `REGISTERED` + `ATTENDED`。

**报表上分开列两个数**：「已确认 N 人」和「待答复 M 人」并排。
藏起来的话，「没人答应」和「还没问」在页面上长得一模一样 ——
同 D27 里「未成年无同意记录为 0 也要画出来」的规矩。

### 被邀请没答复的人当天来了

**直接签到，状态盖成 `attended`。** 沿用 D27 里 `check_in()` 把 `absent`
盖回 `attended` 的先例：**要求先走完流程，结果是没人走流程。**

## 七、打卡：不做，而这不是偷懒

三条事实（查证过，且它们改变正确答案）：

1. 要不要记工时**取决于 exempt / non-exempt，不取决于机构偏好**。
   非豁免员工，FLSA 要求准确记录工时；豁免员工不要求；
2. **「记录工时」≠「打卡」。** 明确允许**例外记录法**：
   记下标准班表，只在偏离时才记一笔；
3. **履行牧职的人（ministerial exception）不需要记工时**，也不受最低工资和加班约束。

一行 `Shift`（带 `status` + 实际起止）**本身就是那份例外记录表**。
所以不另做打卡 —— 不是省掉了一个功能，是这个功能已经被班表做掉了。

由此新增 `Position.flsa_status`（`exempt` / `non_exempt` / `not_applicable`）：
它让系统知道**谁的工时是法律上必须记的**，而不是全靠人记得。

### 顺带能查出来的一件事

🔴 **带薪员工不能以"志愿者"身份做他被雇来做的同一类工作** ——
那些小时数在 FLSA 眼里就是工作时间，要付钱。

这件事本系统**查得出来**：同一个 `Contact` 在某 ministry 有 `compensation=paid`
的在职 `Assignment`，同时又在该 ministry 的 `EventRole` 上有 `Participation`。
做成一条提示，不做成拦截 —— 判断"是不是同一类工作"需要人。

### 措辞

**界面上不要管无薪的人叫 employee。** 写 `Staff (unpaid)` / `Team member`。
数据库里的值无所谓，页面文案和 `choices` 的 label 要注意 ——
真出争议时，机构自己 HR 记录里的措辞是对方的证据。

## 八、工时：两个账本，一条口径

### 两个账本，而且它们会重叠

| 账本 | 装谁的时间 | 谁在读它 |
|---|---|---|
| `Participation.hours` | 参加**活动**的人 | R6 / R7 / [D27](D27-ministry-report.md) 的「已记录工时」 |
| `Shift`（本轮新建） | 有**班表**的在编人员 | 本轮新增的「在编人员投入」那一块 |

⚠️ **两个账本不能相加。** 一个带薪员工在他排班的时段里去办了一场活动 ——
`Shift` 有一行（排班），`Participation` 也有一行（活动工时）。
相加就是重复计算，而它不报错、看起来还很像一个更完整的数字。

所以「实际投入」的口径**只有一份，写在 `services.py` 里**，
模板里不许现算 —— 同 [D18 的落点规矩](D18-admin-boundary.md)，本轮加一条守卫盯着。

### R6 / R7 只数无薪的（第三次静默语义变更）

需求原文是「volunteers 一共做了多少工时，分别在各个工种做了多少工时」——
**问的是志愿者的工时**。而第六节那条指派路径一落地，
ministry admin 就能把带薪员工放进活动，他们的工时会直接混进这两个数。

⚠️ 这是本轮**自己制造出来的**问题：指派路径存在之前，
带薪员工进活动只能自己去公开页面报名，几乎不会发生。

排除规则，三条：

- 排除在**办这场活动的那个 ministry** 里持有 `paid` / `stipend` 编制的人
  （活动当天口径，同 R8）；
- **跨 ministry 不排除** —— 财务部的带薪员工去食物银行的发放日帮忙，
  那是真的志愿服务。FLSA 管的是"同一类工作"，不是"同一个部门"；
- `stipend` 跟 `paid` 一起排除，理由同第二节末尾。

⚠️ 代码判断不了"是不是同一类工作"，所以跨 ministry 那一种**出提示给人看，不拦截**。
同第七节末尾那条 FLSA 提示，一个成因。

### D27 报表加「在编人员投入」

无薪在编成员的投入主要在例会和日常岗位上，那些时间**一行都不在 `Participation` 里** ——
于是他们在「志愿者工时」上接近于零，而他们很可能是投入最多的一批。
拿这个数去跟董事会或捐赠人说明人力价值时，它会系统性地低估这批人。

补法：报表加一块「在编人员投入」，读 `Shift`，三个数 ——
**实到** · **未确认** · **请假**，和「志愿者工时」**并排，不相加**。

「未确认」那个数必须画出来：它是停在 `scheduled` 没人翻的班次，
既不是实到也不是缺席，是"没人看过"。藏起来的话，
「没人处理过」和「真的没缺勤」在页面上长得一模一样 ——
同 D27 [缺勤率分母](D27-ministry-report.md)那一节，一模一样的成因。

### 时间量不出来的人：`hours_tracking` 四档

有一类人时间每周都不固定，投入是真的但特别琐碎，干活的时候也顺手干点别的，
只能按产出衡量。给他们记 `0` 是错的 —— 那是把"量不出来"印成了"没有"。

专业做法收敛在两条机制上：**自助申报 + admin 审核**（用于不绑定时间地点的服务）、
**预定额度**（按岗位记一个约定值）。HR 那一侧更直接：
豁免员工的工时法律上就不要求跟踪，专业系统显示的是"不跟踪"，不是 0。

落成 `Assignment` 上的一个字段：

| `hours_tracking` | 报表那一格显示什么 | 给谁 |
|---|---|---|
| `scheduled` | 读 `Shift`：实到 / 未确认 / 请假 | 有班表的人 |
| `agreed` | 「约定 5 小时/周 · 约 60 小时」+ 注脚**约定值，非观测值** | 时间琐碎但有约定投入的人（用 `fte` 折算，零新结构） |
| `not_tracked` | 「按产出考核 · 不计工时」 | 只能按产出衡量的人，以及 exempt 的牧职人员 |
| `self_logged` | 读工时日志 | **本轮不做**，见第十二节 |

**不变量一句话**：这一格永远显示模式的标签，**永远不显示裸的 `0`**。
这不是新规矩，是 D27 那条「没有和没算不能长得一样」推广一格 ——
而它同时让"写 0"在结构上不可能发生，不是靠谁记得。

⚠️ `hours_tracking` 是人工维护的字段。**填错了不报错，只是那一格用错的口径读出一个像模像样的数。**
所以它进 `Assignment` 的必填项（有默认值 `scheduled`），并且在员工名册上显示出来 ——
一个只有 admin 看得见、且从不出现在页面上的字段，没有人会去维护它。

## 九、补齐的 HRIS 字段（2026-08-14 追加）

这一批不是需求里点名的，是「每个 HRIS 都有、迟早会撞上」的东西，用户要求一并排进来。
按 [D10](D10-person-role-position-assignment.md) 的四层判据分配落点：

| 字段 / 表 | 落点 | 判据 |
|---|---|---|
| `compensation` · `flsa_status` · `headcount` · `location` | `Position` | 换个人来做都成立 → 编制 |
| `fte`（0.50 = 半职）· `work_arrangement`（onsite/hybrid/remote） | `Assignment` | 离不开具体这个人这一段任期 |
| `end_reason` → `EndReason` 字典表 · `is_rehirable` | `Assignment` | 描述的是**这一段任期怎么结束的** |
| `service_start_date`（组织级入职日）· `employee_number` | `Contact` | 换岗位也不变的人级事实 |
| `CredentialType` + `Credential`（证照与有效期） | 新表 | 一个人多张证 → 基数条件破了，[D15](D15-relationship-carriers.md) 判据 → 必须是表 |

### `fte` 顺带解决一件事

`Assignment.clean()` 里那条「`employment_type` 只对 `kind=employee` 有意义」**删掉**。
无薪的人一样分「每周来两天」和「每周来五天」，那个信息交给 `fte`，
而 `employment_type` 回到它字面的意思（合同形态）。

### `service_start_date` 为什么是存的不是派生的

第一版打算派生（`MIN(Assignment.start_date)`，零新字段）。
**`is_rehirable` 进了范围之后这条不成立了** —— 一旦开始跟踪"离开又回来"的人，
`MIN` 给出的是第一次入职的日期，会把中间断掉的几年算进工龄。
HR 管这个叫 adjusted service date，它在各家系统里都是**存的**字段，
原因正是它派生不出来。

### 为什么不建 `StaffProfile` 1:1 表

`service_start_date` + `employee_number` 是 D10 说的"角色层"事实
（换岗位也不变），而 D10 把那一层指给了 1:1 角色表。

**仍然放 `Contact` 上**，两条理由：
[D18](D18-admin-boundary.md) 的敏感度判据不触发（这两个都不敏感，
不像背景审查那样必须靠 model 边界做权限），而 D11 的
「只剩员工编号之类的零碎，不值得一张表」在字段数为 2 时仍然成立。

**重新考虑的条件**：出现第三个员工级字段，**或者**出现任何一个敏感的
（那时按 D18 必须独立成 model，不是可选）。

### ⚠️ `Credential` 不吃掉 `BackgroundCheck`

背景审查**仍然是独立 model**，[D18](D18-admin-boundary.md) 那条决定不撤销
（Django 没有字段级权限，敏感字段只能靠 model 边界隔离）。
把它塞进通用的 `Credential` 表，等于让所有能看证照的人都能看背景审查结果 ——
而这正是 D18 拆表要防的那件事。

`Credential` 装的是普通证照：CPR、食品安全、按立、驾照。
`expires_on` 让「谁的证下个月过期」变成一条查询，
它和 D27 里那个「未成年无同意记录」同类 —— **答的是"有没有出事"，不是"做得怎么样"**。

## 十、薪酬仍然不做

[D11](D11-position-and-assignment.md) 的结论维持，[D17](D17-app-layout.md)
给 `payroll` 留的独立 app 位置也维持。

**何时重新考虑**：真的要在系统里算人力成本或做预算报表时。
那时**必须连同权限方案一起设计**，不能顺手加个字段 ——
`payroll` 独立成 app 的全部意义就是能整个 app 级别地拒绝授权。

⚠️ 本轮加的 `fte` 会让人产生"离算工资只差一个数字了"的错觉。它不是。
`fte` 是给排班和人力统计用的，它进不了工资单，因为工资单还要税、福利、扣缴和审计。

## 十一、代价（如实记，不粉饰）

1. **一次语义迁移，两处会静默改变结果**：`kind` 的取值改写，以及 R8 的名单。
   两处各配一条固定新口径的测试；
2. **表从 4 张涨到 10 张**（`org` 加 `WorkPattern` / `Shift` / `Leave` / `EndReason`，
   `contact` 加 `CredentialType` / `Credential`）。这是本项目单轮加表最多的一次；
3. **多了一个 cron**，也就多了一处"不跑也不报错"的东西。
   ⚠️ 生成任务停摆的表现是**班表在某一天之后突然空了**，而不是报错 ——
   `render.yaml` 开头那段关于「两个 cron 漏掉的表现是没有表现」的警告，现在适用于三个；
4. **稠密班次的行数**：50 个在编人员 × 250 行 / 年 ≈ 12500 行 / 年。
   Postgres 完全不在乎，但它意味着**班表页面必须从第一天就带时间窗**，
   不能有一个"列出全部班次"的入口；
5. **`WorkPattern` 表达不了双周轮换**（隔周一次的例会）。
   现在的做法是手工加 `Shift`。真需要时给 `WorkPattern` 加 `interval_weeks`，
   是加字段不改结构；
6. **三处静默语义变更，不是一处**：`kind` 的取值迁移、R8 的名单、R6 / R7 的分母。
   三处都是同一份数据前后给出不同答案，且都不报错，所以在 roadmap 里各占一步、各配一条测试；
7. **工时从此有两个账本**（第八节），页面上永远并排、永远不相加。
   ⚠️ 代价是**没有一个「总投入工时」的数字可以印** —— 有人一定会问，
   而正确的回答是那个数字加出来就是错的；
8. **`hours_tracking` 靠人维护**。填错了不报错，只是那一格用错的口径读出一个像模像样的数。
   缓解是把它显示在员工名册上，而不是藏进 admin。

## 十二、推迟的，以及各自的重启条件

| 事情 | 何时重新考虑 |
|---|---|
| 假期类型字典表 / 余额 / 累计 / 审批工作流 | 真的要回答"他还剩几天假"时。形状照 ERPNext：`LeaveType` + `LeaveAllocation` |
| 换班（swap）与审批 | 出现"两个人自己商量换了班、而系统不知道"的实际问题时 |
| 开放班次（open shift，先建班次再找人） | `Shift.assignment` 现在非空。真需要时改成可空 + 一个认领动作 |
| 指派的 blockout（"我这几天不行"） | 志愿者开始抱怨被排到没空的日子时。⚠️ 它和 `Leave` 不是一回事：请假是已经在编的人不上班，blockout 是排班之前的可用性 |
| `Position.reports_to` 的双线汇报 / 带日期的组织架构史 | 见 [`../deferred.md`](../deferred.md)，本轮一个字没动 |
| `self_logged` 工时日志（`HoursLog` + admin 审核） | 真的有人抱怨「我投入了但系统上看不出来」时。⚠️ **先别急**：`hours_tracking` 的另外三档已经让那一格不显示 0 了，而自助申报要一张表加一个审核流程，且填的人正是"干活时也顺手干点别的"的人 —— 数字质量不见得比一个谈好的 `agreed` 值高 |
| 薪酬 | 见上面第十节 |
