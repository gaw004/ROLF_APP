# D32 · 编制拆轴：`kind` 收窄，`compensation` 独立（2026-08-14）

结论：`Position.kind` 从「员工 / 志愿者 / 理事」三档**收窄成 `staff | board`**，
把「拿不拿钱」拆成一个独立字段 `compensation`（`paid` / `unpaid` / `stipend`）。
⚠️ R8 的语义跟着变，**而那是一次不报错的变更**。

起因是一个提不出口的需求：**「有一类 ministry 的成员全是志愿者，但他们像员工一样 ——
有固定开会时间、每个人有固定岗位。我想把他们当成 employees，但写成 unpaid。」**

那句话本身就是诊断：需要同时说出「他属于员工那一类」和「他不拿钱」，
而当时只有一个字段可以说。

## ⭐ 唯一的不变量：一个人在基金会里只有一条在编路径

**`Position` + `Assignment`。** 拿不拿钱、排不排班、是不是理事，
全都是挂在这条路径上的字段，**不是另一条路径**。

这一条排除掉的是本轮最容易走的那条歪路：给「像员工的志愿者」建第二套结构。
一旦建了，下面这些立刻分裂成两份，而且每一份都会各自漂移：

| 分裂的东西 | 后果 |
|---|---|
| 组织架构图 | 一半的人不在图上，而图看起来是完整的 |
| R6 / R7 的工时口径 | 两套算法，D27 那张报表要么漏人要么重算 |
| `.active()` / `.serving()` 的时间口径 | 第二份实现，迟早和第一份走散 |
| 权限判断 | `org/permissions.py` 之外的第二处判断 |

⚠️ 这不是靠测试盯着的，是**结构上**排除：没有第二张表，就没有第二套口径。
同 [D27](D27-ministry-report.md) 那条「报表收筛过的 queryset 而不是 ministry id」。

**这一条统辖整个 Phase D** —— D33 的班表挂 `Assignment`、D34 的请假挂 `Assignment`、
D36 的工时口径收 `Assignment` 的 queryset，全都是它的推论。

## 一、诊断：一个字段扛了三个轴

真正独立的是三个轴，而当时它们全挤在 `kind` 里：

| 轴 | 问的问题 | 改之前存在哪 |
|---|---|---|
| 编制轴 | 他在组织架构里有没有一个格子（有上级、有职责、有固定承诺）？ | ✅ **本来就对** —— 有没有 `Position` 行就是答案。外部志愿者没有编制，只有 `Participation` |
| 报酬轴 | 拿不拿钱？ | 挤在 `kind` 里（`employee`=拿钱，`volunteer`=不拿钱，`board`=不拿钱） |
| 时间组织轴 | 他的时间怎么安排 —— 排班，还是自己按场报名？ | 改之前**完全不存在** |

**「unpaid employee」不是一个新类型**，它是「有编制（已有）+ 不拿钱（轴二）+ 有班表（轴三）」。

而它当时塞不进去的真正原因是**轴三根本没建** —— 系统里唯一的"安排时间"机制是活动自助报名。
这一条有一个很硬的旁证：**带薪员工当时也一样无处安放**，他们同样没有班表、
同样只能自己去活动页报名。所以这不是志愿者的特殊情况，
是一个**对所有在编人员都缺失的层**。轴三就是 [D33](D33-work-schedule.md)。

> **后来又长出来的第四个轴**：一次参与是工作还是志愿
> （[D38](D38-served-as-volunteer-or-work.md)）。它挂 `Participation` 不挂 `Position` ——
> 因为它**一次一变**：同一个人这个周末是志愿者，下周三是被派去的。
> 前三个轴描述"他是什么"，第四个描述"这一次是什么"。

## 二、`compensation` 挂 `Position` 不挂 `Assignment`

这一条没有第二个选项，而理由不是这次想出来的，是 [D11](D11-position-and-assignment.md) 自己写的：

> 空缺编制必须说得出自己是有薪岗还是志愿岗（招人的时候正是要知道这些）。

挂在 `Assignment` 上，空缺编制就答不出这个问题 —— 而"能完整描述一个空缺"
正是 D11 第二次修订的全部目的。判据口诀同样在 [D10](D10-person-role-position-assignment.md)：
**换个人来做这条信息还成立的，属于编制**。一个岗位有没有预算，换谁来干都成立。

### 考虑过并否决的：给 `kind` 加第四档 `unpaid_staff`

迁移最小（改一行 `choices`），但它是**把两个轴继续塞在一个字段里**。
D10 和 D11 各为这个病付过一次学费，D11 第二次修订留下的那句话正好是判据：

> 拆层拆到一半比不拆更危险 —— 因为它看上去已经解决了问题。

而且第五档（带津贴的实习生？带薪的志愿者协调员？）来的时候还要再来一次。

### 考虑过并否决的：`kind` 改成字典表

看起来符合 [D5](D05-lookup-tables-not-enums.md)「会变的东西做成数据」，
但 D5 自己的判定规则说**有代码 branch 就该用 `TextChoices`** ——
而 `kind` 被 R8 的查询（`events/services.py` 的 `ministry_staff_participation()`）
和报表分组直接 branch。这是反方向。

### `stipend` 这一档：报表上跟 `paid` 归堆，而这是政策不是法律

结论不变 —— 报表上 `stipend` 跟 `paid` 归堆，不跟 `unpaid` 归堆
（[D38 第七节](D38-served-as-volunteer-or-work.md) 那个志愿小时数的口径里也是这样）。
建模上没有额外成本。

⚠️ **变的是这句话的身份**。本条原来写的是「领津贴的人在 FLSA 眼里通常就是员工」，
那是**把一个保守的政策选择写成了法律事实**。查证下来要收一格：

- 明确保护「nominal fee 不破坏志愿者身份」的那条法规是 **29 CFR 553.106，
  而它只管公共部门** —— 私营非营利不在它的适用范围里；
- 私营非营利走的是更一般的事实判断（这笔钱相对于服务的量算不算 nominal、
  人是不是真自愿、是不是不期待报酬）。**没有一条明线可以写进代码。**

所以准确的说法是：**归堆是本项目替基金会选的保守口径** ——
宁可少算一批志愿小时数，也不要把一个可能是雇员的人算成志愿者。

⚠️ 而这个选择有一个具体的数据后果，写在这里免得以后没人知道它是选出来的：
D38 第七节把 `stipend` 的班表工时**永远**排除在那个可印的志愿小时数之外。
如果基金会给的真的是 nominal 的车马费，那批小时就凭空消失了 ——
而那正是 [D38 第二节](D38-served-as-volunteer-or-work.md) 自己批判过的形状
（把「有、但不该算进这个数」做成了「没有」）。

**处置：去问一次律师，别让代码替他们下结论。** 问出来的答案写回本节，
口径要改就改 D38 第七节那一处。

## 三、R8 的语义变了（这一条会静默改变报表）

需求原文是「开设这个 event 的 ministry 下面的 **employee** 谁参与了、分别负责什么」。
拆轴之后 `employee` 这个词在库里不再有对应的值，必须重新定：

**R8 = 所有在编的人，不看拿不拿钱。** 查询从

```python
position__kind=Position.Kind.EMPLOYEE
```

改成

```python
position__kind=Position.Kind.STAFF          # paid / unpaid / stipend 全算
```

理由：基金会问这个问题的动机是**「我们自己人 vs 外面来的志愿者」**，
不是「拿钱的 vs 不拿钱的」。按字面只算带薪的，那批无薪核心成员
即使实际负责了整场活动也不会出现在 R8 里。

⚠️ 这是一次**语义变更，不是重构**：同一场活动、同一份数据，改之前和改之后
R8 会返回不同的名单，而且两次都不报错。所以它在 roadmap 里是单独一步，
配一条固定住新口径的测试。

### 理事不在 R8 里，而这是选出来的（2026-08-19 确认）

`kind=staff` 这个写法把 `kind=board` 排除在外。**这是有意的，不是漏改**：
R8 问的是「办这场活动的那个部门，我们自己的工作力量谁参与了」，
理事不是那个部门的工作力量；何况理事的岗位多半挂在基金会层面
（`Position.ministry` 可空），本来也过不了那个 ministry 条件。

⚠️ 之所以要写下来并配一条测试，是因为它长得**很像**拆轴时漏改的一处：
下一个人看到「理事参加了活动却不在 R8 名单上」，第一反应是顺手把
`kind__in=[staff, board]` 补上 —— 而那是一次没有人在找的口径变更。
同一个形状同一条处方：说不出为什么的排除，和写下来的排除，长得不一样。

> **R8 名单还要加一列**：[D38](D38-served-as-volunteer-or-work.md) 的「身份」——
> 「我们自己人参加了」和「我们自己人是**被派来上班的**」是基金会分开问的两件事。

## 四、措辞

**界面上不要管无薪的人叫 employee。** 写 `Staff (unpaid)` / `Team member`。
数据库里的值无所谓，页面文案和 `choices` 的 label 要注意 ——
真出争议时，机构自己 HR 记录里的措辞是对方的证据。

同一个成因的另一处在 [D38 第六节](D38-served-as-volunteer-or-work.md)
（身份那两档的措辞），那里更要紧，因为填框的是当事人本人。

⚠️ **两组词各有各的唯一落点，别互相抄**（2026-08-15 补）：
在编身份那一组（`Staff (unpaid)` / `Team member`）在本节，
身份轴那两档（志愿服务 / 工作安排）在 D38 第六节。
两处都服从 [D23](D23-i18n-interface-only.md)「界面统一写英文」——
文档正文里的中文是**文档用语，不是 UI 文案**。

## 五、代价

1. **一次语义迁移，两处会静默改变结果**：`kind` 的取值改写，以及 R8 的名单。
   两处各配一条固定新口径的测试；
2. **反向迁移是有损的**：`staff` + `unpaid` 回不去 `volunteer` 还是回不去 `employee` ——
   信息在正向是增加的。反向函数照写（`compensation` 一律映射回 `volunteer`），
   ⚠️ 但要在 docstring 里注明它有损；
3. **跟着改的地方，一个都不能漏**（漏了大多不报错）。
   ⚠️ **只 grep `Kind.EMPLOYEE` 是漏的** —— `Kind.VOLUNTEER` 也要一起：

   | 在哪 | 改什么 |
   |---|---|
   | `events/services.py::ministry_staff_participation()` | `EMPLOYEE` → `STAFF`（R8 的名单，⚠️ 不报错） |
   | `org/models.py::Position.kind` | ⚠️ **`default=Kind.VOLUNTEER` 要改成 `STAFF`** —— 收窄之后旧默认值不存在了 |
   | `seed_demo.py` | 两处 `Kind.EMPLOYEE` + 一处 `Kind.VOLUNTEER`（Driver） |
   | `org/tests.py` / `events/tests.py` | `grep -rn "Kind.EMPLOYEE\|Kind.VOLUNTEER"`，两个词一起 grep |

4. `compensation` 的默认值是 **`unpaid`**。
   ⚠️ 这一条要写下来，因为同一轮的 `served_as` 有一整节在讲「不许有 default」——
   两个字段的形状**正好相反**，正因为相反才要各自写明：
   `compensation` 是编制的属性，一个岗位必然有报酬状态；
   `served_as` 是一句声明，可以没有人说过。
   默认 `unpaid` 而不是 `paid`：新建的空缺岗位默认无薪，
   比默认带薪安全（错了是招人时被问一句，反过来是报表上凭空多一批薪资岗）。

**Phase D 全轮的代价清单**在 [`../phase-d.md`](../phase-d.md)，那里是完整的一张表。
