## 结论

活动页上一颗 **Add to calendar**，给三个去处：

| 去处 | 装得下 | 再点一次会 |
|---|---|---|
| 下载 `.ics` | 全部（一门课 = N 条 VEVENT） | **更新**已有那一条 |
| Google 日历深链 | 一个事件 | 多出**第二条** |
| Outlook 深链 | 一个事件 | 多出**第二条** |

一门课两种下法都有：**整期一次下完**，或者**只下某一讲**
（`events/<pk>/calendar.ics` 和 `events/sessions/<pk>/calendar.ics`）。

~~订阅式 feed（webcal）**不做**。~~
**2026-09-14 同日推翻：做了。** 每人一条私密地址，见第二节后面补的那一节。

## 为什么

⭐ **这个功能的本质是往别人手机里放一份活动信息的副本，而副本会过期。**
这正是本仓库反复在拆的那个形状（「同一件事有两处记录」）。躲不掉，所以把代价
压到最小、并且**说出来**：

1. **UID 稳定 + SEQUENCE 递增**（`events/ics.py` 顶上那条契约）。同一个人再下一次，
   日历里是那一条**变了**，不是多出第二条。这是「顺滑」在下载式方案里唯一的落点。
2. 每一条 VEVENT 的说明末尾都带一句**「这份不会自己更新，当前信息以活动页为准」**
   （`ics.STALE_COPY_NOTE`，由模块自己追加，调用方忘不了）。
3. 两条深链**做不到**第 1 条 —— 它们打开的是一张新建草稿，日历自己发身份。
   所以界面上三颗键**不画成等价的**，并明写「再点一次会多出第二条」。

## 为什么不是订阅

订阅能自动更新，那确实更好。否掉它的是**代价不对称**：

- 它要给每个人一条带令牌的、**长期公开**的 URL（日历客户端不带登录态）。
- 一条令牌泄露 = 那个人的**全部行程**，而泄露的方式包括「把日历分享给家人」。
- 要新开一张令牌表、一条不认 session 的公开路由、以及吊销机制。

换来的是「改期之后不用重下一次」。今天有 D22 那套改期通知在推，而那句提示
恰好是「重新加一次」的入口。**重启条件**：有人反映改期之后日历里还是旧的。
进了 [`deferred.md`](../deferred.md)。

## 同日推翻：订阅做了（2026-09-14）

用户当天直接要的，**不是上面那个重启条件到了** —— 没有人反映改期之后日历还是旧的。
上一节那三项成本**一项都没有消失**，所以这里逐条写它们各自的出口：

| 上一节说的 | 现在怎么办 |
|---|---|
| 要一条**长期公开**的带令牌 URL | 就是这样做的：`calendar/<token>.ics`，**没有 `@login_required`** —— 抓它的是 Google / Apple 的服务器，挂上去对方拿到的是登录页的 302，订阅「成功」而日历里一条都没有，且不报错 |
| 一条令牌泄露 = 那个人的全部行程 | ⚠️ **这句仍然成立**，只是现在**收得回来**：`CalendarFeed.rotate()` 换一把钥匙，旧的当场作废，配一个确认页（后果是静默的 —— 订着旧地址的日历不报错，只是停在原地）。界面上那行小字直说「谁拿到这条地址就能看见你报的全部」 |
| 要新开一张令牌表、一条不认 session 的路由、以及吊销机制 | 三样都建了。⚠️ 令牌**懒发**：不是 `Contact` 上加一列，而是一张表 + 一颗「Create」的键 —— 加一列等于给库里每一个人都签发一条真能用的凭证，而绝大多数人永远不会去订阅 |

🔴 **上一节唯一被真正推翻的那一句**，是第 2 条实施注记里的
「这份文件是私人的 → `login_required`」。门换了，**而门后的判断一条都没换**：
内容走 `services.my_calendar_occasions()`，读的是 `Participation.objects.mine()`
—— 和 My Signups 同一个谓词，连同里面那个 `visible_to_participants()`。
于是一场撤回发布的活动在**一次刷新之内**从所有订阅里消失。
那是绕过登录之后唯一还拦得住它的东西，所以它绝不能在那条路由里被重写一遍。

⚠️ **「这份不会自己更新」那句话在订阅源里是假的**，而它假得正是本仓库反复定罪的
形状：每个字都对、不报错、没有测试会红，**而读的人会照它行事**（每次回站里核对，
订阅白订）。所以 `ics.calendar_for()` 多了一个 `updates=`，把那句**换成**成立的那
一句（`LIVE_COPY_NOTE`）—— 换，不是省：本模块仍然无条件交代「这份拷贝有多新」。
`updates=False` 是围栏，默认站在两条现成下载路由那一边。

⚠️ 一个人**既下载过又订阅了**，同一个晚上会显示两次（两份住在两个日历里）。
这不是 bug，是两条路同时存在的必然结果 —— 但人不会这么理解，所以界面上明写。

## 三条实施时才现形的

| | |
|---|---|
| 🔴 **一门课的 SEQUENCE 要看两张表** | VEVENT 的时间来自 `Session`，标题/地点/说明来自父 `Event`。改课名不动 `Session.updated_at` → SEQUENCE 不涨 → 每一个已经收下它的日历**永远显示旧名字**，而且**重新下载也没用**（客户端认为自己手上的已是最新）。取 `max(两者)` |
| 🔴 **这份文件是私人的** | 挑过讲次的学员只拿到他挑的那几讲（决定 17/18 在点名册上的直接后果）。同一个地址对不同的人给不同内容 → `login_required` + `Cache-Control: private, no-store`。少了后者，一层共享缓存能把 A 的课表发给 B，而那读起来完全正常 |
| ⚠️ **不放 ATTENDEE** | 这是本人下载的私人副本，不是基金会发出的邀请。放了等于转发一次就带走本人身份；而且有客户端见到它就当成会议邀请，开始向一个不在等回复的 ORGANIZER 发 Accept/Decline。ORGANIZER 用机构地址，不用发布者本人的 |

## 代价，写下来

- 时刻写 UTC，不带 `TZID` + `VTIMEZONE`。**因此这份文件永远不能带 `RRULE`** ——
  `RRULE` + UTC 的 `DTSTART` 会让每周七点的课在十一月第一个周日之后变成六点
  （同 `recurrence.py` 顶上那条 🔴）。真要发规则，先改成 `TZID`，这是前提不是优化。
- 深链的 body 会被两家按 HTML 渲染，所以做了转义；万一哪家其实是纯文本，
  读者会看到一个字面的 `&amp;` —— 难看但读得懂，比反过来静默丢内容好。
