## 这份文档为什么存在

目标是「现代、丝滑、经得起看」。而 20 个模板如果没有一份共同的字典，
最后会得到 **20 种按钮**——每一种单独看都没问题，放在一起就是业余感的来源。

所以这里定的不是审美，是**词汇表**：一个按钮有几种、间距只许取哪几个值、
状态标签长什么样。审美的部分（用哪个色相、圆角多大）定完就固定，
剩下的工作是**照着抄**，不是每页重新发明。

> **判据**（同本项目其它判据，是一个能当场做的动作）：
> **随便打开两个页面，把它们的主按钮并排放**。像不像同一个产品？
> 不像，说明这份文档没起作用或者没被遵守。

## 一、设计令牌

全部写成 Tailwind v4 的 `@theme`，**模板里只用语义名，不写具体色值**。
[`assets/app.css`](../../assets/app.css) 是它们唯一的定义处
（2026-08-03 改路径：原文写 `static/src/app.css`，源文件放 `static/` 里会让
生产的 `collectstatic` 失败，经过在
[04-roadmap.md 的计划外记录](04-roadmap.md#c11--源文件不能放在-static-里面)）。

### 颜色

分三组，**用途不许交叉**：

| 组 | 令牌 | 用在哪 |
|---|---|---|
| 品牌 | `brand-50` … `brand-900`（青蓝，冷静、非营利感，不像促销） | 主按钮、链接、选中态、焦点环 |
| 中性 | `ink-50` … `ink-950`（带一点点蓝的灰，纯灰会显得脏） | 文字、边框、背景、分隔线 |
| 语义 | `success` / `warning` / `danger` / `info`，各带 `-fg` / `-bg` 两档，外加 `-fg-dark` / `-bg-dark` | 消息提示、状态标签、破坏性按钮 |

⚠️ **色值只有一个定义处：[`assets/app.css`](../../assets/app.css) 的 `@theme`。**
这份文档记的是**怎么用**和**量出来是多少**，不是第二份色板 ——
两处都写色值，改了一处的那天就有两套颜色，而没有任何东西会告诉你。

**2026-08-05 起 `brand-*` 是推导出来的**，见 [D26](decisions/D26-palette-from-the-hero.md)：
从首页照片里提主色，**只取色相和饱和度**，每一档的**相对亮度钉死成下面那张表
量过的值**。所以下面每一个比值**对任何照片都精确成立** —— `@theme` 里那套青蓝
成了「没传照片时的默认值」。⚠️ 语义色不跟着变，红色必须是红色。

⚠️ **颜色永远不许是唯一的信息载体。** 这是
[`phase-c.md` 样式落点](phase-c.md#样式的落点css-只许出现在两个地方)那条判据的直接推论：
把 `app.css` 删掉页面必须仍然可用，而「靠绿色和灰色区分已报名 / 未报名」
删掉样式之后就**什么都不剩了**——那不是样式，那是内容。
所以每个状态标签**必须带文字**，颜色只是它的装饰。

### 对比度：量出来的，不是估的

正文和背景至少 **4.5:1**，大字号和图标至少 **3:1**。下面每个数字都是
2026-08-03 按 WCAG 的相对亮度公式算出来的，**不是目测**：

| 用途 | 令牌 | 实测 | |
|---|---|---|---|
| 链接文字 | `brand-700` 白底 | 7.17 | ✅ |
| 主按钮 | 白字 `bg-brand-600` | 5.21 | ✅ |
| 正文 | `ink-900` 配 `ink-50` | 15.41 | ✅ |
| 次要文字 / 帮助文字 | `ink-600` 白底 | 6.37 | ✅ |
| 深色下的正文 | `ink-50` 配 `ink-950` | 17.24 | ✅ |
| 深色下的链接 | `brand-300` 配 `ink-950` | 10.10 | ✅ |
| 语义色 `-fg` 配同名 `-bg` | 四组 | 6.38 – 7.15 | ✅ |
| 语义色 `-fg-dark` 配 `-bg-dark` | 四组 | 8.36 – 10.12 | ✅ |
| 分类徽章，浅色 | `brand-800` 配 `brand-50` | 8.43 | ✅ |
| 分类徽章，深色 | `brand-200` 配 `brand-900` | 7.68 | ✅ |

⚠️ **两条推翻了本文原来写的话，都是量完才发现的**：

1. 原文写「`brand-500` 在白底上做正文文字不够，**做背景配白字够**」——
   **不够**。白字配 `brand-500` 实测 **3.65:1**，和它做文字是同一个数
   （对比度是对称的，换个方向不会变大）。所以**主按钮用 `brand-600`**；
2. **`ink-500` 在白底上是 4.34:1，差一点点** —— 它看着像个「次要文字」色，
   实际过不了正文那条线。⚠️ `ink-500` **只做边框、分隔线、图标**；
   次要文字最浅到 `ink-600`。这条最容易破，因为破了看起来完全正常。

> **这两条的共同教训**：对比度是**算得出来的数**，凭感觉写进规范就会写错，
> 而且错得很难被发现 —— 4.34 和 4.5 在屏幕上根本看不出区别。
> 所以有一条守卫测试盯着这张表（`core.tests.ContrastGuardTests`），
> 改色值改到不达标会红。
>
> ⭐ **2026-08-05 加了更强的一条**（`DerivedPaletteTests`）：既然色阶现在是从
> 照片推出来的，那守卫就不能只测「这十个写死的值达标」。它测的是**生成器** ——
> 十二个色相 × 四档饱和度，四十八套色阶，每一套的三个关键比值都必须过线。
> 它保的是一张**还没被上传的照片**。

### 字号阶梯

只有六档，模板里不许出现其它字号：

| 令牌 | 用途 |
|---|---|
| `text-xs` | 表格里的次要信息、时间戳、帮助文字 |
| `text-sm` | 表单标签、表格正文、按钮 |
| `text-base` | 正文 |
| `text-lg` | 卡片标题、区块小标题 |
| `text-2xl` | 页面标题 |
| `text-4xl` | 只有首页的那一句欢迎语 |

字体走系统栈（`ui-sans-serif, system-ui, ...`），**不引 web font**：
一个内部工具为几十 KB 的字体文件付一次首屏延迟，换不来东西。

### 间距、圆角、阴影

- **间距只取 Tailwind 的 `1 / 2 / 3 / 4 / 6 / 8 / 12 / 16`**（4px 基数）。
  出现 `p-5`、`mt-7` 这种就是没照着这份文档写；
- **圆角三档**：控件 `rounded-md`、卡片和表格容器 `rounded-lg`、
  头像和圆点 `rounded-full`。没有第四种；
- **阴影两档**：卡片 `shadow-sm`、浮层（下拉、模态）`shadow-lg`。
  ⚠️ 深色模式下阴影几乎看不见，所以深色下**靠边框区分层次**，不是靠阴影——
  只写 `shadow-*` 不写 `dark:border` 的卡片，在深色下会糊成一片。

### 焦点环

所有可交互元素统一 `focus-visible:outline-none focus-visible:ring-2
focus-visible:ring-brand-500 focus-visible:ring-offset-2`。

**不许把焦点环去掉**。键盘用户和读屏用户靠它，而它是最容易在「觉得难看」时被删掉的东西。

## 二、深色模式

**做，并且给手动开关**（2026-08-03 定）。

实现走 Tailwind 的 class 策略（`darkMode: 'class'`），三段：

1. **`<html>` 上的 `class="dark"`** 是唯一的开关；
2. **`<head>` 里一段内联脚本**，在页面渲染之前读 `localStorage.theme`，
   没有就读 `prefers-color-scheme`，然后决定加不加那个 class；
3. **导航里一个 Alpine 的切换按钮**，写 `localStorage.theme` 并即时切 class。

⚠️ **第 2 步必须是内联的、必须在 `<head>` 里、必须在任何样式表之后**。
放到外部 JS 或者 `<body>` 末尾，页面会先按浅色画一遍再跳成深色——
那一下闪白是「廉价感」最大的单一来源，而且**它在本机开发时几乎看不出来**
（缓存命中太快），只有真实网络下才明显。

写模板时的规矩：**每写一个 `bg-` 或 `text-` 就当场写它的 `dark:` 对**。
留到最后统一补，等于把 20 个模板再扫一遍——这正是把深色模式排进 C2 而不是 C4 的理由。

## 三、组件

每个组件在 `core/templates/core/components/` 下有一个片段模板，
用 `{% include %}` 复用。**模板里不许手抄 class 串**——抄第二遍就会分叉。

| 组件 | 变体 | 要点 |
|---|---|---|
| 按钮 | `primary` / `secondary` / `danger` / `ghost` | 一屏**最多一个** primary。破坏性动作（取消报名、删工种、撤销授权）必须是 `danger` 且带二次确认 |
| 表单字段 | 常规 / 出错 | 错误文案在字段**下方**，不在页面顶部——顶部的错误在长表单上滚出屏幕，用户看不到自己错在哪 |
| 表格 | 常规 | 一律包在 `overflow-x-auto` 容器里。⚠️ 不包的话窄屏上**整页**横向滚动，导航跟着跑出去 |
| 卡片 | 常规 | 深色下靠 `dark:border-ink-700` 分层，不靠阴影 |
| 状态标签 | 按语义色 | **必须带文字**（见上面颜色那节）。`Event.status` 和 `Participation.status` 各一套，取值直接用 `get_*_display` |
| 分类标签 | `tone="brand"` | ministry 名这类**不表示状态**的标签。⚠️ **别借语义色** —— 它原来用的是 `info`，那是随手挑的，而一旦被当成「信息」读，一个没有任何状态含义的标签就有了语气。分类归 brand（跟着照片变），状态归四个语义色（永远不变），两边不许串 |
| 空状态 | 常规 | 一句话说明 + 一个下一步动作。「暂无数据」四个字是最没用的空状态 |
| 消息提示 | 四种语义 | 对应 `messages` 框架的四档。位置固定在主内容区顶部 |
| 分页 | 常规 | 列表页超过 50 行才出现 |

### 页面骨架

`base.html` 提供：跳转到主内容的链接（`skip link`）、顶栏、消息区、
主内容槽、页脚。版心 `max-w-6xl`，表单页收窄到 `max-w-2xl`。

**375px 宽度是硬要求**——志愿者那几页大概率在手机上打开。

**2026-08-05 改**：顶栏和菜单**和首页是同一个组件**
（`core/components/_top_bar.html` + `_site_menu.html`），
原来那条平铺所有链接、左上角写着「ROLF」的导航条已经没有了。

| | 首页 | 内页 |
|---|---|---|
| 底 | 平时透明，鼠标碰到页面上端才淡入 | 一直白（`solid`），且**吸顶** |
| 右侧 | 只有 login / logout | 加主题切换和用户名（`themed`） |
| 深色模式 | 不跟随 | 有 `dark:` 配色 |
| 字样 | 居中，两边都一样 | 同左 |

**为什么抽成一个组件**：两条 bar 的字号、字距、居中方式、窄屏行为必须
**逐像素一致**，否则从首页点进活动列表时字样会跳一下 —— 而那一下就是
「衔接不丝滑」的全部来源。两份拷贝迟早会差一两个像素。

⚠️ **全局导航全部在菜单里**（站内有哪些地方），但**每场活动那一排
不在**（Edit & roles / Signups / Attendance / Report / Notify）。
后者是「这场活动的哪一面」，性质不同，而且 ministry admin 在那几页之间来回跳 ——
收进两次点击的菜单会明显变难用。

⚠️ **内页的 bar 吸顶**。导航全收进菜单之后，bar 跟着内容滚走就意味着
「在长列表底部想换页得先滚回顶部」。

⚠️ **居中的字样是绝对定位的，不会给左右让位。** 375px 上它原来会换行并压住
Menu（首页从上线起就有这个 bug）。解药是收小不是换行：`white-space: nowrap`
加三档字号（11px / 13px / 18px）。

## 四、HTMX 的用法

### 唯一一条硬规矩：写操作必须有非 JS 的路

⭐ **每一个写操作都必须有一条完整的服务端表单路径，HTMX 只是它的快路。**

完整论证在 [D24 的渐进增强口径](decisions/D24-htmx-alpine-tailwind.md#渐进增强的口径只管写操作)。
一句话：它保住了现有那 404 个直接打 URL 的端到端测试。

**读操作**（筛选、排序、展开详情）不受这条约束，可以只有 HTMX 一条路。

### 约定

- 片段模板命名 `_something.html`，和整页模板放同一目录；
- 视图靠 `request.headers.get("HX-Request")` 决定返回整页还是片段，
  **两个分支共用同一份上下文**——分叉的那天，片段上的数字就会和整页对不上；
- CSRF：在 `base.html` 上挂一次 `hx-headers`，不要每个表单各写一遍；
- `hx-confirm` 用在破坏性动作上；
- 加载态用 `hx-indicator`，**每个会等超过一瞬的操作都要有**。
  没有加载态的按钮，用户会点第二次。

### 这一批页面里，哪些真的需要 HTMX

不是每页都要上。值得的是这几处：

| 页面 | 用 HTMX 做什么 |
|---|---|
| `event_attendance` | 逐人签到 / 签退，只换那一行 |
| `event_roles` | 增删工种，只换列表 |
| `event_list` / `past_events` | 时间段筛选，只换结果区 |
| `accounts/profile` | 增删紧急联系人，只换那一段 |

其余整页刷新完全够用。**别为了用而用**——每加一个片段端点，
就多一处「整页和片段可能对不上」的地方。

## 五、Alpine 的用法

### 允许的状态，以及不允许的

Alpine 只管**纯客户端 UI 状态**：展开 / 收起、下拉开合、模态开关、
标签页选中、主题切换、表单里的条件显示（比如未成年同意那一段的显隐）。

**不许出现在 `x-` 属性里的**：

- 权限判断（`can_manage`、`is_admin` 之类）——它只能问服务端；
- 工时 / 数量 / 金额的计算——服务端已经算过，算第二遍就是第二个真相；
- 日期运算——[D16](decisions/D16-time-and-dates.md) 说「今天」只有一种写法，
  而浏览器的时区不是基金会的时区。

⚠️ **越界不会报错。** 把权限判断写进 `x-show`，页面照常渲染、测试照常绿，
只是那个按钮对不该看见它的人也画出来了。服务端仍然会 403，
所以泄露的是**信息**不是权限——但那也是泄露，而且没有任何东西会告诉你它发生了。

### 守卫

一条 grep 守卫盯着模板里的 `x-` 属性，出现上面那几类关键字就红。
它和现有那 12 条守卫一起，执行方式是两层：

1. **本地**：`.pre-commit-config.yaml`，`git commit` 时闪电跑一遍。
   有人赶进度 `--no-verify` 跳过也没关系，还有第二道；
2. **强制**：GitHub Actions 的 workflow，守卫不过**红灯，禁止合并**。

> 第 2 道才是底线。本项目的记录里反复出现同一件事：
> **只写在验收清单里的规则跨不过下一轮**——守卫测试才是机器检查。

### 约定

- `x-cloak` + 一条 `[x-cloak]{display:none}` 规则，否则模态会在加载瞬间闪一下；
- 状态名统一：`open` / `selected` / `theme`，不要每页起一个新名字；
- 超过五行的 `x-data` 挪进 [`assets/js/app.js`](../../assets/js/app.js) 里的一个
  `Alpine.data()` 具名组件——写在属性里的长逻辑既没有语法高亮也没法测。
  主题切换那个（`themeToggle`）就是照这条写的，可以当样板。

## 七、活动图片（2026-08-05 新增）

活动列表每一项最左边有一张方图：ministry admin 建活动时上传的那张，
没上传就用基金会的 logo。

### 布局

| | 窄屏（< 640px） | 宽屏 |
|---|---|---|
| 尺寸 | 固定 **64 × 64**（`self-start`，不拉伸） | 宽 **96px**，高 **= 卡片的自然高度**（`self-stretch`） |
| 圆角 | 14px | 22px |
| 裁切 | `object-cover` | 同左 |
| 图与卡片的间距 | `gap-6`（24px） | 同左 |

⚠️ **窄屏不拉伸。** 手机上卡片文字换行更多、更高，拉伸会得到一个 64 宽、110 高的
长条。窄屏保持正方形，宽屏保证等高。

### 圆角是量出来的，不是猜的

参考图（基金会 logo 那张烤好圆角的 600×600）里，青色方块边长 **572px**、
圆角起点在 **130px** 处 —— **22.7%**，和苹果图标那个约 22% 的比例对得上。
按宽度取整：96 × 22.5% ≈ **22px**，64 × 22.5% ≈ **14px**。

⚠️ 用 px 不用 %。宽屏上图不是正方形（96 × 90 或 96 × 110），
百分比圆角在非正方形上会变成**椭圆角**，两个角的弧度还不一样。

### ⚠️ 高度：图跟着卡片，不是卡片跟着图 —— 试了三版

**实测的卡片自然高度**：一行详情 **90px**，带地点那种 **110px** ——
本来就不一样，所以「统一一个高度」这个想法本身就是错的。

| 版本 | 做法 | 结果 |
|---|---|---|
| 一 | `aspect-square` + `self-stretch` 直接写在 `<img>` 上 | ❌ 整行被撑成 **600px 高**。浏览器先拿图片的固有尺寸算行高，方向反了 |
| 二 | 图绝对定位进 `self-stretch aspect-square` 的空壳 | ❌ 壳宽**塌成 0，图整个消失**。flex 主轴先于交叉轴解析，`aspect-ratio` 拿不到 stretch 出来的高度 |
| 三 | 方块写死 112px + 整行 `min-h-28` | ⚠️ 能看，但**把 90px 那种卡片撑到了 112** —— 改变了「加图之前每个活动占多高」 |
| 四（现行） | 壳 `self-stretch` + **写死宽度**，图 `absolute inset-0` | ✅ 高度**精确等于**卡片自然高度（实测 90/90、110/110） |

⚠️ **宽度只能写死，这是 CSS 的限制不是写法问题**：没有办法让宽度跟着
「兄弟元素决定的高度」走。96px 是取值 —— 卡片 90 时接近正方形，110 时略高。

⚠️ 那个壳**不是包着好看**：`self-stretch` + `h-auto` 让它拿到行高，
而它自己的内容高度是 0（唯一的子元素绝对定位了），所以**它不参与行高的计算**。
少了这一层就退回第一版。

### 色调：为什么要处理，处理成什么

上传的照片什么色都有 —— 一排下来五颜六色，把「简约大气」这件事直接毁掉。
所以统一压一档：

| 属性 | 浅色 | 深色 | 为什么 |
|---|---|---|---|
| `saturate` | 0.72 | 0.72 | 压掉最扎眼的那部分饱和度，但不到发灰。低于 0.6 会让食物照片看起来不新鲜 |
| `contrast` | 0.96 | 0.96 | 极轻，只是把过硬的对比收一点 |
| `opacity` | 0.94 | 0.94 | 让图稍微「沉」进页面底色，而不是浮在上面 |
| `brightness` | — | 0.88 | ⚠️ 只在深色下。为白底拍的照片放进深色页面会发光，在一排暗色卡片里格外扎眼 |

**悬停时全部还原成本色**（`filter: none`）。⚠️ 这不是装饰：降饱和是为了整页安静，
而人真的想看清那张图的时候得有办法看清。

⚠️ **这四个值是样式，写在 [`assets/app.css`](../../assets/app.css) 的 `.event-thumb` 里，
不烤进上传的图片文件。** 两个理由：

1. 烤进去等于把一个设计决定放到样式表够不到的地方 —— 违反
   [`phase-c.md` 的样式落点规矩](phase-c.md#样式的落点css-只许出现在两个地方)；
2. 看过真实照片之后这几个值多半要调，改 CSS 是一行，
   烤进去要把**所有已上传的图**重新处理一遍。

### 存储：三条约束，每一条都决定了一件事

要求是「尽量不占空间、活动结束就消失、不进任何备份」。推论：

| 要求 | 推出来的做法 |
|---|---|
| 不进任何备份 | ⚠️ **不能存数据库**。备份是 `pg_dump`，列里的东西会进每一份备份、而且永远在。存成文件 |
| 活动结束就消失 | `purge_event_images` 每天跑一次，判据是 **`end_time` 已过**，不是 `status == completed`（后者要人手动改，忘了改图就不会删） |
| 尽量不占空间 | 上传即重编码：最长边 **900px**、**WebP q82**。一张 4 MB 的手机照片变成不到 100 KB |

**900px 是从显示尺寸倒推的**，不是拍脑袋：缩略图最大约 140 CSS px，
900 给到 4 倍屏还有富余，也留了「以后可能放大显示」的余地。

⚠️ **代价说清楚**：活动结束后那张图**永久没了**。往期活动列表因此**不放图位** ——
一整列一模一样的默认 logo 是噪音，不是信息。活动详情页目前也不放图（位置还没定）。

### 上传处理里三件不能省的事

1. ⚠️ **先 `exif_transpose` 再剥 EXIF。** 手机照片是把「这张是横的」记在 EXIF 里而不是
   真的转像素 —— 先剥 EXIF 的话每张竖拍照片都会**躺着**出来，而且文件完全合法，
   不报任何错；
2. ⚠️ **必须剥 EXIF，理由是隐私不是体积。** 手机照片带 GPS 坐标，
   一张在志愿者家里拍的照片会把他家地址公布给所有登录用户；
3. ⚠️ **拒绝 SVG。** 用 Pillow 打开就是校验 —— SVG 打不开，于是天然被挡在外面。
   这不是洁癖：SVG 能带脚本，而它会从本站域名提供，那是一个存储型 XSS。

## 八、公开首页（2026-08-05 新增）

决策和取舍在 [D25](decisions/D25-public-front-page.md)，这里只留写模板时要照抄的东西。

⚠️ 首页**不继承 `base.html`**，也**不跟随深色模式**。它是一张满屏照片加白字，
深色版本没有意义 —— 而如果它也切主题，顶栏那套「白字 / 深蓝字」的规则会全部翻转。

### 顶栏

| 状态 | 底 | 字 |
|---|---|---|
| 平时 | 透明 | 白，带 `text-shadow` 兜底 |
| 鼠标碰到页面上端 / `:focus-within` | 白，400ms 从虚到实 | `brand-900`，阴影去掉 |
| 窄屏（< 640px） | 始终白 | 始终 `brand-900` |

⚠️ 感应区是顶部**一条 96px 高的透明带**，不是顶栏自己 —— 顶栏平时是透明的，
鼠标要先能碰到它才谈得上浮出来。

### 菜单面板

- 面板从左滑入，420ms，`cubic-bezier(0.32, 0.72, 0, 1)`；
- 条目逐个入场：延迟 = `160ms + 序号 × 55ms`，序号由模板的 `--i` 给，**在 CSS 里算**；
- ⚠️ 面板关着时条目必须回到初始状态，否则第二次打开是一次性全部出现 ——
  「呼吸感」只在第一次有。

### 压在照片上的文字，对比度自己造

⚠️ 背景由基金会上传，**内容不可预知**。两层压暗：

1. 全屏 `from-black/45 via-black/15 to-black/40` —— 顶栏那几个字；
2. 下三分之二 `from-black/75 via-black/45 to-transparent`（向上）—— 经文在那里。

**实测**（拿一张带白色云团的刁难图量的）：顶栏区 **9.94:1**、经文区 **5.57:1**。

> 第一版只有第 1 层，经文中间两行直接糊掉。
> **一般形式：任何压在用户上传内容上的文字，对比度都必须由我们自己保证** ——
> 「传上来的图都挺暗的」不是一个能写进代码的前提。

## 九、滚动时的呼吸感（2026-08-05 新增）

活动列表的卡片（`/events/` 和 `/events/past/`）在进出视口时轻微位移 + 缩放，
参照 iOS Messages 的手感。类名 `.scroll-breathe`。

⚠️ **只动 `transform`。不动间距，也不动透明度。**

**不动间距**：滚动中改 `margin` 会改变页面总高度，浏览器要不断重排、
滚动位置和手指打架 —— 结果不是呼吸感，是页面在抖。
视觉上两者是同一件事，代价差一个数量级。

⚠️ **不动透明度 —— 这一条是实测出来的。** 第一版两端把 `opacity` 降到 0.35，
结果在**没有滚动条的短页面上，整个列表一打开就是灰的**：时间轴退化了，
进度直接停在 100%，也就是那一帧。而演示数据只有两场活动，**正是这种页面**。
位移停在 ±6px 肉眼看不出来（实测退化时不到 1px），透明度停在 0.35 一眼就是坏的。

⚠️ `animation-range` 只能写**一个区间**。第一版写成
`entry 0% cover 20%, cover 80% exit 100%` —— 逗号在这里的意思是
「给多个动画各配一个区间」，于是后半段被整个丢掉，**而且没有任何报错**。

实现是**纯 CSS 的滚动驱动动画**（`animation-timeline: view()`），零 JS：

- ⚠️ 整段包在 `@supports (animation-timeline: view())` 里。
  **Firefox 目前不支持** —— 那里连规则都不会应用，列表照常可用；
- ⚠️ 再包一层 `prefers-reduced-motion: no-preference`。
  这一条不能只靠 `app.css` 顶上那条全局规则：那条把 `animation-duration` 压到
  0.01ms，而滚动驱动动画的进度由滚动位置决定、**不看时长**，压不住；
- `animation-range` 只覆盖进出视口的两端，中间是静止的 ——
  全程都在动会让人晕，而且看不出是在响应滚动。

> **只有两三张卡片时几乎看不出来。** 这个效果在长列表上才明显，
> 而演示数据只有两场活动 —— 别据此判断它没生效。

## 十、深色模式的第二形态：照片背景（2026-08-05 新增）

传了首页照片之后，深色模式不再是纯黑：

| | 没传照片 | 传了照片（`<html>` 上有 `.has-hero`） |
|---|---|---|
| 页面底 | `ink-950` 实心 | 那张照片，压暗 80%，**fixed 不随内容滚动** |
| 卡片 / 表格 | `ink-900` 实心 | `rgb(0 0 0 / 0.72)` + 10px 模糊 |
| 顶栏 | `ink-900` 实心 | `rgb(0 0 0 / 0.62)` + 14px 模糊 |
| 表单控件 | `ink-800` 实心 | `rgb(0 0 0 / 0.45)` |

⚠️ **0.72 是量出来的**，不是挑好看的：它是能让正文在照片最亮的区域上仍然过
4.5:1 的最低值。实测（最亮处）：正文 **9.32:1**、链接 **5.93:1**、次要 **6.62:1**。

⚠️ **背景层在 `-z-10`，是整页一张**，不是每张卡片各自贴一块。后者会让十几张卡片
各自截取照片的一小块，滚动时那些小块跟着动，看起来像一堆各自为政的窗口。

⚠️ **浅色模式一个字不变。** 浅色下页面已经是干净的浅灰底，铺照片只会让每一段
文字都变成「压在照片上的文字」—— 那是要一处一处保证对比度的东西。

⚠️ **只用图片，从不用视频。** 每一页都解码一段视频在手机上是发烫和耗电，
而没有人在看它。

## 十一、滚动惯性（2026-08-05 重做）

活动列表的卡片**滞后于滚动**，而且每张滞后得不一样多 —— 快速拖动时卡片之间的
间距看起来被拉开又合拢，松手后弹回对齐。实现在
[`assets/js/app.js`](../../assets/js/app.js) 的那段 IIFE，类名仍是 `.scroll-breathe`。

原来那版纯 CSS 的（`animation-timeline: view()`）**已整个删掉**。
它按设计工作，只是给不了要的东西：滚动驱动动画知道的是元素在视口里的**位置**，
而「拖拽的惯性」需要的是**速度**。那是那个技术的边界，不是参数没调够。

⚠️ **两套不能并存。** 它们会同时写同一个元素的 `transform`，谁最后写谁赢，
而那取决于帧的时序 —— 必然出 bug。

三个参数：

| | 值 | 为什么 |
|---|---|---|
| 位移上限 | 18px | 一次「滚到底」的滚轮事件速度可以是几千，没有上限卡片会被甩出屏幕 |
| 速度衰减 | 每帧 ×0.82 | 手指停了之后卡片还要追几帧才归位，那几帧就是惯性看起来的样子 |
| 跟随系数 | 每张 0.10–0.155，由**序号**推出 | ⚠️ 全都一样的话它们整体平移，看起来只是页面在晃。用序号不用随机：刷新之后同一张卡片行为要一致，否则每次手感都不同，像坏了 |

⚠️ 动的**始终只有 `transform`**。真改 `margin` 会让页面总高度不断变化、
滚动位置和手指打架 —— 那是抖，不是惯性。间距是**看起来**不均匀的：
相邻两张位移不同，中间那道缝就宽窄不一。视觉上没有区别。

⚠️ **循环在静止时自己停下**，并把 `transform` 清空。一个永远在跑的 rAF 循环
会让手机一直保持高频唤醒，而这整个效果只存在于手指在动的那半秒。
`prefers-reduced-motion` 下**两处都关**：JS 直接不启动，CSS 再兜一层
`transform: none`。

## 十二、图表（2026-08-05 新增）

管理列表右边那块报表面板用的（[D27](decisions/D27-ministry-report.md)）。
**没有引任何图表库** —— 五张图全部是条形图，用两个模板组件画：

| 组件 | 画什么 |
|---|---|
| `events/_bar_chart.html` | 一组横条，每条一个标签一个数字 |
| `events/_paired_bar_chart.html` | 一行两条共用一把尺子（「要几人 / 来了几人」） |

### 为什么是 CSS 的条子，不是 SVG

原方案写的是服务端渲染 SVG。真写下来发现五张图**全是条形图**，
于是 SVG 的好处一样都用不上，而 CSS 的条子反而更好：

- 继承主题色 —— `bg-brand-500` 跟着 [D26](decisions/D26-palette-from-the-hero.md)
  从首页照片推出来的色阶走，SVG 里要另外把色值灌进去；
- 自己会重排，不用管 viewBox 和媒体查询；
- 不用 ~200KB 的 Chart.js，读操作也不必依赖 JS。

⚠️ 线图、面积图、饼图这三种 CSS 画不了。**这一页也没有它们**：
时间趋势是离散的月份，用竖直的柱或横条都对；构成占比不画饼图 ——
人比较不了角度，三块以上的饼必须标数字，标了数字饼就没用了。

### 五张全是横的

包括两张按月的。这个面板在宽屏上只有半个屏，十二根竖条各 20px 宽，
底下还要塞「Aug 2026」。横过来每个标签独占一行按自然字号排，
而且**五张共用一个组件** —— 这一页上不可能出现两张长得不一样的图。

代价：按月的图变成**从上往下**读，最早的在上面。接受。

### 三条硬规矩

| 规矩 | 不遵守会怎样 |
|---|---|
| 按**最大值**缩放，不按总和 | 最长那根只画到三分之一，会被读成「占某个东西的三分之一」，而页面上没有任何东西说那是什么 |
| 少于三根**退回文字** | 一根柱子的柱状图看起来像在比较，但没有可比的对象 —— 比它替换掉的那句话更难读 |
| 数字**始终**以文字写在条子旁 | 条子是给眼睛扫的，不是唯一载体：读屏软件读不出一个 div 的宽度 |

⚠️ 宽度是**行内样式**，因为它是数据不是设计 —— Tailwind 的类名在构建时就固定了，
表达不了一个运行时算出来的百分比。⚠️ 但**百分比本身在 `services.py` 里算好**，
模板只负责画：模板里不许有算术（[D18](decisions/D18-admin-boundary.md)）。

### 颜色

| 用途 | 令牌 |
|---|---|
| 普通的条 | `bg-brand-500`（跟着照片走） |
| 条的槽 | `bg-ink-100` / 深色 `bg-ink-700` |
| 「要几人」那根（参考量） | `bg-ink-300` / 深色 `bg-ink-500` |
| 缺人的那根 | `bg-warning-fg`，配 `text-warning-fg` 的数字 |
| 唯一的风险数字（未成年无同意记录） | `text-danger-fg`，**为 0 时也画出来** |

⚠️ 缺人用 warning 不用 danger：danger 在全站的意思是「这里出问题了」，
而人手不够是一条要看的信息，不是一次事故。签到页上「No-show」那个徽章同理。
