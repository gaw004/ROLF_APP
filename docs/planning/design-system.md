## 这份文档为什么存在

目标是「现代、丝滑、经得起看」。而 20 个模板如果没有一份共同的字典，
最后会得到 **20 种按钮**——每一种单独看都没问题，放在一起就是业余感的来源。

所以这里定的不是审美，是**词汇表**：一个按钮有几种、间距只许取哪几个值、
状态标签长什么样。审美的部分（用哪个色相、圆角多大）定完就固定，
剩下的工作是**照着抄**，不是每页重新发明。

> **判据**（同本项目其它判据，是一个能当场做的动作）：
> **随便打开两个页面，把它们的主按钮并排放**。像不像同一个产品？
> 不像，说明这份文档没起作用或者没被遵守。

## 一、设计令牌

全部写成 Tailwind v4 的 `@theme`，**模板里只用语义名，不写具体色值**。
[`assets/app.css`](../../assets/app.css) 是它们唯一的定义处
（2026-08-03 改路径：原文写 `static/src/app.css`，源文件放 `static/` 里会让
生产的 `collectstatic` 失败，经过在
[04-roadmap.md 的计划外记录](04-roadmap.md#c11--源文件不能放在-static-里面)）。

### 颜色

分三组，**用途不许交叉**：

| 组 | 令牌 | 用在哪 |
|---|---|---|
| 品牌 | `brand-50` … `brand-900`（青蓝，冷静、非营利感，不像促销） | 主按钮、链接、选中态、焦点环 |
| 中性 | `ink-50` … `ink-950`（带一点点蓝的灰，纯灰会显得脏） | 文字、边框、背景、分隔线 |
| 语义 | `success` / `warning` / `danger` / `info`，各带 `-fg` / `-bg` 两档，外加 `-fg-dark` / `-bg-dark` | 消息提示、状态标签、破坏性按钮 |

⚠️ **色值只有一个定义处：[`assets/app.css`](../../assets/app.css) 的 `@theme`。**
这份文档记的是**怎么用**和**量出来是多少**，不是第二份色板 ——
两处都写色值，改了一处的那天就有两套颜色，而没有任何东西会告诉你。

**2026-08-05 起 `brand-*` 是推导出来的**，见 [D26](decisions/D26-palette-from-the-hero.md)：
从首页照片里提主色，**只取色相和饱和度**，每一档的**相对亮度钉死成下面那张表
量过的值**。所以下面每一个比值**对任何照片都精确成立** —— `@theme` 里那套青蓝
成了「没传照片时的默认值」。⚠️ 语义色不跟着变，红色必须是红色。

⚠️ **颜色永远不许是唯一的信息载体。** 这是
[`phase-c.md` 样式落点](phase-c.md#样式的落点css-只许出现在两个地方)那条判据的直接推论：
把 `app.css` 删掉页面必须仍然可用，而「靠绿色和灰色区分已报名 / 未报名」
删掉样式之后就**什么都不剩了**——那不是样式，那是内容。
所以每个状态标签**必须带文字**，颜色只是它的装饰。

### 对比度：量出来的，不是估的

正文和背景至少 **4.5:1**，大字号和图标至少 **3:1**。下面每个数字都是
2026-08-03 按 WCAG 的相对亮度公式算出来的，**不是目测**：

| 用途 | 令牌 | 实测 | |
|---|---|---|---|
| 链接文字 | `brand-700` 白底 | 7.17 | ✅ |
| 主按钮 | 白字 `bg-brand-600` | 5.21 | ✅ |
| 正文 | `ink-900` 配 `ink-50` | 15.41 | ✅ |
| 次要文字 / 帮助文字 | `ink-600` 白底 | 6.37 | ✅ |
| 深色下的正文 | `ink-50` 配 `ink-950` | 17.24 | ✅ |
| 深色下的链接 | `brand-300` 配 `ink-950` | 10.10 | ✅ |
| 语义色 `-fg` 配同名 `-bg` | 四组 | 6.38 – 7.15 | ✅ |
| 语义色 `-fg-dark` 配 `-bg-dark` | 四组 | 8.36 – 10.12 | ✅ |
| 分类徽章，浅色 | `brand-800` 配 `brand-50` | 8.43 | ✅ |
| 分类徽章，深色 | `brand-200` 配 `brand-900` | 7.68 | ✅ |

⚠️ **两条推翻了本文原来写的话，都是量完才发现的**：

1. 原文写「`brand-500` 在白底上做正文文字不够，**做背景配白字够**」——
   **不够**。白字配 `brand-500` 实测 **3.65:1**，和它做文字是同一个数
   （对比度是对称的，换个方向不会变大）。所以**主按钮用 `brand-600`**；
2. **`ink-500` 在白底上是 4.34:1，差一点点** —— 它看着像个「次要文字」色，
   实际过不了正文那条线。⚠️ `ink-500` **只做边框、分隔线、图标**；
   次要文字最浅到 `ink-600`。这条最容易破，因为破了看起来完全正常。

> **这两条的共同教训**：对比度是**算得出来的数**，凭感觉写进规范就会写错，
> 而且错得很难被发现 —— 4.34 和 4.5 在屏幕上根本看不出区别。
> 所以有一条守卫测试盯着这张表（`core.tests.ContrastGuardTests`），
> 改色值改到不达标会红。
>
> ⭐ **2026-08-05 加了更强的一条**（`DerivedPaletteTests`）：既然色阶现在是从
> 照片推出来的，那守卫就不能只测「这十个写死的值达标」。它测的是**生成器** ——
> 十二个色相 × 四档饱和度，四十八套色阶，每一套的三个关键比值都必须过线。
> 它保的是一张**还没被上传的照片**。

### 字号阶梯

只有六档，模板里不许出现其它字号：

| 令牌 | 用途 |
|---|---|
| `text-xs` | 表格里的次要信息、时间戳、帮助文字 |
| `text-sm` | 表单标签、表格正文、按钮 |
| `text-base` | 正文 |
| `text-lg` | 卡片标题、区块小标题 |
| `text-2xl` | 页面标题 |
| `text-4xl` | 只有首页的那一句欢迎语 |

**2026-08-06 改口**：引一个**自托管**的 web font（Jost），推翻了原来那条「不引 web font」。

原话是「一个内部工具为几十 KB 的字体文件付一次首屏延迟，换不来东西」。
换来的东西现在有了：一个几何无衬线的调子，而系统栈给不出这个调子。

| | |
|---|---|
| 要的是 | Futura 那种感觉 |
| 为什么不是 Futura 本体 | 🔴 **商业字体，我们没有 webfont 授权，不能打包发布。** 这不是取舍 |
| 为什么不是「字体栈里写 Futura」 | Futura 只装在 macOS / iOS 上。写进字体栈的结果是**你看到的和多数志愿者（Android）看到的不是同一套设计**，而且你无法验证 |
| 用的是 | **Jost**（SIL OFL，专门做成 Futura 那个调子），自托管在 `core/static/core/fonts/` |
| 多大 | latin 26KB + latin-ext 17KB，**一个文件覆盖全部字重**（可变字体，实测和 Google 给 `wght@100..900` 的响应字节相同）|

⚠️ **系统栈一个都不许从 `--font-sans` 里删掉。** Jost 里没有中文、日文、韩文，
而这个系统存的是人的真实姓名。少了后面那一档，一个中文名会掉到浏览器最后的兜底字体上。

⚠️ **`@font-face` 里的 `url()` 是部署风险，不是样式细节。** 生产用
`ManifestStaticFilesStorage`，它会解析 CSS 里的 `url()` 并去 `STATIC_ROOT` 里找 ——
找不到就让 `collectstatic` 失败，也就是让部署停住。改完路径请真的跑一次
`collectstatic`；`core.tests.SelfHostedFontTests` 也盯着这一条。

### 间距、圆角、阴影

- **间距只取 Tailwind 的 `1 / 2 / 3 / 4 / 6 / 8 / 12 / 16`**（4px 基数）。
  出现 `p-5`、`mt-7` 这种就是没照着这份文档写；
- **圆角四档**（2026-08-06 改，原来是三档）：
  **按钮 `rounded-full`（药丸）**、输入框和下拉 `rounded-md`（6px）、
  卡片和表格容器 **12px**（同日从 8px 加大）、头像和圆点 `rounded-full`。
  ⚠️ 药丸只给**按钮**。输入框保持方角（参照那张 LV 的图就是方角输入框配药丸按钮），
  badge 保持 `rounded-md` 因为它不可点 —— 跟着变成药丸会让「能按的」和
  「不能按的」长得一样。药丸的水平内边距要比方角按钮大一档（`px-5` 而不是 `px-4`），
  圆端会吃掉一部分视觉空间；
  ⚠️ 卡片圆角写在 `.card` 里而不是模板的 `rounded-lg` 上 —— 12px 不是 Tailwind 的一档，
  而「差一档的圆角」是那种一屏里同时出现两种才看得出来的不齐；
- **阴影**：卡片是**两层**（一层大而散的落影 + 一层贴边的接触影），浮层 `shadow-lg`。
  ⚠️ 卡片这一档 2026-08-06 加重到约 4 倍。原因是同一天去掉了卡片边框：白卡片配
  `ink-50` 页面底几乎同色，没有线又没有影，几块内容会糊成一片，卡片不再读作「物件」。
  ⚠️ 深色下**落影要换方向想**：黑影压在暗背景上看不见，起作用的是卡片外围那一圈
  更暗的晕（照片亮的地方尤其有效），加上上面那条方向性亮边。

### 焦点环

所有可交互元素统一 `focus-visible:outline-none focus-visible:ring-2
focus-visible:ring-brand-500 focus-visible:ring-offset-2`。

**不许把焦点环去掉**。键盘用户和读屏用户靠它，而它是最容易在「觉得难看」时被删掉的东西。

## 二、深色模式

**做，并且给手动开关**（2026-08-03 定）。

实现走 Tailwind 的 class 策略（`darkMode: 'class'`），三段：

1. **`<html>` 上的 `class="dark"`** 是唯一的开关；
2. **`<head>` 里一段内联脚本**，在页面渲染之前读 `localStorage.theme`，
   没有就读 `prefers-color-scheme`，然后决定加不加那个 class；
3. **导航里一个 Alpine 的切换按钮**，写 `localStorage.theme` 并即时切 class。

⚠️ **第 2 步必须是内联的、必须在 `<head>` 里、必须在任何样式表之后**。
放到外部 JS 或者 `<body>` 末尾，页面会先按浅色画一遍再跳成深色——
那一下闪白是「廉价感」最大的单一来源，而且**它在本机开发时几乎看不出来**
（缓存命中太快），只有真实网络下才明显。

### 深色下的玻璃材质（2026-08-06 重调，同日改了三次）

深色模式下背景是**两层叠起来的**：照片 + 压在它上面的遮罩 → 卡片的半透明黑。

| | 照片怎么压暗 | 卡片黑 | blur | 卡片表面能看见多少照片结构 | 卡内正文 | 卡外文字 |
|---|---|---|---|---|---|---|
| 一 | 平铺 0.80 | 0.72 | 10px | 差 **0.36pp**（几乎纯黑） | 16.26:1 | 9.37:1 |
| 二 | 平铺 0.68 | 0.40 | 3px | 差 **3.36pp** ≈ 9 倍 | 10.24:1 | 6.03:1 |
| 三 | 照片自己的 `filter` | 0.40 | 3px | 同上，照片有质感了 | 10.63:1 | 6.68:1 |
| 四（现在） | 和首页**同一份**遮罩 | 0.40 | 3px | 同上 | 7.81:1 | 4.03:1 ⚠️ |

（前三行的对比度是纯白照片这个最坏情况；第四行是**当前那张照片** —— 原因见下。）

🔴 **一条量错的注释，2026-08-06 更正。** `app.css` 原来写着「0.72 是能让正文过 4.5:1 的
**最低值**」。拿真实 hero 照片重量：0.72 实际给出 **16.26:1**。那个数是在全页遮罩存在
**之前**量的 —— 加上遮罩之后照片先被压掉 80%，卡片再压 72%，只剩 5.6% 能到卡片表面。
代价看得见：卡片表面的亮度范围只有 0.36 个百分点，它不是玻璃而是一块纯黑。

⚠️ **主要旋钮是照片那一层，不是卡片。** 照片不压暗的话，卡片再透也没东西可看；
而压暗的下限由**卡外的文字**决定（页面标题、条数、区块说明直接压在照片上）。

⚠️ **模糊几乎不影响对比度**（实测 0.78pp vs 0.79pp），所以「少一点模糊」代价为零。
变暗全部交给不透明度 —— `backdrop-filter` 在不支持它的浏览器上会被整个忽略，
而对比度不能依赖一个可以被忽略的东西。

⚠️ **警示框不是玻璃**（`:not(.border)`）—— 一条要人注意的提示，透出照片就等于把它
降级成装饰。它复用「警示框都显式带 `border`」这个标记。
⚠️ 弹窗也不透（上面是要逐字读的表单）；顶栏更实（0.62 / blur 14px），内容从它底下
滚过去，太透会把字糊在一起。
⚠️ 表格容器和卡片是同一套材质，只是边框由它自己画，见组件表那一行。

#### 🔴 照片怎么变暗：第四版是**一次知情的退让**

前三版都在追「压得够暗、对比度过线」，第三版做到了最好：照片自己的
`filter: brightness(.39) contrast(1.4) saturate(1.2)`，乘系数而不是加常数，实测比平铺黑
分离 **+64%**、饱和度 **+91%**，纯白照片下卡外文字还有 **6.68:1**。

**它被推翻的理由只有一个：太暗，不好看。** 现在用的是**和首页同一份**两层渐变遮罩
（`_hero_scrim.html`，首页和内页共用一个文件）。

⚠️ 代价是真实的，而且要写在能被看见的地方（这里、片段的注释里、`phase-c.md` 的已知缺口）：

| | 卡外小字 | 卡内正文 |
|---|---|---|
| 当前那张照片 | **4.03:1**（低于 AA 的 4.5） | 7.81:1 |
| 纯白照片 | 1.73:1 🔴 | 4.11:1 🔴 |

⚠️ 大标题不受影响 —— 大字判据是 3:1，4.03 过得很宽。掉线的是卡片外的**小字**
（列表的条数行、区块的说明行）。
🔴 **而它跟着照片变，且不报错。** 前三版守卫的口径是「纯白照片下也过线」，正是因为
基金会会换首页照片；第四版**放弃了这条口径**。守卫现在只盯得住「遮罩还在、数值没被
悄悄改」（`GlassMaterialContrastTests` 把 1.73 / 4.11 钉住，再往下掉会红），
盯不住「传了什么照片」。

⚠️ 这一节值得留着的判据是这个：**第三版在每一项指标上都更好，而它仍然是被换掉的那个。**
一个改动在所有能量的东西上都赢，不等于它对 —— 而反过来，选了好看就要把代价写清楚，
不能让它在某一天以「怎么这行字看不清」的形式被别人发现。

⚠️ 抽成共用片段是这次要求本身逼出来的：要求是「跟首页压暗的强度**一样**」，而「一样」
如果靠两个模板各写一遍 class 串来维持，它一定会分叉。抽完拿像素比对验过首页：
**0 个像素变化**，纯重构。

#### 玻璃按钮：只给 secondary 和 ghost，只在深色 + 有照片时

⚠️ 限定深色**不是保守**：浅色模式下按钮背后是白卡片压白页面，没有东西可透，
「玻璃」只会得到一个更淡的按钮，而更淡的按钮对比度更差。

🔴 **`primary` 一度做了玻璃，那是个上线了的缺陷（2.71:1），当天改回实心。**
两个独立的错，而它们的共同点是**我量的不是这个按钮**：

| 错在哪 | 表现 | 为什么没被发现 |
|---|---|---|
| 底色写成 `rgb(31 117 148 / 0.75)` —— app.css 里 brand-600 的**字面量** | 品牌色是 [D26](decisions/D26-palette-from-the-hero.md) 从首页照片推出来的（`--color-brand-*`），写死字面量等于把按钮从主题里摘出来。当前照片推出的是暖沙棕 `#806856`，按钮却是默认青 `#1f7594` | **只在深色模式下错**，浅色是对的。而字面量在 CSS 里长得完全合理 |
| 对比度算的是**白字**配那个底（6.51:1） | 这个按钮在深色下根本不是白字 —— `button.html` 写的是 `dark:text-ink-950`（近黑），因为深色实心底是更亮的 brand-500。真实值 **2.71:1** | 我量的是「一个 primary 按钮该有的颜色」，那是脑子里的模型；真实颜色要去读 computed style |

⭐ 由此立两条通则：
**① 玻璃规则里一个品牌色字面量都不许有** —— 要带 alpha 就用
`color-mix(in srgb, var(--color-brand-N) X%, transparent)`；
**② 对比度必须按元素**上真实生效的那两个颜色算，不按变体名推。
两条都有守卫（`GlassMaterialContrastTests`）。

改回实心而不是改成白字（白字能到 6.75:1，也可行）的理由：一屏最多一个 primary，
它的全部作用是告诉人「你最可能要做的是这件事」，这件事不该有任何可读性上的余量问题。
代价如实说：并排时它是唯一实心的那个。

⚠️ `ghost` 平时无底，所以它的玻璃只在 hover 时出现。`danger` 完全不做 ——
半透明会让红色取决于背后是什么，而一个警示色不能随背景改变。

🔴 那段 CSS **故意写在 `@layer components` 外面**。按钮的底色来自 Tailwind 工具类
（`bg-brand-600` 等），而工具类在 `@layer utilities`，层级高于 components ——
写在层里会被压掉。**未分层的作者样式胜过所有层**，所以那是唯一正确的位置。
⚠️ 这和「模板上的 `w-16` 压掉了 CSS 里的宽度」是同一个坑换了个场合 ——
Tailwind 的层级顺序**静默地决定谁赢**，而两次都不是靠读 CSS 发现的。

#### 🔴 `backdrop-filter` 会被祖先杀掉，而且是静默的

同一天踩到两次，两次都是「这条规则本身怎么看都对」：

| 祖先做了什么 | 后代的 `backdrop-filter` |
|---|---|
| `overflow: hidden` | ✅ 照常 |
| 固定高度 | ✅ 照常 |
| 动画只动 `translate` | ✅ 照常 |
| 动画动了 `opacity` | ❌ **永久失效**，不只是动画期间 |
| 自己有 `backdrop-filter`（成为 backdrop root） | ❌ 后代采样到空 |

第一次是入场动画：`event-row-in` 里有 `opacity`，挂在 `<li class="event-row">` 上，于是
里面 `.card` 的玻璃**从加上动画那一刻起就没生效过**。强制 `backdrop-filter: none` 重渲染
去比像素：**0 个像素变化**。把动画挪到 `.event-row > .card` 之后：27,294 个像素变化。

⚠️ 元素动**自己**的 opacity 是可以的 —— `backdrop-filter` 在元素自身 opacity 之前生效。
只有**祖先**会毁掉它。所以修法是「往下挪一层」，不是「不要淡入」。
⚠️ 当时的往期活动页不受影响（那里 `<li>` 本身就是卡片）；那一页和它的 `.event-row-past` 2026-08-17 一起删了。

⭐ 判据，而它已经收了三次学费：**一条声明写在哪个元素上，决定了它伤到什么 ——
而读这条声明本身永远看不出来。**

| 声明 | 挂错在哪 | 后果 | 靠什么发现 |
|---|---|---|---|
| `animation`（keyframes 里有 `opacity`） | 挂在 `<li class="event-row">`，也就是卡片的祖先 | 卡片的 `backdrop-filter` **永久失效** | 强制 `backdrop-filter: none` 比像素：0 个变化 |
| `backdrop-filter: brightness()` | 挂在亮边环上，而它在卡片这个 backdrop root **里面** | 环采样到空的，乘出来是**暗的** | 在渐变背景上摆带 blur / 不带 blur 两张卡分别量 |
| `overflow: hidden` | 挂在 `.event-row`，而它的框和卡片三边重合 | 卡片的落影被切掉，每个角留一个**深色尖角** | **用户看出来的。** 量了才知道卡下方是 248/248/248，一点阴影都没有 |

三条的成因都不在出问题的那条声明里，所以三条都写成**禁止**
（`GlassMaterialContrastTests` / `EventRowEntranceTests` / `CardShadowIsNotClippedTests`）
而不是「检查它生效」—— 后者根本写不出来。

⚠️ 而第三条是**用户先看见的**，不是我量出来的。它和 hover 下划线那次是同一个形状：
浅色模式下很明显，而我的验证一直在深色模式上（那批改的是深色玻璃）。
判据补一条：**改了任一个模式，两个模式都要看。**

#### 🔴 反方向：祖先的 `backdrop-filter` 会**抓住**后代的 `position: fixed`（2026-08-09）

上一节讲的是「祖先毁掉后代的 `backdrop-filter`」。同一个根因还有**反方向**，
而且它咬了两次 —— 上一节的表格里一条都没覆盖到它，所以没人往这儿看：

> **`position: fixed` 不等于「相对视口」。** 祖先只要有
> `transform` / `filter` / `contain` / `backdrop-filter` 中的任何一个，
> 那个祖先就成为后代的**包含块**，`inset: 0` 铺满的是**它**，不是视口。

⚠️ **加 `z-index` 没有用，加多大都没有用。** 这跟层叠顺序无关。

而这个项目恰好到处都是 `backdrop-filter`（深色玻璃），于是两个覆盖层都中招：

| 覆盖层 | 祖先 | 表现 |
|---|---|---|
| 改密码弹窗（`.modal`） | `.dark.has-hero .card` | 深色下被关进 Login Information 那张卡片，表单下半截被裁。**浅色模式正常**，所以报上来是「有时候」 |
| Memories 悬浮窗（`.wall-lightbox`） | `.dark.has-hero .wall` | **看起来一直是对的** —— 纯属巧合，`.wall` 恰好 `100dvh` 且满宽。把 `.wall` 临时改成 600×400，悬浮窗立刻跟着变 600×400 |

判据：**覆盖层一律 `<dialog>` + `showModal()`，进 top layer。**

top layer 的包含块永远是视口，是这个平台上唯一一个**祖先绝对够不着**的位置。
所以这不是「以后小心点别放进卡片里」—— 第二个例子已经证明那条纪律靠不住：
它错了三天，看起来一直是对的，而**调用方那一行一个字都没写错**，
错在它外面第几层有什么，那是另一个文件、另一个人、而且只在一个主题下才成立。

写法见 `core/templates/core/components/modal.html` 和 `assets/js/app.js` 的
`x-dialog` 指令。⚠️ 顺手换来的四件事：Esc 关闭、焦点关在窗口里、
关掉后焦点复位、背景 inert —— 后两件原来**根本没做**。

⚠️ **`<dialog open>` 是这一片里最尖的坑**：它把元素显示出来，但**留在原地、
不进 top layer**，也就是原样把上面的 bug 请回来 —— 而且现场看起来完全正常
（元素确实显示了），review 时看见 `<dialog>` 就过了。
开弹窗**只有 `showModal()` 一条路**，`OverlaysLiveInTheTopLayerGuardTests` 盯着它。

⚠️ 唯一的例外是侧滑菜单（`_site_menu.html`），而它是**有条件的**例外：
菜单是 `<body>` 的直接子元素，祖先只有 `<body>` 和 `<html>`。
那条条件本身也上了守卫（不许给 html / body 加上面那四个属性里的任何一个）——
一个例外的安全条件如果没被守卫盯住，**它就是个洞**。

### 原生控件：`color-scheme`（2026-08-06 加）

⚠️ `<select>` 展开后那个列表**不是网页画的，是操作系统画的** —— CSS 碰不到它的背景、
高亮和圆角，`<option>` 上设颜色在 macOS 上完全被忽略。在此之前这个项目从没设过
`color-scheme`，于是浏览器不知道页面是深色的，就让系统按浅色画那个列表：
白面板压在深色页面上。

```css
html      { color-scheme: light; }
html.dark { color-scheme: dark;  }
```

它一并管住：日期输入框的日历图标和弹出的日历、滚动条、根画布的默认底色。

⚠️ **它给不了的东西**：高亮仍然是系统强调色，圆角仍然是系统的。要完全掌控只能自绘
一整套 ARIA listbox —— 代价是手机上失去系统选择器（比任何自绘控件都好用）、
无 JS 时控件是死的、以及给 **7,079** 个选项的 `preferred_language` 再做一个带搜索的
变体。2026-08-06 定：先不做。

⚠️ 跟着 `.dark` 走，**不跟着 `prefers-color-scheme` 走** —— 主题可以被用户手动覆盖，
而 `color-scheme` 必须和页面**实际**呈现的那一套一致。首页不加 `.dark`，
所以它是 light，这是对的：那一页是照片加白字，本来就不跟随深色模式。

写模板时的规矩：**每写一个 `bg-` 或 `text-` 就当场写它的 `dark:` 对**。
留到最后统一补，等于把 20 个模板再扫一遍——这正是把深色模式排进 C2 而不是 C4 的理由。

## 三、组件

每个组件在 `core/templates/core/components/` 下有一个片段模板，
用 `{% include %}` 复用。**模板里不许手抄 class 串**——抄第二遍就会分叉。

| 组件 | 变体 | 要点 |
|---|---|---|
| 按钮 | `primary` / `secondary` / `danger` / `ghost` | 一屏**最多一个** primary。破坏性动作（取消报名、删工种、撤销授权）必须是 `danger` 且带二次确认。⚠️ 深色 + 有照片时 **secondary 和 ghost** 变玻璃；`primary` 和 `danger` 保持实心 —— 半透明会让红色取决于背后是什么，而一个警示色不能随背景改变。⚠️ 那段 CSS 故意写在 `@layer` **外面**，见下面「玻璃按钮」。<br>`disabled=True` 渲染一个灰掉、点不动、也不进 Tab 顺序的按钮（2026-08-06 加，草稿预览页在用）。⚠️ **不能和 `href` 同时给** —— `<a>` 没有 disabled 属性，不报错，渲染出来是一个看着灰、点了照样跳的链接。⚠️ 它是**展示**，不是权限：真正的拒绝永远在视图里 |
| 表单字段 | 常规 / 出错 | 错误文案在字段**下方**，不在页面顶部——顶部的错误在长表单上滚出屏幕，用户看不到自己错在哪 |
| 表格 | 常规 | 一律包在 `overflow-x-auto` 容器里。⚠️ 不包的话窄屏上**整页**横向滚动，导航跟着跑出去 |
| 卡片 | 常规 | **没有边框**（2026-08-06 改）。浅色下靠一层柔和阴影分层，深色下靠 ink-900 对 ink-950 的色差、压在照片上时靠 40% 半透明黑加一道方向性亮边。⚠️ 去线条**必须**同时加强阴影：白卡片配 ink-50 页面底几乎同色，原来那层 `0 1px 2px / 5%` 几乎看不见，只靠它卡片会消失。⚠️ `.table-wrap` **保留**边框 —— 表格的行线需要一个外框收口，但**圆角和玻璃材质跟着卡片走**：它和报表卡片在管理页上是并排的，而「同一屏两种卡片」只有把两处规则并排读才发现，代码里各自看都没问题。⚠️ 「卡片 + 彩色边」的警示框要在模板里各自显式写 `border`：Tailwind 的 `border-<色>` 只给颜色，宽度原来是 `.card` 给的，守卫在 `core.tests.BorderlessCardTests` |
| 状态标签 | 按语义色 | **必须带文字**（见上面颜色那节）。`Event.status` 和 `Participation.status` 各一套，取值直接用 `get_*_display` |
| 分类标签 | `tone="brand"` | ministry 名这类**不表示状态**的标签。⚠️ **别借语义色** —— 它原来用的是 `info`，那是随手挑的，而一旦被当成「信息」读，一个没有任何状态含义的标签就有了语气。分类归 brand（跟着照片变），状态归四个语义色（永远不变），两边不许串 |
| 空状态 | 常规 | 一句话说明 + 一个下一步动作。「暂无数据」四个字是最没用的空状态 |
| 消息提示 | 四种语义 | 对应 `messages` 框架的四档。位置固定在主内容区顶部 |
| 分页 | 常规 | 列表页超过 50 行才出现 |
| 弹窗 | 常规 | `modal.html`，全站一份。⚠️ 打开它的控件必须是**真链接**（`button.html` 的 `opens` 参数），Alpine 没加载出来时点它跳到那一页，同一件事照样做得完。遮罩上是 `click.self` —— 用 `click` 会连弹窗里的点击一起收到，于是**点输入框就把弹窗关掉了**。深色下弹窗**不透**背景照片：上面是一张要逐字读的表单，而照片里任何一块亮色都会把某一行字的对比度打穿 |
| 密码框 | 常规 | 右侧一个「看一眼」按钮，做在 `field.html` 里按 `input_type == "password"` 自动生效 —— 注册、登录、改密码三处一份实现。⚠️ 按钮必须写 `type="button"`：默认值是 submit，于是在登录页上「看一眼」等于拿半个密码去登录 |
| 只读值 | 常规 | `.readonly-value`，长得像输入框但不是 input。⚠️ 旁边**必须有一句话说去哪里改** —— 「看起来能改其实不能改」比「明显不能改」更让人困惑 |

## 三之二、活动列表的一行（2026-08-06 重做，第四版）

这一段存在的理由是它已经改过三次，而每一次改的都是同一个东西：**图片到底跟着谁**。

| 版本 | 做法 | 为什么不行 |
|---|---|---|
| 一 | 卡片跟着图（整行 `min-h-28`） | 等于改了「加图之前每个活动占多高」，矮卡片被凭空撑高 |
| 二 | 图跟着卡片的自然高度，宽度写死 96px | 卡片高度本来就有两种（有地点 110、没地点 90），所以图必然有一类不方 |
| 三 | 同上，宽度改成 110px | 只是把「不方的那一类」换成了另一类 |
| 四 | 行高**定死**，图片壳的宽和高都取**同一个** CSS 变量 | 所有卡片等高、所有图正方，而且换字体换字号都不会破 |
| 五（现在） | 同上，但图缩到 84px（行高的 75%）、垂直居中 | 「和卡片等高」改成「比卡片矮一圈」，照参考图量的比例 |

⚠️ 判据从「量出来的巧合」变成了「结构上必然」：宽和高读的是**同一个**自定义属性
（`--event-row-thumb`），所以它们不可能分叉。

🔴 而这条判据在第五版上**被绕过了一次**：缩小那一改把宽高写成了两个 `5.25rem`
字面量 —— 今天是方的，但已经退回成「两个数字碰巧一样」。它没有被任何守卫拦住，
因为当时**没有守卫**，只有这段文字。现在有了
（`core.tests.EventThumbnailIsStructurallySquareTests`），而它查的不是「是不是方的」，
是「方是不是结构保证的」。
⚠️ 记一句：这一段已经改过五次，其中三次是同一个毛病。**写下判据不等于守住判据。**

行高是**推出来的，不是量出来的** —— 这是它经得起换字体的原因：

```
卡片上下内边距  2rem
标题一行        1.75rem    text-lg 的 line-height
标题与详情间距  0.5rem
详情两行        2.5rem     text-sm 的 line-height × 2
                6.75rem  → 取 7rem 留余量
```

⚠️ Tailwind 的 `text-*` 把 `line-height` **显式**写出来了，所以这些数字和字体无关。
Jost 只改字形，不改行盒高度。

三件在浏览器里量出来才知道的事：

1. ⚠️ **模板上的 `w-16` 会压掉 CSS 里的宽度。** Tailwind 的工具类在 `utilities` 层，
   优先级高于 `components` 层 —— 第一版把窄屏尺寸留在模板上，结果宽屏下图是
   64×112。CSS 不报错，图只是不方。**尺寸的所有者只能有一个**，现在全在 app.css；
2. ⚠️ **窄屏和宽屏的高度不一样，而且必须不一样。** 窄屏活动名允许两行
   （`line-clamp-2 sm:line-clamp-1`），因为窄屏的缩略图是固定 64×64、本来就是方的，
   在那里截断只损失信息。实测 390px 下一律一行会切掉 16 个活动里 **13 个**的名字；
3. ⚠️ **窄屏也要定死高度。** 不定死的话「两行标题的卡比别人高一截」——
   那正是这次要修的毛病换了个成因（原来是 location，现在是标题）。

### 逐个入场（2026-08-06）

和菜单条目同一个节奏：**55ms 一档**，`opacity` 0→1 加上从下方 12px 升到位，**1260ms**。

⚠️ 时长是菜单那一档的三倍多，而**步长和封顶都没动**（2026-08-06 第二版）。
于是相邻卡片的动画大幅重叠：第 1 张 1.26s 才落定，第 10 张 0.495s 就开始了 ——
十张卡同时在动，读起来是一道**波**扫过去，不是十个依次排队的动作。
全部安顿完约 1.76s。

🔴 **用 `translate`，不许用 `transform`。** 这些 `<li>` 上同时挂着 `scroll-breathe`，
而滚动惯性那段 JS 每帧往它们写 `style.transform` —— 两个东西写同一个属性，
正是这份文档下面那条「两套东西不能并存」判过刑的写法。
`translate` 是**独立属性**，和 `transform` **叠加**而不是互相覆盖。
实测：入场停在起点（translate 12px）同时打上 7px 的 inline transform，
两者都在（`bothChannelsAlive`），而入场走完时元素只移动 12px、那 7px 仍在。

⚠️ 用 `animation` 不用 `transition`：菜单靠 `.is-open` 状态类驱动（会开会关），
卡片没有开关状态，要的是「一进页面就播一次」。附带好处是 HTMX 换片段时插进来的是
全新节点，动画**自动重播** —— 点了 Filter 之后卡片逐个重新浮现，读起来是
「新的结果到了」，零额外代码。

⚠️ 延迟**封顶在第 10 张**（`min(var(--i), 9)`）。一页 20 张，不封顶第 20 张要等
1.05s，而第 10 张之后本来就在屏幕外 —— 累加只会让一进页面就往下滚的人看到
一片还在淡入的空白。实测第 10 张起全部是 0.495s。

⚠️ **reduced-motion 下必须把延迟也清掉。** 这份文档开头那条全局 reduced-motion
只压 `animation-duration`，**不压 `animation-delay`** —— 只靠它的话卡片会隐身
最多半秒再瞬间出现，比原来的动画更糟。`animation: none` 是简写，会把 delay 一起复位。

整行可点用的是**铺满一层链接**，不是把整张卡包进 `<a>`：后者会把标题、badge、
时间全塞进一个链接的可访问名里，读屏念出来是一长串。代价如实说：盖了一层之后
卡片里的文字不好选中，这是所有「整块可点」写法共同的代价。

活动名的下划线：默认没有，鼠标进入**整行**时从左画进来，离开时向右滑走。
⚠️ 两个状态的 `transform-origin` 不一样，那就是「进来从左、出去向右」的全部机关；
两边写同一个 origin 的话出去的方向会反。⚠️ `:focus-within` 也要触发，
否则这个提示对键盘用户不存在。⚠️ 普通正文链接**不改** —— 段落里的链接去掉下划线
只剩颜色，那就撞上「颜色不许是唯一的信息载体」。

⚠️ **下划线必须 `bottom: 0`，不许用负偏移。** 活动名带着 `line-clamp-*`，
而那个工具类会设 `overflow: hidden` —— 放在盒子外面的东西会被裁掉、**根本画不出来**。
第一版写的是 `bottom: -0.125rem`，结果下划线从来没出现过，
而**每一个信号都说它是好的**：规则在服务端发出的样式表里、选择器命中、
计算样式报 `visibility: visible` / `height: 1px` / 颜色正确 —— 屏幕上什么都没有。
守卫在 `core.tests.HoverUnderlineTests`（它同时钉住「名字仍然是被 clamp 的那个元素」，
因为那才是这条规矩成立的前提）。

⚠️ 版心：Events / 活动详情**两页同一个值**（`max-w-4xl`）。
深色模式下背景是首页那张照片，版心顶到 1152px 时两侧几乎不剩地方。
两页必须一致 —— 少改一页，从列表点进详情时整块内容会往外一弹。
（原来是三页，Past Events 2026-08-17 删了；见下面「日程壳」那一节 ——
开日程时**版心仍然不变**，撑出去的是版心里面那一层。）

## 三之三、2026-08-06 第三批的五处版面

### 首页经文的入场

**从屏幕底边**升到位 + 由透变实，**3600ms**，出处那一行晚 600ms。

⚠️ 行程 `40vh`，两行**用同一个值**。写 `calc(14vh + 100%)` 才是「各自刚好出屏」，
但 `100%` 指元素自己的高度，而经文两三行、出处一行 —— 两者位移不同，
升的过程里行距会变，看起来像在展开而不是一起飘。

⚠️ **透明度在 95% 就走完，位移走到 100%。** 两者同时结束的话，大半段行程里字是
看不见的，「从底部升上来」那一段就白费了。

⚠️ 这个百分比比看起来更敏感，因为**缓动是分段作用的** —— 不透明度在
`0%..95%` 这一段里跑完整条 easeOutQuad 曲线，而不是线性推进。
2026-08-06 调过两次（55% → 85% → 95%），三次都实测过：

| 时间 | 位移还剩 | 95%（**定稿**） | 85% | 55% |
|---|---|---|---|---|
| 20% | 170px | 0.39 | 0.43 | 0.62 |
| 40% | 90px | 0.69 | 0.74 | 0.93 |
| 50% | 62px | 0.79 | 0.84 | 0.99 |
| 60% | 40px | 0.87 | 0.92 | 1.00 |
| 80% | 12px | 0.97 | 0.99 | 1.00 |

55% 的时候字在**一半行程**就几乎全实了，剩下的路是「已经看清的字继续挪」；
95% 让它几乎一路都在变实，最后那十几个像素才完全清晰 —— 那就是要的「从雾里出来」。

⚠️ 不透明度和位移**用的是同一条缓动曲线**，因为 `animation-timing-function`
只能整条动画设一次。真要让不透明度线性、位移缓出，得拆成两个动画（两个类）——
没做，因为分段缓动已经够用，而多一个类就多一处会和另一处不同步的地方。

⚠️ 缓动是很轻的 ease-out（easeOutQuad），不是 expo-out —— 后者把大部分位移挤在
头几百毫秒，读起来是「窜上来然后停住」。

⚠️ 40vh 是量过取的余量：813px 窗口（视口 726）下需要 33.4vh 才整块出屏。
533px 那种极矮视口上仍会露出约 19px —— 那一刻不透明度是 0，看不见。

⚠️ 用 `animation` 不是 `transition` —— 没有状态变化可以驱动 transition，
要的是「页面一出现就播一次」，而这正是两者的分界。于是刷新就重播，不需要 JS。

⚠️ `both` 填充模式不能省。少了它，元素在动画开始之前是**最终状态** ——
首帧会闪一下完整的字再跳回起点。那一闪比没有动画更糟。

⚠️ 只动 `opacity` 和 `transform`（都在合成层）。改 `top` / `margin` 会让这块字
每帧重新布局，手机上看得见卡顿。

⚠️ `prefers-reduced-motion` 下把 `opacity: 1` 和 `transform: none` **明确写回来**，
不能只写 `animation: none` —— 带 `both` 的动画关掉之后元素回到样式表里的值，
把「看得见」写成显式声明比依赖默认值可靠。

### 报表面板的出口挪到标题行

`View full report →` / `Save as PDF` 从面板底部的横条移到 `Report` 标题行最右。

⚠️ 2026-08-05 那条规矩没有变，反而更稳：**出口必须在滚动区外面**。
标题行和原来那条横条一样是 `shrink-0`，而挪上去之后离视线落点更近，还少一条分隔线。
实测 24rem 宽度下标题行 28px 高 —— 一行，右边缘齐平。

⚠️ 两个出口 `whitespace-nowrap`：面板宽度固定，`View full report →` 在 full
后面断行会读成两个链接。

实测两页差 148px。做法是把搜索框和控件行套进一个 `w-fit max-w-full` 的列包装器 ——
`fit-content` 按最宽的子元素（控件行）定宽，搜索框 `w-full` 就正好等于它。
实测两页都是「比 Clear 右边多 59px」，那 59px 正是 `Loading…` 指示器的宽度。
⚠️ `max-w-full` 不能少：`fit-content` 取 max-content，控件行不换行时比手机屏还宽。

## 四、HTMX 的用法

### 唯一一条硬规矩：写操作必须有非 JS 的路

⭐ **每一个写操作都必须有一条完整的服务端表单路径，HTMX 只是它的快路。**

完整论证在 [D24 的渐进增强口径](decisions/D24-htmx-alpine-tailwind.md#渐进增强的口径只管写操作)。
一句话：它保住了现有那 404 个直接打 URL 的端到端测试。

**读操作**（筛选、排序、展开详情）不受这条约束，可以只有 HTMX 一条路。

### 约定

- 片段模板命名 `_something.html`，和整页模板放同一目录；
- 视图靠 `request.headers.get("HX-Request")` 决定返回整页还是片段，
  **两个分支共用同一份上下文**——分叉的那天，片段上的数字就会和整页对不上；
- CSRF：在 `base.html` 上挂一次 `hx-headers`，不要每个表单各写一遍；
- `hx-confirm` 用在破坏性动作上；
- 加载态用 `hx-indicator`，**每个会等超过一瞬的操作都要有**。
  没有加载态的按钮，用户会点第二次。

### 这一批页面里，哪些真的需要 HTMX

不是每页都要上。值得的是这几处：

| 页面 | 用 HTMX 做什么 |
|---|---|
| `event_attendance` | 逐人签到 / 签退，只换那一行 |
| `event_roles` | 增删工种，只换列表 |
| `event_list` / `event_manage_list` | **实时**筛选与搜索，只换结果区 |
| `accounts/profile` | 增删紧急联系人，只换那一段 |

### 实时筛选：三条属性，各挡一个毛病（2026-08-17）

`Filter` 按钮撤掉了 —— 筛选实时之后它按不按都一样，而一颗点了什么都不变的按钮
比没有按钮更难懂：人会以为自己漏了一步。

```
hx-trigger="input delay:400ms, submit"  hx-sync="this:replace"
hx-replace-url="true"           hx-indicator="#filter-busy"
```

⚠️ 触发器写在 `<form>` 上，事件从各个输入框冒泡上来。不写在字段上 ——
字段由 `field.html` 渲染，给它加 hx 属性等于让全站所有表单都长出筛选的行为。

⚠️ 是 `input` 不是 `keyup`。`keyup` 抓不到粘贴、抓不到输入法候选词、
也抓不到 `type="search"` 那颗浏览器自带的清除按钮 —— 三种情况表现一样：
框里的字变了，列表没动。

🔴 **不许写 `changed`**。那个修饰符读的是**挂着触发器的那个元素**的 `value`，
而这里挂在 `<form>` 上，`form.value` 是 `undefined` —— 于是「值变了没」永远答
「没变」，一次请求都发不出去。不报错，筛选就是死的。

⚠️ 400ms 同样落在下拉框和日期框上（它们也发 `input`）。知情的取舍：
写成 `input, change` 两个触发器的话，选一次下拉会**发两次请求**。

⚠️ `hx-sync="this:replace"` 不能少。防抖**减少**并发但消不掉它：网慢时
「kitch」那次可能后回来，而 htmx 默认谁回来谁贴上去 —— 屏幕上是上一个字的结果，
框里是新的字，下一次敲键又自己好了，于是它读起来像「偶尔抽一下」。

⚠️ `hx-replace-url`，不是 `hx-push-url`。push 是每敲一个字（防抖之后）往历史里
塞一条 —— 搜完 "kitchen" 要按七次后退才出得去。replace 保住了「这份筛选可以被
收藏、被转发」，同时让后退键仍然是「回到我进来之前那一页」。

⚠️ 没有 JS 的那条路靠 `<noscript>` 里的一颗提交按钮。**不许改成用 CSS 或
`x-show` 藏起来** —— 那样它仍然在 DOM 和 Tab 顺序里，键盘用户会 Tab 到一颗
看不见的按钮上。

⚠️ `Clear` 和 `Generate report` 留着，它们不是筛选按钮：前者是「一下子回到全部」
（实时化之后反而更有用，四个框逐个清很烦），后者是另一件事 ——
十三个指标是十来条聚合查询，当初就是专门决定不跟着筛选实时算的。
代价如实说：出了报表再改一个日期，报表当场消失（提交按钮的 name/value
只有点它那一次才带得上）。这不是回归，是同一条规矩在新的触发频率下的样子。

其余整页刷新完全够用。**别为了用而用**——每加一个片段端点，
就多一处「整页和片段可能对不上」的地方。

## 五、Alpine 的用法

### 允许的状态，以及不允许的

Alpine 只管**纯客户端 UI 状态**：展开 / 收起、下拉开合、模态开关、
标签页选中、主题切换、表单里的条件显示（比如未成年同意那一段的显隐）。

**不许出现在 `x-` 属性里的**：

- 权限判断（`can_manage`、`is_admin` 之类）——它只能问服务端；
- 工时 / 数量 / 金额的计算——服务端已经算过，算第二遍就是第二个真相；
- 日期运算——[D16](decisions/D16-time-and-dates.md) 说「今天」只有一种写法，
  而浏览器的时区不是基金会的时区。

⚠️ **越界不会报错。** 把权限判断写进 `x-show`，页面照常渲染、测试照常绿，
只是那个按钮对不该看见它的人也画出来了。服务端仍然会 403，
所以泄露的是**信息**不是权限——但那也是泄露，而且没有任何东西会告诉你它发生了。

### 守卫

一条 grep 守卫盯着模板里的 `x-` 属性，出现上面那几类关键字就红。
它和现有那 12 条守卫一起，执行方式是两层：

1. **本地**：`.pre-commit-config.yaml`，`git commit` 时闪电跑一遍。
   有人赶进度 `--no-verify` 跳过也没关系，还有第二道；
2. **强制**：GitHub Actions 的 workflow，守卫不过**红灯，禁止合并**。

> 第 2 道才是底线。本项目的记录里反复出现同一件事：
> **只写在验收清单里的规则跨不过下一轮**——守卫测试才是机器检查。

### 约定

- `x-cloak` + 一条 `[x-cloak]{display:none}` 规则，否则用 `x-show` 的东西会在
  加载瞬间闪一下；
  ⚠️ **覆盖层不需要它**（2026-08-09 起）：`<dialog>` 不带 `open` 时 UA 样式就是
  `display: none`，降级和防闪都是自动的。见上面「覆盖层」那一条。
- 覆盖层不自己写开关，一律 `<dialog x-dialog="状态名">` —— 理由是包含块，
  不是风格，见[反方向那一节](#-反方向祖先的-backdrop-filter-会抓住后代的-position-fixed2026-08-09)；
- 状态名统一：`open` / `selected` / `theme`，不要每页起一个新名字；
- 超过五行的 `x-data` 挪进 [`assets/js/app.js`](../../assets/js/app.js) 里的一个
  `Alpine.data()` 具名组件——写在属性里的长逻辑既没有语法高亮也没法测。
  主题切换那个（`themeToggle`）就是照这条写的，可以当样板。

## 七、活动图片（2026-08-05 新增）

活动列表每一项最左边有一张方图：ministry admin 建活动时上传的那张，
没上传就用基金会的 logo。

### 布局

| | 窄屏（< 640px） | 宽屏 |
|---|---|---|
| 尺寸 | 固定 **64 × 64**（`self-start`，不拉伸） | 宽 **96px**，高 **= 卡片的自然高度**（`self-stretch`） |
| 圆角 | 14px | 22px |
| 裁切 | `object-cover` | 同左 |
| 图与卡片的间距 | `gap-6`（24px） | 同左 |

⚠️ **窄屏不拉伸。** 手机上卡片文字换行更多、更高，拉伸会得到一个 64 宽、110 高的
长条。窄屏保持正方形，宽屏保证等高。

### 圆角是量出来的，不是猜的

参考图（基金会 logo 那张烤好圆角的 600×600）里，青色方块边长 **572px**、
圆角起点在 **130px** 处 —— **22.7%**，和苹果图标那个约 22% 的比例对得上。
按宽度取整：96 × 22.5% ≈ **22px**，64 × 22.5% ≈ **14px**。

⚠️ 用 px 不用 %。宽屏上图不是正方形（96 × 90 或 96 × 110），
百分比圆角在非正方形上会变成**椭圆角**，两个角的弧度还不一样。

### ⚠️ 高度：图跟着卡片，不是卡片跟着图 —— 试了三版

**实测的卡片自然高度**：一行详情 **90px**，带地点那种 **110px** ——
本来就不一样，所以「统一一个高度」这个想法本身就是错的。

| 版本 | 做法 | 结果 |
|---|---|---|
| 一 | `aspect-square` + `self-stretch` 直接写在 `<img>` 上 | ❌ 整行被撑成 **600px 高**。浏览器先拿图片的固有尺寸算行高，方向反了 |
| 二 | 图绝对定位进 `self-stretch aspect-square` 的空壳 | ❌ 壳宽**塌成 0，图整个消失**。flex 主轴先于交叉轴解析，`aspect-ratio` 拿不到 stretch 出来的高度 |
| 三 | 方块写死 112px + 整行 `min-h-28` | ⚠️ 能看，但**把 90px 那种卡片撑到了 112** —— 改变了「加图之前每个活动占多高」 |
| 四（现行） | 壳 `self-stretch` + **写死宽度**，图 `absolute inset-0` | ✅ 高度**精确等于**卡片自然高度（实测 90/90、110/110） |

⚠️ **宽度只能写死，这是 CSS 的限制不是写法问题**：没有办法让宽度跟着
「兄弟元素决定的高度」走。96px 是取值 —— 卡片 90 时接近正方形，110 时略高。

⚠️ 那个壳**不是包着好看**：`self-stretch` + `h-auto` 让它拿到行高，
而它自己的内容高度是 0（唯一的子元素绝对定位了），所以**它不参与行高的计算**。
少了这一层就退回第一版。

### 色调：为什么要处理，处理成什么

上传的照片什么色都有 —— 一排下来五颜六色，把「简约大气」这件事直接毁掉。
所以统一压一档：

| 属性 | 浅色 | 深色 | 为什么 |
|---|---|---|---|
| `saturate` | 0.72 | 0.72 | 压掉最扎眼的那部分饱和度，但不到发灰。低于 0.6 会让食物照片看起来不新鲜 |
| `contrast` | 0.96 | 0.96 | 极轻，只是把过硬的对比收一点 |
| `opacity` | 0.94 | 0.94 | 让图稍微「沉」进页面底色，而不是浮在上面 |
| `brightness` | — | 0.88 | ⚠️ 只在深色下。为白底拍的照片放进深色页面会发光，在一排暗色卡片里格外扎眼 |

**悬停时全部还原成本色**（`filter: none`）。⚠️ 这不是装饰：降饱和是为了整页安静，
而人真的想看清那张图的时候得有办法看清。

⚠️ **这四个值是样式，写在 [`assets/app.css`](../../assets/app.css) 的 `.event-thumb` 里，
不烤进上传的图片文件。** 两个理由：

1. 烤进去等于把一个设计决定放到样式表够不到的地方 —— 违反
   [`phase-c.md` 的样式落点规矩](phase-c.md#样式的落点css-只许出现在两个地方)；
2. 看过真实照片之后这几个值多半要调，改 CSS 是一行，
   烤进去要把**所有已上传的图**重新处理一遍。

### 存储：三条约束，每一条都决定了一件事

要求是「尽量不占空间、活动结束就消失、不进任何备份」。推论：

| 要求 | 推出来的做法 |
|---|---|
| 不进任何备份 | ⚠️ **不能存数据库**。备份是 `pg_dump`，列里的东西会进每一份备份、而且永远在。存成文件 |
| 活动结束就消失 | `purge_event_images` 每天跑一次，判据是 **`end_time` 已过**，不是 `status == completed`（后者要人手动改，忘了改图就不会删） |
| 尽量不占空间 | 上传即重编码：最长边 **900px**、**WebP q82**。一张 4 MB 的手机照片变成不到 100 KB |

**900px 是从显示尺寸倒推的**，不是拍脑袋：缩略图最大约 140 CSS px，
900 给到 4 倍屏还有富余，也留了「以后可能放大显示」的余地。

⚠️ **代价说清楚**：活动结束后那张图**永久没了**。当时的往期活动列表因此**不放图位** ——
一整列一模一样的默认 logo 是噪音，不是信息。活动详情页目前也不放图（位置还没定）。

### 上传处理里三件不能省的事

1. ⚠️ **先 `exif_transpose` 再剥 EXIF。** 手机照片是把「这张是横的」记在 EXIF 里而不是
   真的转像素 —— 先剥 EXIF 的话每张竖拍照片都会**躺着**出来，而且文件完全合法，
   不报任何错；
2. ⚠️ **必须剥 EXIF，理由是隐私不是体积。** 手机照片带 GPS 坐标，
   一张在志愿者家里拍的照片会把他家地址公布给所有登录用户；
3. ⚠️ **拒绝 SVG。** 用 Pillow 打开就是校验 —— SVG 打不开，于是天然被挡在外面。
   这不是洁癖：SVG 能带脚本，而它会从本站域名提供，那是一个存储型 XSS。

## 八、公开首页（2026-08-05 新增）

决策和取舍在 [D25](decisions/D25-public-front-page.md)，这里只留写模板时要照抄的东西。

⚠️ 首页**不继承 `base.html`**，也**不跟随深色模式**。它是一张满屏照片加白字，
深色版本没有意义 —— 而如果它也切主题，顶栏那套「白字 / 深蓝字」的规则会全部翻转。

### 顶栏

| 状态 | 底 | 字 |
|---|---|---|
| 平时 | 透明 | 白，带 `text-shadow` 兜底 |
| 鼠标碰到页面上端 / `:focus-within` | 白，400ms 从虚到实 | `brand-900`，阴影去掉 |
| 窄屏（< 640px） | 始终白 | 始终 `brand-900` |

鼠标要先能碰到它才谈得上浮出来。

### 菜单面板

- 面板从左滑入，420ms，`cubic-bezier(0.32, 0.72, 0, 1)`；
- 条目逐个入场：延迟 = `160ms + 序号 × 55ms`，序号由模板的 `--i` 给，**在 CSS 里算**；
- ⚠️ 面板关着时条目必须回到初始状态，否则第二次打开是一次性全部出现 ——
  「呼吸感」只在第一次有。

**2026-08-06 改**：条目**不再写在模板里**，改由
`core.context_processors.navigation` 生成一个有序列表，模板用 `forloop.counter0`
当 `--i`。原因就是上面那个序号：管理侧现在分成两组（Ministry admin /
Foundation admin，各带一个小标题），哪一组不显示，手写的序号里就留一个洞 ——
某一项白等一拍，逐个入场看起来一顿一顿的。这件事不报错，而且只有用对的账号
打开菜单才看得见。

小标题（`.home-menu-heading`）自己带上边框和上间距，**那道线就是 admin 页面和
非 admin 页面之间的分界** —— 不另画分隔元素，两种画法并存的话某一组不显示时
会剩下一条孤零零的线。字号比链接小、字距拉开、全大写：它是**分类**，
不是可点的东西，而菜单里所有一样大的字都会被当成链接去点。

### 压在照片上的文字，对比度自己造

⚠️ 背景由基金会上传，**内容不可预知**。两层压暗：

1. 全屏 `from-black/45 via-black/15 to-black/40` —— 顶栏那几个字；
2. 下三分之二 `from-black/75 via-black/45 to-transparent`（向上）—— 经文在那里。

**实测**（拿一张带白色云团的刁难图量的）：顶栏区 **9.94:1**、经文区 **5.57:1**。

> 第一版只有第 1 层，经文中间两行直接糊掉。
> **一般形式：任何压在用户上传内容上的文字，对比度都必须由我们自己保证** ——
> 「传上来的图都挺暗的」不是一个能写进代码的前提。

## 九、滚动时的呼吸感（2026-08-05 新增）

活动列表的卡片（`/events/` 和 `/events/past/`）在进出视口时轻微位移 + 缩放，
参照 iOS Messages 的手感。类名 `.scroll-breathe`。

⚠️ **只动 `transform`。不动间距，也不动透明度。**

**不动间距**：滚动中改 `margin` 会改变页面总高度，浏览器要不断重排、
滚动位置和手指打架 —— 结果不是呼吸感，是页面在抖。
视觉上两者是同一件事，代价差一个数量级。

⚠️ **不动透明度 —— 这一条是实测出来的。** 第一版两端把 `opacity` 降到 0.35，
结果在**没有滚动条的短页面上，整个列表一打开就是灰的**：时间轴退化了，
进度直接停在 100%，也就是那一帧。而演示数据只有两场活动，**正是这种页面**。
位移停在 ±6px 肉眼看不出来（实测退化时不到 1px），透明度停在 0.35 一眼就是坏的。

⚠️ `animation-range` 只能写**一个区间**。第一版写成
`entry 0% cover 20%, cover 80% exit 100%` —— 逗号在这里的意思是
「给多个动画各配一个区间」，于是后半段被整个丢掉，**而且没有任何报错**。

实现是**纯 CSS 的滚动驱动动画**（`animation-timeline: view()`），零 JS：

- ⚠️ 整段包在 `@supports (animation-timeline: view())` 里。
  **Firefox 目前不支持** —— 那里连规则都不会应用，列表照常可用；
- ⚠️ 再包一层 `prefers-reduced-motion: no-preference`。
  这一条不能只靠 `app.css` 顶上那条全局规则：那条把 `animation-duration` 压到
  0.01ms，而滚动驱动动画的进度由滚动位置决定、**不看时长**，压不住；
- `animation-range` 只覆盖进出视口的两端，中间是静止的 ——
  全程都在动会让人晕，而且看不出是在响应滚动。

> **只有两三张卡片时几乎看不出来。** 这个效果在长列表上才明显，
> 而演示数据只有两场活动 —— 别据此判断它没生效。

## 十、深色模式的第二形态：照片背景（2026-08-05 新增）

传了首页照片之后，深色模式不再是纯黑：

| | 没传照片 | 传了照片（`<html>` 上有 `.has-hero`） |
|---|---|---|
| 页面底 | `ink-950` 实心 | 那张照片，压暗 80%，**fixed 不随内容滚动** |
| 卡片 / 表格 | `ink-900` 实心 | `rgb(0 0 0 / 0.72)` + 10px 模糊 |
| 顶栏 | `ink-900` 实心 | `rgb(0 0 0 / 0.62)` + 14px 模糊 |
| 表单控件 | `ink-800` 实心 | `rgb(0 0 0 / 0.45)` |

⚠️ **0.72 是量出来的**，不是挑好看的：它是能让正文在照片最亮的区域上仍然过
4.5:1 的最低值。实测（最亮处）：正文 **9.32:1**、链接 **5.93:1**、次要 **6.62:1**。

⚠️ **背景层在 `-z-10`，是整页一张**，不是每张卡片各自贴一块。后者会让十几张卡片
各自截取照片的一小块，滚动时那些小块跟着动，看起来像一堆各自为政的窗口。

⚠️ **浅色模式一个字不变。** 浅色下页面已经是干净的浅灰底，铺照片只会让每一段
文字都变成「压在照片上的文字」—— 那是要一处一处保证对比度的东西。

⚠️ **只用图片，从不用视频。** 每一页都解码一段视频在手机上是发烫和耗电，
而没有人在看它。

### 一张照片，谁怎么用（2026-08-13 补）

整个站只有 `HomePage.hero_image` 一个字段，也只有 `hero_focus` 一个焦点。
下面这张表说的是**行为**，而每一格的取值都来自同一处，不是三份实现：

| | 首页 | 内页 / Memories |
|---|---|---|
| 有视频 | **放视频**（`HomePage.hero` 定的，只此一处） | 仍然放图片，永不放视频 |
| 只有图片 | 放图片 | 放图片 |
| 都没有 | 退回基金会 logo | 不铺背景，退回纯 `ink-950` |
| 怎么铺 | `<img object-cover>` + `object-position` | CSS `background-image` + `background-position` |
| 裁切焦点 | `hero_focus` | `hero_focus`（同一个值） |

⚠️ 表里**唯一两处不同**（首页的 logo 兜底、img 与背景图两种铺法）是有意的：
首页不能是一块空屏，而内页拿 logo 当满幅背景就是压在文字底下的噪声。
其余每一格共用同一份取值、同一份遮罩（`_hero_scrim.html`）。

⚠️ `.has-hero` 这个 class **由 `core.context_processors` 算好**，模板只是印出来。
它原来在 `base.html` 和 `wall.html` 各写一遍 `{% if site_hero_image %}` ——
少了它，照片照画、压在上面的 62% 黑不画，整页又花又亮，**而且不报错**。撞到过一次。

## 十一、滚动惯性（2026-08-05 重做）

活动列表的卡片**滞后于滚动**，而且每张滞后得不一样多 —— 快速拖动时卡片之间的
间距看起来被拉开又合拢，松手后弹回对齐。实现在
[`assets/js/app.js`](../../assets/js/app.js) 的那段 IIFE，类名仍是 `.scroll-breathe`。

原来那版纯 CSS 的（`animation-timeline: view()`）**已整个删掉**。
它按设计工作，只是给不了要的东西：滚动驱动动画知道的是元素在视口里的**位置**，
而「拖拽的惯性」需要的是**速度**。那是那个技术的边界，不是参数没调够。

⚠️ **两套不能并存。** 它们会同时写同一个元素的 `transform`，谁最后写谁赢，
而那取决于帧的时序 —— 必然出 bug。

三个参数：

| | 值 | 为什么 |
|---|---|---|
| 位移上限 | 18px | 一次「滚到底」的滚轮事件速度可以是几千，没有上限卡片会被甩出屏幕 |
| 速度衰减 | 每帧 ×0.82 | 手指停了之后卡片还要追几帧才归位，那几帧就是惯性看起来的样子 |
| 跟随系数 | 每张 0.10–0.155，由**序号**推出 | ⚠️ 全都一样的话它们整体平移，看起来只是页面在晃。用序号不用随机：刷新之后同一张卡片行为要一致，否则每次手感都不同，像坏了 |

⚠️ 动的**始终只有 `transform`**。真改 `margin` 会让页面总高度不断变化、
滚动位置和手指打架 —— 那是抖，不是惯性。间距是**看起来**不均匀的：
相邻两张位移不同，中间那道缝就宽窄不一。视觉上没有区别。

⚠️ **循环在静止时自己停下**，并把 `transform` 清空。一个永远在跑的 rAF 循环
会让手机一直保持高频唤醒，而这整个效果只存在于手指在动的那半秒。
`prefers-reduced-motion` 下**两处都关**：JS 直接不启动，CSS 再兜一层
`transform: none`。

## 十二、图表（2026-08-05 新增）

管理列表右边那块报表面板用的（[D27](decisions/D27-ministry-report.md)）。
**没有引任何图表库** —— 五张图全部是条形图，用两个模板组件画：

| 组件 | 画什么 |
|---|---|
| `events/_bar_chart.html` | 一组横条，每条一个标签一个数字 |
| `events/_paired_bar_chart.html` | 一行两条共用一把尺子（「要几人 / 来了几人」） |

### 为什么是 CSS 的条子，不是 SVG

原方案写的是服务端渲染 SVG。真写下来发现五张图**全是条形图**，
于是 SVG 的好处一样都用不上，而 CSS 的条子反而更好：

- 继承主题色 —— `bg-brand-500` 跟着 [D26](decisions/D26-palette-from-the-hero.md)
  从首页照片推出来的色阶走，SVG 里要另外把色值灌进去；
- 自己会重排，不用管 viewBox 和媒体查询；
- 不用 ~200KB 的 Chart.js，读操作也不必依赖 JS。

⚠️ 线图、面积图、饼图这三种 CSS 画不了。**这一页也没有它们**：
时间趋势是离散的月份，用竖直的柱或横条都对；构成占比不画饼图 ——
人比较不了角度，三块以上的饼必须标数字，标了数字饼就没用了。

### 五张全是横的

包括两张按月的。这个面板在宽屏上只有半个屏，十二根竖条各 20px 宽，
底下还要塞「Aug 2026」。横过来每个标签独占一行按自然字号排，
而且**五张共用一个组件** —— 这一页上不可能出现两张长得不一样的图。

代价：按月的图变成**从上往下**读，最早的在上面。接受。

### 三条硬规矩

| 规矩 | 不遵守会怎样 |
|---|---|
| 按**最大值**缩放，不按总和 | 最长那根只画到三分之一，会被读成「占某个东西的三分之一」，而页面上没有任何东西说那是什么 |
| 少于三根**退回文字** | 一根柱子的柱状图看起来像在比较，但没有可比的对象 —— 比它替换掉的那句话更难读 |
| 数字**始终**以文字写在条子旁 | 条子是给眼睛扫的，不是唯一载体：读屏软件读不出一个 div 的宽度 |

⚠️ 宽度是**行内样式**，因为它是数据不是设计 —— Tailwind 的类名在构建时就固定了，
表达不了一个运行时算出来的百分比。⚠️ 但**百分比本身在 `services.py` 里算好**，
模板只负责画：模板里不许有算术（[D18](decisions/D18-admin-boundary.md)）。

### 颜色

| 用途 | 令牌 |
|---|---|
| 普通的条 | `bg-brand-500`（跟着照片走） |
| 条的槽 | `bg-ink-100` / 深色 `bg-ink-700` |
| 「要几人」那根（参考量） | `bg-ink-300` / 深色 `bg-ink-500` |
| 缺人的那根 | `bg-warning-fg`，配 `text-warning-fg` 的数字 |
| 唯一的风险数字（未成年无同意记录） | `text-danger-fg`，**为 0 时也画出来** |

⚠️ 缺人用 warning 不用 danger：danger 在全站的意思是「这里出问题了」，
而人手不够是一条要看的信息，不是一次事故。签到页上「No-show」那个徽章同理。

## 十三、翻页与打印（2026-08-05 新增）

### 翻页

`core/components/pagination.html`，三个活动列表共用。
每页条数在 `events/views.py` 顶上：志愿者两页 **20**（卡片带图），管理列表 **50**
（表格行矮）。

⚠️ 链接用 Django 5.1 起内置的 `{% querystring %}` —— 它**保留当前所有查询参数**、
只换 page。手写 `?page=2` 会把筛选丢掉，症状是「翻一页，筛选没了」。

⚠️ `hx-swap="outerHTML show:#event-results:top"`：换完片段把视口拉回列表顶部。
少了 `show:`，点 Next 之后人还停在上一页的半空中，看到的是新一页的中间。

⚠️ 只有一页时整个不画。「Page 1 of 1」是纯噪音。
也不画一二三四五那排页码 —— 真到了要跳第 17 页的规模，该加的是搜索。

### 打印

只服务一个页面：[完整版报表](decisions/D27-ministry-report.md#完整版报表页与-pdf)。
「Save as PDF」调的是浏览器自己的打印对话框，所以 `@media print` 里写的
**就是那份 PDF 的排版** —— 没有第二套要维护。

| 规则 | 不写会怎样 |
|---|---|
| `html, body, main` 强制白底 | 屏幕上的 ink-50 印成整页一层灰墨，费墨且难看 |
| `print-color-adjust: exact` | 浏览器默认「省」掉背景色，所有条形图变成空槽 —— 图还在，数据没了 |
| 深色模式整套复位 | 半透明黑压在照片上是屏幕设计；印出来是一张几乎全黑、字还看不清的纸 |
| `.no-print` / 顶栏 / 菜单 / messages 不印 | 纸上点不动，还占掉第一页三分之一 |
| `.report-charts { display: block; column-count: 2 }` | ⚠️ `display: block` 不能省 —— 分栏属性对 grid 容器**完全无效且不报错**，实测第一页只放下一张图 |
| `.print-break-before` | 活动清单从新的一页开始 |
| `tr, li, section { break-inside: avoid }` | 表格行和图被切在两页中间 |

⚠️ 要加新的「不该印」的东西，给它挂 `.no-print`，不要在打印块里点名 ——
点名的那份清单会和模板走散。

## 十四、飘着的羽毛（2026-08-06 新增）

公开首页和 `/events/` 两页上，一两片白羽毛缓慢飘落、被阵风吹得打转或吹高，
然后落下或半路淡出。实现在 [`assets/js/app.js`](../../assets/js/app.js) 最后那段 IIFE，
样式是 `app.css` 的 `.feather-sky` / `.feather`，标记是
`core/components/_feather_sky.html`，素材是 `core/static/core/img/feather-1..7.webp`（共 52KB）。

⚠️ **哪些页面有，写在模板里，不写在 JS 里。** 那段代码从头到尾不认得任何一个 URL，
只找 `.feather-sky` —— 加一页就是加一个 `{% templatetag openblock %} include {% templatetag closeblock %}`。

### 位置是积分出来的，这一条决定了其余全部

每片羽毛带一对速度 `vx / vy`，每帧各自往基线回落一点（`SETTLE`），风改的是速度。

⚠️ 第一版不是这样：`y` 每帧加一个固定的下落量，风只能推着羽毛横着走。
于是「把它吹高」在那个模型里**根本没有地方可落** —— 而这件事从代码上看不出来，
只有盯着页面看很久才发现「羽毛好像只会从上面下来」。
改成速度模型之后，上吹、侧吹、转圈才都变成同一件事的三个参数。

### 行为，以及一条砍掉的

| 行为 | 怎么做的 |
|---|---|
| 入场 | 上边 70%、左边 15%、右边 15%。⚠️ **不从下边进** —— 那需要一个持续的上升气流才说得通，而页面上没有任何东西暗示那件事，看起来只会像它掉反了。侧面进来的羽毛横速和入场边**一起定**：没有持续的横速，它会贴着边缘直直往下掉，读起来不是被风吹进来，是从边上漏出来了 |
| 飘（大部分时间） | 下落 16–34 px/s，横向是**两条周期不同的正弦叠加**。一条正弦是钟摆，看得出周期；两条叠起来人眼就找不到规律 |
| 微风 | 每 3–9 秒一次。推一下、转一点，两者**同号** —— 只转不推看起来是贴图在原地拧 |
| 强风 | 四面来，每次阵风检查有 40% 抽到它（2026-08-06 从 16% 提上来）。🔴 给的是**加速度**，配 sin² 包络（0 → 满 → 0，两端斜率都是 0），持续 0.9–1.8 秒 —— **不是一记瞬时的速度冲量**。理由见下面「尖角」那一节。⚠️ 方向**往上偏六成**：均匀取的话一半的强风和重力同向，那一半几乎看不出来，真正读得出「来了一阵风」的是被托上去的那一下。往下的那一半冲量减半，不减会把羽毛直接砸出下沿 —— 于是一次强风的全部表现就成了它消失了 |
| 打一个大圈 | 2–4 秒内转 1–1.6 圈，半径 42–98px，**sin² 包络**（不是 sin，见下）。⚠️ 圈是**画上去的偏移**，不是积分出来的：靠受力积分出的圆半径由速度决定，而速度这时候正被风改着，结果是条说不清的螺线 |
| 落下消失 | 三成的羽毛半路淡出，其余落到视口下沿淡出 |
| ~~停在某处~~ | 2026-08-06 砍掉。落点自己在动 —— 卡片挂着 `scroll-breathe` 每帧被写 `transform`、列表会被 HTMX 整个换掉 —— 一片「停住」的羽毛得每帧重读目标位置才不穿帮，而那是整个功能里唯一会出怪相的部分 |

⚠️ 三档风共用**同一个**到点检查，不是各自一个定时器。三个定时器意味着强风和转圈
可以同时开始，而那一下看起来不是风大，是羽毛坏了。

### 尖角：路径必须处处可导（2026-08-06）

肉眼在页面上看到过一个尖角，出在羽毛被吹起来的那一段。成因有两处，**都是数学上的**，
而且两处都不是「参数没调好」：

| 来源 | 为什么是角 |
|---|---|
| 风写成 `f.vx += mag` | 速度在**一帧之内**从 20 跳到 400。路径在那一点一阶不连续 —— 而一条一阶不连续的曲线，眼睛读出来就是一个角 |
| 转圈用 `sin(πk)` 包络 | 半径在两端是 0，**但它的导数不是**（`radius·π/dur` ≈ 111px/s 瞬间出现）。所以进圈和出圈各留一个折角 |

改法：风给**加速度**（有界 ⇒ 速度连续 ⇒ 路径处处可导），转圈换 `sin²` 包络
（两端值和导数都是 0）。⚠️ 包络必须是 `sin²`：`sin` 的导数在两端不为零，
加速度会从 0 跳到峰值 —— 比冲量温和得多，仍然是一次阶跃。

实测（45 分钟模拟，5 帧步长量速度）：**五帧内的最大速度变化 786 → 99 px/s**。
那 786 就是那一记冲量本身。

### 两条只在「被吹高」之后才存在的退场规则

| 规则 | 少了会怎样 |
|---|---|
| 被吹到视口**上方**不算走 | 按「y 超出视口」退场的话，每一记上吹都以羽毛凭空消失收尾 —— 而 `vy` 本来会自己落回基线把它送回来 |
| 左右出界只对**已经进过画面**的算数 | 从侧面进场的羽毛出生在 x ≈ -118，而摆动最多再往外拉 66px，加起来就越过了退场线 —— 它还没进来就没了。⚠️ 表现不是报错，是「从侧面来的羽毛特别少」，而那看起来只像随机数不走运 |

### 分布：实测出来的，不是估的

**验收线：平缓的时间不得低于 35%**（2026-08-06 拍板）。原来定的是「九成时间平缓」，
当天改口放宽 —— 改口留说明，见 [`revisions.md`](revisions.md#十九2026-08-06-第十批平缓的验收线从九成放宽到-35)。
现行这一档量出来 **80%**，离线还有 45 个百分点，所以三档风的概率**还有很大的上调余地**。

「1–2 片，1 片占多数」和「平缓不低于 35%」都是对**结果**的要求，而代码里能调的是
原因（出场间隔、三档风的概率、余韵长短、每片的存活时长）。中间隔了好几层，
**光看那些数说不出结果是多少**。所以把真实那段代码摘出来，在 Node 里配桩 DOM
跑了 90 分钟模拟（60fps），从 transform 流里量 —— 那也正是眼睛能看到的全部：

| 量的是什么 | 结果 |
|---|---|
| 1 片在屏幕上 | ~70% 的时间 |
| 0 片 | ~20% |
| 2 片 | ~10% |
| 平缓 | ~80% 的时间 |
| 大动作（0.5 秒净位移 >120px/s，或自转 >120°/s） | ~20% |
| 一生中被托起 >40px 的羽毛 | ~66%（中位抬升 324px） |
| 五帧内最大速度变化（折角的度量） | ~100–150px/s（冲量那版是 786） |
| 高速段的转弯半径 | 中位 562px，p1 29px |
| 入场边 | 上 ~68% / 左 ~13% / 右 ~20% |

⚠️ 「平缓」从 87% 掉到 80%，是**换成加速度模型的直接后果**，不是又调了参数：
一记冲量瞬间给完就开始衰减，而一段加速度要铺满 0.9–1.8 秒 —— 弧线本来就比折角费时间。
同一个阈值下它落在「大动作」里的帧更多，但**看起来更柔**，因为那正是尖角没了的原因。
按现行的 35% 验收线，这一档过得很宽松。

（写成约数是因为每次跑都不一样 —— 这些是分布，不是常量。跨运行稳住的是**相对
大小**，而那正是要求本身。）

⚠️ 上限硬编码为 2。这个分布不是参数调得好看，是它同时满足三件事：
1 片占多数、2 片占少数、以及**留出空档** —— 一直有东西在飘会变成背景噪音。

### 这个功能上量错了三次

调参靠的是那份 Node 模拟，而**它自己错过三次**，每次都给出一个看起来很像证据的具体数字：

| 量错的 | 表现 | 真相 |
|---|---|---|
| 「被吹高」写成「比**入场位置**高」 | 110 片里只有 2 片，像强风没生效 | 从上边进场的羽毛入场时 y≈−100，之后从 400 被托到 200 仍然远低于入场点 —— **这个指标永远为负**。改成「相对自己到过的最低点」 |
| 「大动作」按**瞬时**速度算 | 常态也超阈值 | 快的那条正弦瞬时速度就有 106px/s。改成量 0.5 秒窗口的**净位移**，来回摆动会被平均掉 |
| 折角按**逐帧**速度差算 | 报出 133–192px/s 的「阶跃」，且不随帧率变化 | 两个叠加的假象：跟踪器第一帧拿速度和 0 比，把羽毛的正常速度报成了阶跃；而 transform 写的是 `.toFixed(1)`，0.1px 在 60fps 下就是 6px/s 的速度量化、±360px/s² 的加速度噪声。改成 **5 帧步长**，噪声降约 25 倍 |

⚠️ 第三次尤其值得记：靠着那个错数字，我先后改长了阵风时长、放慢了摆动的正弦 ——
**两项后来量出来都没有可测的收益**，已经撤回。真正有用的只有「冲量改成加速度」这一条。
拿没验证过的度量去调参数，比不调更危险：它会给你一个具体的数字，而具体的数字读起来像证据。

⚠️ **改 `LOOP_CHANCE` / `STRONG_CHANCE` / `SETTLE` 必须重跑一次模拟**，
否则等于凭感觉调一个看不见的量。量过的三档：

| 概率（loop / strong） | 平缓 | 备注 |
|---|---|---|
| 0.06 / 0.10 | 94.7% | 第一版。比要的还静，而「静了一点」和「正常」长得一样，看不出来 |
| 0.10 / 0.16 | 92.5% | 对着当时的「九成平缓」调的 |
| 0.10 / 0.40 | 86.9% | 2026-08-06 拍板要更常来的强风 |

| 0.10 / 0.40 + 加速度模型 | 80% | 现行。修尖角的直接后果 |

⚠️ 现行这一档低于**当初**定的「九成时间平缓」，但当天验收线已经放宽到 **35%**，
所以它过得很宽松。换来的是 66% 的羽毛一生中被明显托起过（最早那版是 40%），
中位抬升从 143px 涨到 324px。要更静，把 `STRONG_CHANCE` 调回 0.16；
要更闹，往上调 —— 到 35% 那条线之前都还有余地，⚠️ 但每次都要重跑模拟。

### 白羽毛的真正难点是浅色模式

深色模式下背景是压暗过的照片，白羽毛本来就清楚。浅色模式下页面底是 `ink-50`、
卡片是纯白，**白羽毛几乎隐形**。

拿真实素材在三种底上渲染出来比过之后定：**只加投影，不压暗**。
压暗到 70% 确实更清楚，代价是浅色模式下它变成一片灰羽毛 —— 两个模式里就不是
同一样东西了。投影按 alpha 通道算，所以勾的是羽毛真正的轮廓，连羽枝的毛边都跟着走。
深色模式下换成更散更暗的一层：压暗过的照片上，1px 的硬边影子看不出来。

### 四条不能删的规矩

| 规矩 | 少了会怎样 |
|---|---|
| `pointer-events: none` | 这一层盖满整个视口 —— 少了它，报名按钮会时不时点不动，而那种 bug 只在羽毛飘过去的那两秒里存在，谁也复现不出来 |
| `z-index: 20` | 高过顶栏（`z-30`）或菜单（`z-40`/`z-50`）的话，羽毛会飘到导航前面。那一刻它不再像装饰，像页面坏了 |
| `aria-hidden="true"` + 每张图 `alt=""` | 这一层一个字都没有，读屏软件读到它只是打断正在读的东西 |
| 图片 URL 由模板的 `{% templatetag openblock %} static {% templatetag closeblock %}` 生成，逗号分隔进 `data-feathers` | 生产的静态文件名带内容哈希。在 JS 里按序号拼路径的话开发环境完全正常，**上线后七张图全部 404 且不报错**，表现只是羽毛再也不出现。守卫在 `core.tests.AssetPathsComeFromTemplatesGuardTests` |

### 它是「循环必须自己停下」那条规矩的唯一例外

[滚动惯性](#十一滚动惯性2026-08-05-重做)那一节写着：一个永远在跑的 rAF 循环会让手机
一直保持高频唤醒。羽毛按定义就是一直在动的，所以这条被**主动打破**了一次。
代价压到最小的三件事都不能删：

- 同时最多 2 片，且两片之间留空档；
- 一片都没有的时候用 `setTimeout` 等下一次出场，**不空转 rAF**（实测约 18% 的时间是这样）；
- ⚠️ `document.hidden` 时立刻停。少了这一条，一个开着二十个标签页的人会有二十份 rAF
  在后台跑 —— 而这件事在开发机上永远看不出来。

`prefers-reduced-motion` 下两层都关：JS 直接不启动，CSS 再兜一层 `display: none`
（不是 `visibility` —— 全屏的那一层留着不画仍然是一个合成层）。打印时也不画。

## 十五、Memories：一条等高的照片带（2026-08-06 新增，2026-08-07 按新参考图重做）

一整页：左上角一个返回，上方是标题，下方是一条**等高、自然宽度**的照片带，
缓慢向左滑，每张下面一行小字。入口是[飘着的羽毛](#十四飘着的羽毛2026-08-06-新增)，
**而且只有它**。

⚠️ **上一版整个换掉了。** 那一版是「两行反向漂移 + 标题压在正中 + 随机高度 +
按比例裁切重构」，还配了一套从旧参考图量来的常量（13.5 倍面积落差、45/35/20 的
三种构图、40% 的裁切红线）。新的设计是等高不裁切，那一整套**用不上了，
于是连代码带测试一起删掉** —— 留着不用的规则没有任何东西在检验它，
而它会以「原来这里支持这个」的样子误导下一个人。

**这一页不继承 `base.html`**，和首页同一个理由：那是应用内部的外壳（顶栏、消息区、
页脚、版心），而这一页要的是整屏的画面。⚠️ 但它**跟随深色模式**而首页不跟随，
所以主题的首帧脚本被抽成了 `core/components/_theme_boot.html` ——
它和 `app.js` 的 `themeToggle` 读同一个 `localStorage.theme`，本来就是两处要对齐的
东西，再抄第三份就是三处，而分叉的表现是「刷新一下主题就跳回去」，没有任何报错。

### 比例是从参考图上量的（2000 × 1148）

| 量的东西 | 参考图 | 落到哪 | 实测 |
|---|---|---|---|
| 照片带高度 | y 477→985 = 508px，占页高 **44%** | `--strip-h: 44dvh`（现在是**上限**，不是每张的高度） | 44.0% |
| 照片带上沿 | y 477，页高的 **41.5%** | `.wall-head { flex: 0 0 41.5% }` | 41.5% |
| 图与图的缝 | 303→305 = 2px | `gap: 14px`（2026-08-08 放宽，理由在下面） | 14px |
| 左边距 | x 137，页宽的 **6.9%** | `--wall-pad: clamp(1.25rem, 6.9vw, 9rem)` | |
| 标题字号 | —— | `clamp(0.875rem, 1.6vw, 1.5rem)` ⚠️ 2026-08-08 缩小 | 24px |
| 标题位置 | —— | 右下角，`right/bottom: --wall-pad` | 右 6.5%，下 4% |
| 标题字重 | —— | `font-weight: 200` + `+0.22em` 字距 | 200 |
| hover 时缩到 | 508 → 457px = **0.90** | `transform: scale(0.9)` | 0.90 |

⚠️ 标题是**细的、窄的**（2026-08-08：「title 不要 bold，瘦瘦窄窄的才好看」），
`font-weight: 200`。

⚠️ 同日晚些又缩小并挪到了**右下角**（「title 变小些，换到页面右下角的位置」）：
从 5.5vw 降到 1.6vw —— 它从一个标题变成了角落里的一个署名。
**字距因此从 -0.02em 反过来放到 +0.22em**：大字号靠收紧显瘦，
小字号收紧只会糊成一团，靠散开才显瘦。同一个「瘦窄」，两种做法。

⚠️ 它在 DOM 里仍然**排在照片前面**，只是被绝对定位到角落。视觉位置在右下、
阅读顺序在最前 —— 让读屏用户先听完几十张照片再听到这一页叫什么是本末倒置。
绝对定位正是让这两件事可以分开的东西。

⚠️ 标题文案仍然是那一个词 `MEMORIES`。参考图那两行字和右边那段说明是**它自己的
文案**，照抄过来等于替基金会编一段它没说过的话 —— 这个项目为「编一个看起来合理的
名字」付过一次学费（见 `base.html` 页脚那条注释）。

### 不等高、不裁切、不放大：一个统一的缩放比

2026-08-08 拍板：「照片只要在一条线上流动，中心对齐就好，不再需要任何缩放，
不再需要任何裁剪，出来的效果就按每张图原生的大小就好，不需要等高」。

每张照片画成 `带高 × --rel`，而 `--rel` 是**这张照片自己存下来的高度**除以
`GALLERY_THUMB_MAX_EDGE`（700）。因为没有一张缩略图比那个常量还高，
这个系数对页面上每一张都是同一个 —— 也就是**一个统一的缩放比**，
和第一张参考图左上角那个 `SCALE 0.10` 是同一回事。
实测：所有照片都画在自己存储尺寸的 55%。

于是尺寸差异来自**照片本身**：700×700 的画成满带高，700×389 的画成 0.56，
260×200 的画成 0.29。

> ⚠️ **这一节替代的是一个真实的 bug。** 等高的版本必须把比带子矮的照片**放大** ——
> 一张 400px 的扫描件画到 340 CSS px，在 2 倍屏上要 680 个真实像素而只有 400 个。
> 那就是「有些照片为了做成等高的照片都糊了」。现在这个系数**永远 ≤ 1**，
> 照片只会被画得比存的小，不可能糊。守卫在
> `gallery.tests.StripDrawTests.test_no_photo_is_ever_drawn_larger_than_it_is_stored`。

⚠️ `GALLERY_THUMB_MAX_EDGE` 因此**同时是存储尺寸和版面的分母**。改它会改变页面上
每一张照片的大小；调小它还会让整条带子在 2 倍屏上变糊，而那种糊**只在高分屏上出现**，
也就是不会出现在改这个数的那台机器上。

⚠️ 照片在格子里**垂直居中**，格子占满带高。所以高矮不齐的照片是「在一条线上流动」的。

⚠️ 没有 `object-fit`。容器的宽高比就是图片的宽高比，它没有任何东西可做，
而留着它会让人以为这里存在裁切。

⚠️ `width_ratio`（跑马灯算时长用的那个）**不再等于宽高比**。等高的时候两者
恰好是同一个数，现在不是了 —— 用错会让带子按照片的大小差异跑偏速度。

### 圆角、投影，以及缝为什么从 2px 放宽到 14px

2026-08-08：「每张照片都带一点圆角，来点悬浮感」。`border-radius: 0.5rem`
加一层很淡的投影。

⚠️ 圆角给的是 `<img>` **不是外面那个格子**。格子是满带高的，照片在里面居中，
圆在格子上会在照片上下各画出一段没有东西可圆的弧。

⚠️ 深色模式要自己的一套：黑投影压在纯黑页面上什么都不是。那边换成一圈极淡的白边
（`0 0 0 1px rgb(255 255 255 / 0.10)`），起的是同一个作用 —— 把照片从背景里托起来。

⚠️ 缝从 2px 放宽到 14px。2px 那条「很细很细的分割线」是配**齐平贴边**的照片的 ——
那时候相邻两张严丝合缝，细缝就是分界。现在每张有圆角、有投影、高矮还不一样，
2px 会让相邻的圆角几乎咬在一起、两张的投影互相糊进对方，「悬浮感」正好被这一点
空间不足抵消掉。**圆角、投影、缝宽是一套**：要退回 2px，另外两个也得一起去掉。

### 横缝和竖缝是同一个值（2026-08-08）

拍板：「每个带子图片高度占满的时候，中间的距离和同一带子两张照片的距离一样」。
所以 `--photo-gap` 一个属性同时喂给 `.wall-track / .wall-set` 的横向 gap
和 `.wall-strips` 的纵向 gap。

⚠️ 写成两个碰巧相等的数字也能达到今天的效果，但**改横缝的人不会想到去改竖缝**，
而那时候这条等式已经悄悄不成立了 —— 没有任何东西会说一声。

⚠️ 实际看到的竖缝**通常比 14px 大，而且每一对都不一样**：照片在带高里是垂直居中的，
而大部分照片填不满带高，所以真实间距是
`14px + 上面那张的下留白 + 下面那张的上留白`。
只有上下两张都正好填满带高时才正好是 14px —— 这正是拍板那句话里的条件。
这是**等高居中**换来的，不是没对齐。

⚠️ `.wall-track` 和 `.wall-set` **必须是同一个值**，否则两份之间的缝比份内的宽，
接缝处每一轮会顿挫一次，很难指认。写成一条规则就是为了这个。

### hover：缩一圈，并且慢很多很多倍

两件事，两套机制，而**把它们弄混就是这一节存在的理由**：

| | 做什么 | 靠什么 | 挂在哪 |
|---|---|---|---|
| hover | 这一张缩到 0.90 | CSS `transform` | 每张照片（`:hover`） |
| hover | 整条带子慢到 **1/2.5** | Web Animations 的 `playbackRate` | 整条带子 |
| 打开悬浮窗 | 整条带子**停住** | `animation-play-state` | 轨道 |

⚠️ **减速不能靠改 `animation-duration`。** 浏览器会按新时长重算「当前播到哪儿了」，
同一个进度百分比对应的位置变了，带子会在鼠标进来的那一瞬间跳一大段。
`updatePlaybackRate()` 是专门为这件事设计的：下一帧平滑接管，位置不动，只有速度变。

⚠️ **减速挂在整条带子上，不是逐张照片上。** 逐张挂的话，指针每越过一条 2px 的缝
就会连着触发 leave + enter，速度一抖一抖 —— 而那条缝只有 2px，谁也瞄不准。
缩小是逐张的，减速是整条的，这正好就是参考图里的行为。

⚠️ **1/2.5，而且下限比上限更重要**（2026-08-08 从 1/20 改上来）。
两头都是实测反馈：一开始要的是「慢很多很多倍」，做成 1/20 之后的反馈是
「慢到我以为带子都停了」。

而「停下来」是**悬浮窗在做的另一件事**（`animation-play-state`）。慢到看不出在动，
就等于把那个状态偷走了 —— 打开悬浮窗那一下就再没有任何反馈。
所以这个数有下限，守卫在 `test_the_hover_slowdown_stays_visibly_in_motion`，
它断言的是 `0.2 ≤ rate < 1`，两头都写着理由。

⚠️ 这个数**只在 `app.js` 一处**。CSS 里一度还有一个 `--wall-linger`，
没有任何东西读它 —— 同一个数字的第二个家，迟早和真的那个对不上，
而且被人改到的往往是死的那个。

### 条带上没有图注（2026-08-08）

拍板：「每个图不要带标签了」。照片下面那行 `ministry · 年份` 整个去掉了，
条带上只有照片。

⚠️ 但每个按钮**还留着一个 `sr-only` 的名字**。图是 `alt=""`，所以少了它，
读屏软件会念出六十个「按钮、按钮、按钮」，彼此没有任何区别。
那行字在屏幕上一个像素都不占。

⚠️ 那一行**在悬浮窗里还在**（点开之后照片下方）。「每个图带的标签」和
「点开之后的说明」是两件事，后者是 2026-08-06 单独定的。

⚠️ 顺带记一个已经不在了、但下一个人会再撞到的坑：图注当初是
`position: absolute; top: 100%` 挂在照片下面的，而 `.wall-strip` 的
`overflow: hidden` 是**两个方向一起**的 —— CSS 不允许一轴 hidden 另一轴 visible，
另一轴会被强制成 auto。所以那时候这一层必须比照片高出一条 `--caption-h`，
否则图注被整齐地裁掉，而**页面看起来完全正常，只是一行字都没有**。
现在没有图注了，这一层就是 `--strip-h`。往这条带子里加任何**超出照片**的东西之前，
先读这一段。

### 三条带子（2026-08-08：「同样的原理，再来两条照片带子」）

三条同速、同向、同一套规则，模板是同一份 `_wall_strip.html`。
⚠️ 三条各抄一份的话，改 hover、改 lazy 的规则、改接缝的份数都得记得改三处，
而漏掉一处不会报错 —— 表现只是其中一条的行为和另外两条不一样。

| 规矩 | 少了会怎样 |
|---|---|
| 60 张**分**给三条，不是每条 60 张 | 三条各 60 张是 180 张照片、算上接缝副本 360 个 `<img>` —— 笔记本上要卡一下才稳住，手机上直接不能用 |
| 一张照片只在**一条**带子上 | 一份 id 列表切三段就保证了。同一张出现在两条上，读起来是「我刚才是不是看过」 |
| 照片不够时**少给几条**，不是给空带子 | 一条空带子是一道看起来像加载失败的空白横杠，而「照片不够」正是基金会刚开始用的状态 |
| ⚠️ 三条的起始相位要**错开** | 三条同速同向，不错开的话每条都以一张贴着左边缘的照片开场，三条读起来是一整块在滑 |

错相位靠一个**负的** `animation-delay`（`--strip-index × -0.37 × 时长`）——
负值是「从中途开始播」，不是「延迟开始」。⚠️ 系数取 0.37 而不是 1/3：
用 1/3 的话三条的相位每一轮会重新对齐一次。

⚠️ **减速要认准是哪一条。** Alpine 的 `x-ref` 在同名多次出现时只留最后一个，
所以三条都写 `x-ref="track"` 的话，鼠标停在第一条上会去减第三条的速 ——
而那个 bug 的表现是「减速有时候有效有时候没效」，最难查的那一种。
`linger()` 因此接收被 hover 的那个元素，在它自己里面找轨道。

### 无缝循环，以及照片很少的时候

轨道里放 N 份一模一样的照片，整体平移 `-100% / N` —— 正好是一份的宽度，
所以下一份接上来那一帧和这一份的开头逐像素相同。

⚠️ **N 至少是 2，照片少的时候更多。** 一份如果比窗口还窄，平移到头时会有一条空白
横穿页面 —— 而「照片很少」正是基金会刚开始用的状态，也就是这个问题最容易出现、
最不该出现的时候。判据在 `MIN_STRIP_SPAN`，算法在 `repeats_for()`。
⚠️ 所以 keyframes 里**不能写死 `-50%`**：写死的话 N=3 时每轮会跳过半份内容。

⚠️ **速度写在样式里，时长由服务端算。** `--wall-speed` 是「一个带高单位走完要几秒」，
服务端把这条带子的总宽写成 `--wall-span`，两者相乘才是动画时长。写死总时长的话，
**照片越多跑得越快** —— 基金会每加一批照片，这一页就更急躁一点。

⚠️ **正本的图不 lazy，克隆的才 lazy。** 这条带子不是被滚动的，是被 `transform`
平移的，懒加载在这种情况下触发得不可靠 —— 表现是照片以空白的样子滑进视口。

⚠️ `.wall-track` 上**故意没有** `will-change: transform`。这条轨道满载时上万像素宽，
而它的动画从打开就在跑、永远不停 —— 浏览器无论如何都会在第一帧把它交给合成器，
`will-change` 买不到任何东西，只是让一大块常驻显存的提示多挂一份。

那条 bar 在深色下有**两副样子**，取决于基金会传没传首页大图，所以这一页也写两条：

⚠️ **抄一条不抄另一条的表现是「有的部署上对，有的部署上不对」**，而两种部署都不报错。

⚠️ 这一页不继承 `base.html`，所以那张首页大图的图层要**自己再写一遍**

代价照旧存在（半透明黑压在一张照片上，暗部会带上背景的调子）——
2026-08-08 知情选择了和全站一致，而不是这一页单独干净。

### 每天换一批，同一天不动

一天从全部照片里抽 60 张（`STRIP_SIZE`）。种子是**当天的日期字符串**。

| 规矩 | 少了会怎样 |
|---|---|
| 按日期播种，不是每次请求重抽 | 刷新一下、或者从悬浮窗退回来，整条带子重排一次 —— 那读起来是 bug 不是变化 |
| ⚠️ 用 `Random("...")`，**绝不用 `hash()`** | Python 每个进程给字符串哈希加盐，于是两个 web worker 会给出两条不同的带子，而且哪里都复现不了 |
| 60 张是**页面**的上限，不是保管的上限 | 老照片一张不删，只是今天没上墙。不设上限的话，页面会一直好用到某一天忽然不好用 |

### 悬浮窗

不复用 `core/components/modal.html`。那个是「一张卡片里放一段表单」——
有内边距、标题行、白底，每一件事都在跟一张浮在暗底上的照片作对。
共用的只有 Esc 关闭和点遮罩关闭这两条**交互约定**，那是约定，不是可以共用的 DOM。

- 左右翻走的是**一条环形序列**，走完整条带子；
- `←` `→` `Esc`，Tab 关在窗口里，打开时焦点送到关闭按钮，关掉时**送回原来那张照片**；
- 照片下一行小字：`Food Pantry · 2019`。⚠️ 年份从 EXIF 读，**必须在重编码之前读** ——
  重编码就是元数据消失的那一刻。⚠️ 扫描件带的是扫描日期不是拍摄日期，这条治不了；
- 打开时带子停住。不停的话，关掉窗口回到页面上，刚才点的那张已经走到别处去了。

⚠️ 序列走 `json_script`，不手拼 `<script>`。里面有一半是管理员填的 ministry 名字。

### 上传：一次十张，重复的不收

- 一次最多 `MAX_PHOTOS_PER_UPLOAD = 10` 张。⚠️ 这是对**一次请求**的上限，不是对
  收藏量的：十张手机照片是三五十 MB 加十次重编码；一百张会把请求跑超时，
  而管理员只会看到一个浏览器错误页，不知道哪几张进去了。超过十张**整批拒绝** ——
  取前十张、剩下的悄悄扔掉更糟；
- 重复靠 `GalleryPhoto.image_digest`（重编码后大图的 SHA-256，全库唯一）。
  ⚠️ 哈希取的是**重编码之后**的文件 —— 同一张照片一次发 JPEG 一次发 PNG，
  进去是不同的字节，出来是一模一样的，而那正是重复在现实里的来法；
- ⚠️ 它只认字节相同的图：重新裁过、换质量存过、截图，都会进去。
  说清楚是因为「查重」听起来管的比它实际管的多；
- 跳过的那几张**要报名字**。一批十张悄悄变成八张，人会重传那两张、看不到反应、
  然后断定页面坏了；
- ⚠️ 重编码在 `clean` 里做完才写库。反过来的话，一批十张里第九张是 PDF，
  前八张已经存进去了。

### 无障碍：这一页有代价，而且是知情的

进这一页的路只有飘着的羽毛一条（2026-08-07 拿掉了顶栏那枚静止的）。
而那一层是 `aria-hidden`、键盘到不了，`prefers-reduced-motion` 下更是整层
`display: none`。所以：

> 键盘用户、读屏用户、开了减少动效的人**进不去** Memories，也不会知道它存在。

这是拍板，不是待修的缺口。守卫在 `gallery.tests.FeatherEntranceTests`，
而且是**朝着「不该有那个链接」的方向**断言的 —— 免得哪天被人当成漏掉的链接补回来。

⚠️ 减少动效下带子改成可以横向手推，克隆藏起来，hover 的缩放也一起关掉。
动画停掉之后必须给一条别的路看完整条带子，否则这些人只能看到第一屏那几张 ——
那不是「少了个动效」，是内容没了。

## 十六、菜单面板的深色档（2026-08-08 补）

菜单在此之前只有一个写死的 `bg-white`，于是深色模式下它是一整块白的。
底色改成 `--color-ink-900` —— **和吸顶 bar 的深色档是同一个值**
（`.home-bar.is-solid` 用的也是它），拍板口径是「菜单化开的是那条 bar」。

⚠️ **底色一变，跟着要有深色档的一共五处**，漏掉任何一处的表现都是
「深色下这一块看不清」，而不会报错：

| 哪一处 | 深色档 | 漏了会怎样 |
|---|---|---|
| 面板底 | `.dark .home-menu` / `.dark.has-hero .home-menu`（**在样式表里**，见下） | 一整块白 |
| 关闭按钮 | `dark:text-ink-300` | 深底上的深灰字 |
| 链接 | `dark:text-ink-100` | 同上，而这是全站唯一的导航 |
| 链接的下边线 | `dark:border-ink-700` | 一排很亮的横线，比字还显眼 |
| 小标题 + 它的上边框 | `.dark .home-menu-heading` | 那道分界线亮得像画错了 |

⚠️ 文字那几档**不是重挑的**，是照搬内页深色已经在用的那一对：`base.html` 的页脚就是
`ink-900` 底配 `ink-300` 字。对比度是量过的，不该在这里重新猜一个。

### 面板底色：抄的是 bar 的两副样子，而且必须写在样式表里

⚠️ **第一版只抄了 `ink-900` 那一档，结果是面板泛蓝。** `--color-ink-*` 是一条
**固定的冷灰阶**，只有 `--color-brand-*` 跟着首页照片走 —— 所以 ink-900 永远带蓝调，
主题色是紫的也一样。而同一个部署上的那条 bar（有首页大图）是中性黑玻璃，
两块放在一起看就是「菜单发蓝」。用户原话：「现在的主题色是紫色，
但是深色模式下的 menu 面板竟然泛蓝光」。

所以和 Memories 那一页同一个口径 —— **两副都抄**：

| 情况 | 吸顶 bar | 菜单面板 |
|---|---|---|
| 没传首页大图 | 实心 `--color-ink-900` | `.dark .home-menu` 同值 |
| 传了 | `rgb(0 0 0 / 0.62)` + `blur(14px)` | `.dark.has-hero .home-menu` 同值 |

⚠️ 🔴 **底色四种状态全部写在样式表里，标签上一个 `bg-` 都不许有。**
Tailwind 的工具类在 `@layer utilities`，**层的优先级高于选择器具体度** ——
留一个 `bg-white` 在标签上，`.dark.has-hero .home-menu` 再具体也盖不过它。
而失败的样子不是「没样式」，是**白底 + 已经改成浅色的字**，
也就是全站唯一那套导航几乎读不出来。同一个坑 `button.html` 那边也记着。
守卫：`core.tests.SiteMenuShapeTests.test_the_menu_panel_has_a_dark_pair_for_everything_it_paints`。

⚠️ **首页不需要任何例外，而且是自动的。** 首页永远不带 `.dark`（满屏照片配白字，
不跟随深色模式），所以上面每一个 `dark:` 档在那边一次都不会命中，
菜单在首页照旧是白的。这一条写下来是因为它看起来像漏掉了。

### Admin Site 开新标签页

菜单里**唯一**带 `target="_blank"` 的一条，因为它是唯一一个离开这套界面的入口。
理由：人打开 Django admin 往往是**在做别的事的中途**去查一条记录，
覆盖当前标签页就把那件事丢了，而回来的路是浏览器的后退键 ——
穿过一个可能是 POST 的页面。

⚠️ 其余条目一律不给。它们都是站内页面，逐个开新标签页只会攒出一堆；
而且一个和邻居行为不同、又看不出为什么不同的链接，比两种行为里的任何一种都糟。

⚠️ 一起给 `rel="noopener"`。同源下威胁不大，但成本是零，
而「什么时候还算同源」是以后可能变的（比如 admin 哪天挪到子域名上）。

## 十七、日程壳：Events 页让位给日程（2026-08-17 新增）

筛选卡上多一颗 `Schedule`。按下去，整列活动往左让，右侧腾出来的地方给日程。

⚠️ 这一节讲的是**房间**（面板多宽、多高、钉在哪儿）。房间里那份日历
2026-08-18 画上了，见[第十八节](#十八日程本身2026-08-18-新增)；当时那个
虚线占位框、以及 app.js 里那段实测宽×高的读数，一起删了 —— 它们的全部用途
是量这间房。

### 让位的做法：撑宽外壳，不是推走卡片

壳是居中的，宽度一变大，它的左边缘**自然**往左走 ——
于是标题、筛选卡、每一张卡片**一起挪，相对关系一点没变**。

给每张卡片加 `translateX` 是行不通的，两个原因，各自都足够：
滚动惯性那段 JS 每一帧都在往这些 `<li>` 上写 `transform`
（[十一](#十一滚动惯性2026-08-05-重做)判过刑的写法）；
而且标题和筛选卡不会跟着走，读起来是「卡片跑了、外壳留在原地」。

### 🔴 版心不动，撑出去的是版心里面那一层

`<main>` 的 `max-w-4xl` 一动不动，`.events-shell` 靠**对称的负外边距**探出它两侧。

不去换 `main` 的 max-width，是因为那有两条路，两条都要别人替这一页背账：
把 `main_width` 做成跟着 Alpine 状态变的 class（全站共用的外壳为一页加一个全局
状态），或者让 JS 去改 `<main>`。而且 `#messages` 也是 `main` 的直接子元素 ——
跟着变宽之后提示条会比正文宽一截。

### 🔴 两个宽度都由媒体查询给，一个 `vw` 都不许有

`100vw` **含竖滚动条的宽度**，而媒体查询不含。所以
`min(78rem, calc(100vw - 2rem))` 这种写法在刚好卡在边界的视口上会横向溢出
十几个像素 —— 表现是整页可以左右拖动，看起来像某张卡片坏了，而不像一个宽度。
这个坑[筛选卡那一行](#筛选卡里的搜索框)已经踩过一次。

媒体查询里的数字**保证了余量**，所以里面写死 rem 就够，不必再 `min()` 一次。
守卫：`core.tests.ScheduleShellTests.test_the_open_widths_never_come_from_vw`。

⚠️ 代价如实写：只有两档，所以 80rem 以上的屏幕越宽、两侧白得越多。
拿它换掉的是「整页能左右拖」这一类不报错的 bug。

### 几何

| 视口 | 壳宽 | 每侧负外边距 | 列宽 | 日程宽 |
|---|---|---|---|---|
| ≥ 80rem | 78rem | (54−78)/2 = −12rem | 34rem | 42.5rem（680） |
| 64–80rem | 62rem | (54−62)/2 = −4rem | 34rem | 26.5rem（424） |
| < 64rem | 54rem | 0 | 列表整个藏起来 | 满宽 |

54rem（864）是版心内容宽，也就是 `max-w-4xl` 减掉 `px-4`。
1440px 上就是：**整体左移 192px，卡片 756 → 436，右侧空出 680**。

⚠️ **一行里两道竖缝都是 24px**（图↔卡片的 `gap-6`，列↔日程的 `gap: 1.5rem`）。
后者 2026-08-17 从 2rem 改成 1.5rem 跟前者对齐 —— 两道缝不一样宽时，日程看起来
离得更远，读成了另一个区域而不是并排的第三块。
⚠️ 日程宽 = 壳宽 − 34rem − **1.5rem**，表里那两个数是这么来的；那道缝一改，
两个数都得跟着改。

⚠️ 列宽 34rem 是**定死的**，不跟着壳变。多出来的地方全部归日程 ——
卡片再宽回去就等于把这次收窄白做了。

⚠️ 34rem = 缩略图 84 + 间距 24 + 卡片 436，**三个数加出来的，而只有卡片可以动**
（2026-08-17 定）。少了这条，下一次「卡片再窄一点」会从缩略图身上找 ——
而缩略图一小，那张正方形图就不再是这一行的锚点了。

🔴 **34rem 有一个算得出来的下限，而下限不在版面里，在内容里。**
卡片 = 34rem − 缩略图 5.25rem − 间距 1.5rem = 436px，去掉左右各 1rem 的内边距，
正文可用 **404px**。而时间那一行
（`Aug. 18, 2026, 4:39 p.m. – Aug. 18, 2026, 7:39 p.m.`）在 text-sm 下约
360–380px，月份名长的时候更宽。行高定死 7rem、`.card` 上有 `overflow: hidden` ——
那一行一旦折行，**被裁掉的不是它自己，是下面的地点**。不报错，地点就是没了。
所以再往下收之前得先把时间的写法改短（同一天不重复写日期），
而那是改**内容**、要另外拍板的事。

⚠️ **80rem 以上不再加档**（2026-08-17 定）：更宽的屏幕上两侧留白更多，
日程仍是 42.5rem。曾经加过一串 8rem 一档、一直到 160rem 的阶梯，当天撤掉了。

⚠️ 窄于 64rem 时列表 `display: none`、日程占满，**不是并排**。1024 以下并排的话
日程只剩一百多像素 —— 那不是「窄了一点」，那是画不出一天。

⚠️ 标题在壳里、在那一行**外面**：窄屏藏起来的是「列」，标题放在列里会跟着消失。

🔴 **两端的 `flex-basis` 都必须是长度。** 列的静息态写 `0 0 100%` 而不是
`1 1 auto` —— `auto` **不可插值**，浏览器不报错，它只是**不过渡**：第 0 帧卡片
就已经收到 436 了，然后外壳才慢慢往左滑，而 CSS 里每一条都写着 560ms。

### 🔴 日程的高度是一屏，不是列表的高度

flex 默认拉伸，二十场活动的列表会拉出一块两三屏高的日历 —— 而日历是「一天/一周
正好一页」的东西，拉长它只是把格子变成空白。所以：

```
align-self: flex-start;                              /* 不拉伸 */
position: sticky;  top: calc(var(--top-bar-h) + 1rem);
height: calc(100svh - var(--top-bar-h) - 2rem);      /* 前一行留 100vh 兜底 */
```

左边的活动照常往下滚，滚到下一页活动，右边这一页还在原地。

⚠️ **三条缺一不可，而少任何一条都不报错**：少了 `sticky`，日历跟着卡片滚走；
少了显式高度，flex 项被 stretch 拉成整行高 —— 和包含块一样高的元素没有可粘的
行程，`sticky` 看起来像没写；少了 `align-self: flex-start`，stretch 盖掉高度，同上。

⚠️ `top` 必须**让开吸顶的导航栏**。`top: 0` 会把面板顶上那一截塞到白色 bar
底下，而日历上那一截正好是写星期几的一行。
`--top-bar-h` 是**推出来的**：bar 里 `text-sm`（行高 1.25rem）配 `py-4` /
`sm:py-5`，即 52px / 60px。两个文件之间没有任何东西连着它们，所以
`ScheduleShellTests.test_the_top_bar_is_still_the_height_this_assumes` 钉着
那两个工具类 —— 改了 bar 的内边距，这里就差那么多，而屏幕上只是日历顶上被切掉一条。

⚠️ `svh` 不是 `dvh`。手机地址栏一伸一缩，`dvh` 会让面板每滚一下重算一次高度，
连那行尺寸读数一起跳。`svh` 取「地址栏展开」那一档，于是它在任何时刻都装得下；
代价是地址栏收起来时底下多一条空白。

⚠️ 装不下的内容归**日历自己**滚（2026-08-18 落到 `.schedule-scroll` 上）。
不要把面板改成 `overflow: auto`：那会让整块日历带一条自己的滚动条，而
「正好一页」的意思就是不该有那条 —— 而且星期那一行会跟着滚走，于是一屏格子
说不出自己是哪一天。

### 关着的时候必须逐像素等于改之前

`.events-shell` 的静息状态只有 `width: 100%`，没有自己的宽度、没有外边距 ——
版心是什么样，它就是什么样。没按过按钮的人看到的就是这一档，而它是全站最常
打开的一页：在这里顺手改一点点，等于拿所有人的默认视图去换一个没人要求默认
打开的功能。守卫：`ScheduleShellTests.test_the_closed_shell_is_exactly_the_page_it_replaced`
（它同时钉着「负外边距不许出现在静息态上」）。

⚠️ 这也是「关着时和活动详情页同宽」的来源：两页都是 `max-w-4xl`，而壳在关着时
不改变任何东西。有了这一条，从列表点进详情才不会弹一下。

### 面板收起时是 `visibility: hidden`，不只是宽度为 0

宽度为 0 的东西**仍然在无障碍树和 Tab 顺序里** —— 日历上将来那些按钮会变成
一串按不到也看不见的焦点。`visibility` 可以过渡（顶栏菜单也是这么写的），
所以它不会让面板在动画开始之前就消失。

### 状态挂在壳上，不在筛选卡上，也不在结果区里

HTMX 的筛选和翻页换掉的是 `#event-results`。状态声明在被换掉的那块里，
等于每筛一次、每翻一页日程自己关一次 —— 而这件事**只在真站上发生**，
读第一次渲染的单元测试永远看不到。
守卫：`events.tests.ScheduleToggleTests`（状态和面板都必须在片段外面）。

### 按钮：`toggles`，而且强制 `type="button"`

`button.html` 多了一个 `toggles` 参数（翻转一个 Alpine 布尔，
当前状态写进 `aria-pressed`）。它**强制** `type="button"`，不接受调用方传别的：
这类开关几乎总是长在表单里，而默认的 `submit` 会让「点一下开关」变成
「提交一次筛选」—— 整页重来、状态归零，屏幕上读起来是「这按钮点了没反应」。

⚠️ 和 `opens` 不同：那个必须配一个真实的 `href`，因为它开的是一个有对应页面的东西。
日程是就地改版面的纯 UI 状态，没有对应的 URL。代价如实说：
Alpine 没加载出来时它是个死按钮 —— 和菜单那颗 `Menu` 同性质，不违反 D24，
D24 要求有服务端路径的是**写操作**。

### 减少动效下不是关掉功能

只把那 560ms 的行程去掉，让位本身瞬间发生。腾地方是版面，不是装饰；
一个开了减少动效的人照样要看日程。

## 十八、日程本身（2026-08-18 新增）

[第十七节](#十七日程壳events-页让位给日程2026-08-17-新增)腾出来的房间，这一节是
住进去的东西。占位框和 app.js 里那段尺寸读数一起删了。

```
.schedule                 一列 flex
  .schedule-nav             [‹] Aug 18 – Aug 21 [›]   ← 三对，CSS 只放出一对
  .schedule-head            空格 + 星期几             ← 在滚动区外面
  .schedule-scroll          ← 滚的是这一层
    .schedule-grid          高 24 × 48px = 1152px
      .schedule-gutter        整点刻度
      .schedule-col × 4       格线、卡片、红线
```

### 定下来的十条

| | 定下来的 |
|---|---|
| 时间轴 | 全天 `12am – 11:59pm`，**48px/小时**，一天 1152px |
| 装不下 | `.schedule-scroll` 内部滚。面板仍是一屏、仍 `overflow: hidden` |
| 打开时滚到哪 | **7am 打底，「现在」是下限**（2026-08-18 改）。7am–6pm = 528px，正好是 900px 窗口上的一屏 |
| 翻页 | 一次翻「那一档看得见的天数」，左箭头到 `max(今天, 筛选的 From)` 为止置灰 |
| 数据 | 那几天的**全部**可见活动。跟搜索/日期/事工筛选，**不跟分页** |
| 颜色 | 24 格浅色盘，由 `pk` 的 crc32 定色，撞上邻居时往后顺延。**两个模式同一套色值** |
| 重叠 | 完全和部分一律往右下偏，一档 8px，封顶 3 档 |
| 已取消 | 灰底 + 标题删线，不占彩色盘 |
| 已结束 | `opacity: 0.5` |
| 今天 | 整列一层 7% 的主题色，星期那一格用主题色 |

### 🔴 一次翻几天 = 那一档看得见几列

服务端永远画四列，CSS 按档藏掉尾巴：

| 视口 | 日程宽 | 看得见 | 每列 |
|---|---|---|---|
| ≥ 80rem | 42.5rem（680） | 4 天 | ~160px |
| 64–80rem | 26.5rem（424） | 2 天 | ~192px |
| < 64rem | 满宽 | 3 天 | 视屏而定 |

⚠️ 中间那档如果也放四列，一列 96px —— 活动名基本只剩一两个字就截断。
手机那档日程是**满宽**的，所以反而比中间那档宽，能放三列（和参考图的手机版一样）。

于是箭头有**三对**，目标日期各不相同、由服务端算好，CSS 只放出一对。
换掉的是「让 JS 去 `+4 天`」—— 那条路上算出来的日期没有任何测试看得见，
而算错一天的表现是「按一下跳过了一天」，不会有人报上来。

⚠️ 列数**写死在每个断点里**，不写 `repeat(var(--n), …)`：`repeat()` 的次数不接受
自定义属性代换，写了不报错，整条 `grid-template-columns` 失效，四列叠成一列。

⚠️ 星期行和格子行**共用** `--schedule-gutter` 和同一套列，否则表头和格子对不齐。

### 🔴 每小时多少像素，存在三份

`48` 在 Python 里算卡片的 `top` / `height`，在 CSS 里画格线（`--schedule-hour`），
在 JS 里摆红线。三者之间没有任何东西连着，对不上的表现是**每张卡都和它自己的
时间差半格** —— 而在一天只有一场活动的开发数据上看不出来。
JS 从 CSS 变量里读，少一份手抄；剩下两份由
`events.tests.ScheduleGeometryGuardTests` 钉着。

同一条守卫钉着 24 格颜色盘的条数（`schedule.PALETTE` ↔ `--schedule-fill-N` ↔
`.schedule-card--N`）：少一格，尾巴上那个颜色落到兜底值（一张灰卡混在彩色里）；
多一格，那个变量根本没定义 —— 而 CSS 对未定义的变量不报错，它渲染成一张**透明**的卡。

### 颜色：固定，但可能挪一格

本命色 = `crc32(pk) % 24`，撞上「画面上挨着」的卡（框上下相差不到 8px，或直接
相交）时从本命色往后顺延。

⚠️ **不能用内置的 `hash()`** —— 它对 str 加了每进程的随机盐，同一场活动在两个
gunicorn worker 上是两个颜色。本机单进程跑起来一切正常，测试也全绿。

⚠️ 代价如实写：邻居变了，同一场活动的颜色**可能**跟着挪一格。这是「不撞色」和
「固定一色」之间必须付的账，选的是「大多数窗口里不变」。

⚠️ 深色下不写第二套色值，而是把同一个色 `color-mix` 兑进深底里（22%），
文字用同色兑白（82%）。24 个颜色各写一份深色版，是 24 次分叉的机会。

### 重叠：往右下偏，一档 8px

`--depth` 由 `schedule.py` 算出来（**逻辑**：谁压着谁），偏多远写在 CSS 里
（**设计**）。用 `translate` 而不是改 `top` —— `top` 是时间，偏移是画面上的让位，
两件事写进同一个属性，下次调偏移量就得去动时间的算法。

⚠️ 「跟几张卡相交」和「压在第几层」是两个数。三张互不相交、但都跟第一张相交的卡，
按张数算全部落在第 1 档 —— 于是它们三张完全重合，正是偏移要解决的那件事。

⚠️ **接着的不算叠着的**：3–5pm 和 5–7pm 都偏移的话，一整天连着排的活动会像楼梯
一样一路往右下跑。

⚠️ 代价：偏下去的卡片，上沿不再精确对应它的开始时间（一档 8px = 10 分钟）。
完全重叠的两张里总得有一张让步。

### 红线只画在今天那一列

⚠️ 位置只能用**绝对时刻**算：模板给的是 epoch 毫秒，JS 做的唯一一次算术是两个
瞬间相减。浏览器自己取本地午夜的话，一个在纽约的志愿者看到的红线差三小时 ——
基金会的时区是洛杉矶（D16），而开发机上永远看不见这个错。

⚠️ 「还剩多久」挂在**线**上，不在卡上，写的是**最快结束**的那一场。线同时压着
三张卡时，一卡一个倒计时就是三个互相矛盾的数字并排。

⚠️ 服务端把红线、倒计时、半透明都渲染好了，JS 是**刷新**（30 秒一次，回到前台
立刻重画），不是初始化。反过来写会让没有 JS 的人得到一张没有红线的日历 ——
而红线是这一页最有用的东西。

⚠️ 两份实现（Python 的 `remaining()` 和 JS 的 `remainingText()`）必须同样**向上
取整到分钟**：向下取整的话最后 59 秒写「0m left」，读起来是「已经结束了」。

### 卡片

名称（最多两行）+ 时间段（`3pm – 5pm`），整张卡是通往活动详情页的链接 ——
160px 宽的东西上再放一个小链接，手指点不中。

⚠️ 矮到放不下两行时用 `@container` 把时间那行**收起来**，不是靠 `overflow` 切一半：
切一半的字比没有字更像坏了。半小时的活动（24px）就是这一档。

⚠️ 卡片高度有下限 22px（十分钟的活动按比例是 8px，一条线）。代价：下限生效的
卡片高度不再等于时长 —— 所以重叠判定用**画出来的框**，不用真实时间，否则屏幕上
明明压在一起的两张卡，代码认为它们不重叠。

⚠️ 跨夜的活动在两列里各有一张卡，各自裁到自己那天的边界，但**两张都写整场活动
的时间**，用箭头标出它从哪边延过来。第二天那张写「12am – 1am」是错的：人是拿
这行字安排时间的。

### 窗口位置是筛选表单里的一个字段

`from` 是一个 `<input type="hidden">`，不是只写在 action 的查询串里。

⚠️ 理由和 `scope` 那一条一模一样：`method="get"` 的表单提交时浏览器把 action 上的
查询串**整个丢掉**，换成表单自己序列化出来的那一份。少了这个字段，翻到第三屏
之后随便改一个筛选，日程就自己弹回起点 —— 而列表看起来完全正常。
箭头翻页时用 out-of-band 把它改掉。

⚠️ 反过来那半边：筛选换掉的是 `#event-results`，日程在它**外面**，所以筛选那一次
请求要把日程作为 out-of-band 的第二块带回去。少了它，筛完之后左边是新结果、
右边是上一次的日程，而两边**各自**看起来都正常。

⚠️ 窗口的下限是 `max(今天, 筛选的 From)`，**单向夹紧**：比下限早就抬上来，比下限
晚则留在原地。双向夹紧的话，改一个筛选就等于丢掉正在看的那一周。

### JS 挂在 `htmx:afterSettle` 上，不是 `afterSwap`

out-of-band 的那一块在 `afterSwap` 时还没落到文档里。用 `afterSwap` 的话，筛选
之后日程变成一块没有红线、也不会自己滚的静态图 —— 而它看起来完全正常。

⚠️ 而且要从 `document` 起扫，不从 `event.target` 起：oob 换掉的那一块**不是**
target（target 是列表），从 target 起扫会正好漏掉日程。

### 卡片、没有竖线（2026-08-18 补）

日程整块坐在一张 `.card` 上 —— 模板写的是 `class="schedule-panel card"`，
浅色白卡、深色 `ink-900`、配了首页大图时深色下自动变毛玻璃
（`.dark.has-hero .card:not(.border)`：blur + saturate + 方向性高光），
**这里一行颜色都没另写**。

⚠️ 玻璃只在有大图时出现，这是全站规则不是这一页的：没有照片的时候，糊什么都没有。

🔴 **`.card` 会静默地把面板从「钉住」变成「跟着滚」。** 它在样式表里排在
`.schedule-panel` 后面，带着 `position: relative`，同特异性后来者胜 ——
于是那条 `sticky` 被盖掉，日程跟着列表一路滚出屏幕。不报错，看起来像
「这个功能本来就这样」。按回去的是 `.schedule-panel.card`（0-2-0），
**不是**源码顺序：顺序会被下一个人重排，特异性不会。

列与列之间**没有竖线**，分开靠 `column-gap: var(--schedule-column-gap)`。

⚠️ 整点格线因此画在 `.schedule-grid` 上，不在列上。画在列上的话，每道竖缝都会
把横线切断一截 —— 一条断成四段的线读起来不是刻度，是四个盒子各自的边框，
正好把刚去掉的竖线暗示回来。

⚠️ 表头和格子必须用**同一个** gap 变量。两行用不同的缝，星期几就会和它底下那
一列错开，而错开一两像素看起来只是「字没对齐」，不像一个几何错误。

### 点一张卡：详情就地打开，左边跟着走（2026-08-18 补）

一次点击、一次请求、两块东西：面板里换成详情，左边换成**那一场所在的那一页**
并圈上它（out-of-band）。分成两次请求的话，慢网下中间那一下是「右边已经是新
活动、左边还高亮着上一个」。

| | 怎么做 | 为什么不是另一种 |
|---|---|---|
| 日程那一块 | `x-show` **藏起来** | 换掉的话，关闭时回不到你翻到的窗口和滚动位置 |
| 详情内容 | 详情页那份正文，一字不改 | 「面板专用的精简版」会在第二次改动后和整页说两件不一样的事 |
| 塞进 680px | `zoom: 0.85` | `transform: scale()` 不重排版面，右边空一条、热区也对不上 |
| 高亮记什么 | 一个 pk | 记页码的话，筛选一变，同一个页码指向另一批人 |
| 状态挂哪 | 面板上 | 它切换的两块都会被 HTMX 换掉，状态写在里面等于每换一次归零一次 |

🔴 **`.schedule-detail` 是 `height: 100%`，不是 `calc(100% / 0.85)`。**
百分比在**已经缩放过的**坐标系里解析，再除一次是重复计算 —— 详情比面板高出
84px（量出来的），多出来的那一截被面板的 `overflow: hidden` 裁掉**而且滚不到**。
屏幕上看起来只是「这个活动没写那么多」。

⚠️ 同一个症状还有第二个来源：HTMX 的靶子和 `.schedule-detail` 之间**不许再套一
层 div**。中间那层高度是 auto，里面的百分比就落在 auto 上，整条失效。

⚠️ 面板里那份正文**不画「← 返回」**（`in_panel`）。它是两处唯一的差别：在面板
里那条链接会把整页导航走，而人只是想关掉右边那一块 —— 关掉的 × 就在几十像素
之外。两条「回去」的路并排、一条会把页面整个换掉，是这一页最容易点错的东西。

⚠️ 「第几页」在**当前筛选下**算，所以卡片的 `hx-get` 带着完整查询串。算不出来
（那一场不在左边的列表里）是正常结果：开详情，但**不圈任何人**。

⚠️ 滚进视口用 `block: "center"`，不是 `"start"` —— start 会把那一行顶到吸顶导航栏
底下，正好被盖住一截。

### 颜色不分模式，光圈是霓虹（2026-08-18 补）

日程卡片的 24 格调色盘同日 **+15% 白**（`#b3dcfb → #bee1fc`）；2026-08-19 又把其中**偏灰的八格按亮度对齐**兑到 0.89（最脏的 `#b7ddd4` 兑了 47% 白）——「脏」的成因是低饱和**加上**偏暗，所以按亮度对齐而不是一律加同一个百分比。
没取更浅的一档：再浅下去，盘里那四个粉、三个黄开始彼此接近，而「不跟邻居撞色」
靠的就是它们分得开。兑白不改色相，所以色族表不用动。

🔴 **深色下卡片颜色和浅色一模一样，不兑深底。** 日程是这一页唯一的彩色信息
载体，「这一场是什么颜色」必须在两个模式下是同一个答案。连带三条：
文字留在深色（`ink-900`，不跟着 `.dark` 翻白）、hover 同样是压暗、
取消的那张也不给开例外。守卫：
`events.tests.ScheduleColourTests.test_dark_mode_does_not_repaint_the_cards`。

🔴 **色族表是量出来的，不是按色相名字排的**（2026-08-19 重排）。它回答的是「哪些格子看起来一样」，而撞色回避只保证不同族的两格可以相邻 —— 把两个长得一样的色值分进两族，回避就等于没有。守卫：
`events.tests.ScheduleColourTests.test_two_swatches_that_may_sit_side_by_side_never_look_the_same`。

选中行的光圈是霓虹，不是 `outline`：发白的管芯 + 贴着管子的浓光 +
散开的辉光（深色下再加一层最外的空气辉光）。三条硬要求：

- 🔴 `box-shadow` **不能累加**，所以卡片那两层悬浮影存进了 `--card-elevation`，
  光圈那几层后面必须跟着它 —— 否则选中的那张当场变平，而周围每一张还浮着。
- 🔴 「没有影子」写 `0 0 #0000`，**不能写 `none`** —— `none` 在逗号列表中间是语法
  错误，整条声明被丢掉，霓虹光圈在深色模式下一起消失。
- 🔴 **不许画在伪元素上** —— `.event-row > .card` 是 `overflow: hidden` 的，
  伪元素的外辉光会被整个裁掉（屏幕上是「有环、没有光」）；元素自己的
  box-shadow 不受自己的 overflow 影响。`::after` 那一格也已经被深色玻璃的亮边环占着。

⚠️ 浅色那一档**刻意克制**，比深色弱得多。试过加强版（实心主题色管芯 + 四层
辉光），看过之后退回来了：它旁边就是一列安静的白卡片，那个响度不属于这一页。
这是选择，不是没调完 —— 要动之前先读 revisions.md 四十三。

⚠️ 面板和左边活动卡的圆角是**同一条规则**给的（12px，两处都挂 `.card`）。
日程里那些**活动卡**是 8px，故意小一档：最矮的只有 22px 高，12px 圆角会让它
变成药丸形，而药丸在这套设计里是**按钮**专用的语言。

### 打开在早上，筛选卡钉住（2026-08-18 补）

日程打开时停在 **7am**，「现在」是下限（傍晚打开时窗口跟着红线走，但永远不会
比 7am 更早）。⚠️ 凌晨的活动**不会**把窗口往上拽 —— 宁可让那种少见的情况多滚
一下，也不要每翻一页起点都不一样。

日程开着时，筛选卡 `position: sticky` 钉在顶栏底下。⚠️ **只在开着的时候**：
关着那一档是全站最常打开的默认视图，和「关着时逐像素等于改之前」同一条决定。

- ⚠️ `z-index` 不能省 —— 活动行带 `relative`，少了它卡片会从筛选卡上面穿过去。
- ⚠️ `--top-bar-h` 现在两处声明（面板、筛选卡），守卫钉的是「所有声明只有
  4.25 / 4.75 两个值」，而不是各钉各的。
- ⚠️ 代价：这张卡连下边距约 257px，钉住之后那一列永久少掉这么多。

### 左边的卡片也开面板；钉住的东西会挡住「滚到这里」（2026-08-19 补）

日程**开着**时，点左边那张活动卡也把详情打进面板（和点日程卡是同一件事、
同一个端点、同一个 `is-picked`）。日程**关着**时照旧跳整页。

一份标记两种行为，靠的是 `hx-trigger="click[!!document.querySelector('.events-shell.is-open')]"`：
过滤器为假时 htmx 完全不接管，浏览器跟着 `href` 走 —— 没有 JS 那条路也一并成立（D24）。

🔴 **那两个 `!!` 少不得。** htmx 判断事件要不要放行用的是严格相等
（`eventFilter.call(elt, evt) !== true`），而 `querySelector` 返回的是元素 ——
truthy 但 `!== true`，于是每一次点击都被静默过滤掉，请求根本不发。
表现是「点了左边，右边那张卡是空的」，控制台一声不吭。守卫：
`events.tests.SchedulePanelTests.test_the_trigger_filter_returns_a_real_boolean`。

⚠️ `detail` 这个 Alpine 状态因此从面板挪到了 `.events-shell` —— 左边的卡片够不着
面板的作用域。它仍然在被 HTMX 换掉的两块之外，那才是原来那条规矩要的东西。

🔴 **钉住的东西会挡住「滚到这里」。** 翻页用 `show:#event-results:top` 把结果区顶到
视口最上面，而钉住的筛选卡正好压在那儿 —— 第一张卡完全看不见。修法是
`scroll-margin-top: calc(顶栏 + 1rem + var(--filter-h) + 0.75rem)`。

⚠️ `--filter-h` 由 JS 实测（`ResizeObserver`）。写死不行：那张卡窄屏换行、报错时
多一行字。而 `resize` 事件抓不到开关日程那 560ms 过渡里的换行。
