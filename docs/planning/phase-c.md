## 一、这一阶段要达成什么

一句话：把 Phase B 建好的东西**交到真人手上，并且交得起**。

Phase B 结束时的状态是：334 个测试全绿，
但**没有一个真人用过**，页面是裸 HTML，`/` 是 404，忘了密码找不回，
`prod.py` 是一句 `from .base import *`，备份一行脚本都没有。

2026-07-31 更正：**14 条需求并没有全部落地**。本文件原来写的是「代码全部落地」，
那是照 `02-roadmap.md` 的完工记录转述的，而那份记录只核对了**模型和服务层**。
按优先级逐条重查代码之后，发现**五处缺口，其中四处是没有页面**（见下面
[Phase B 的五处缺口](#phase-b-的五处缺口2026-07-31-发现)）。它们不是 Phase C 的新功能，
是 Phase B 的收尾 —— 所以进 [`03-roadmap.md` 的 C0.2](03-roadmap.md#c02--补齐-14-条的功能缺口)，
补完才轮得到上样式。

本阶段完成的定义：**一个 ministry 的真实志愿者，用自己的账号，报名并完成了一场真实活动，
而这场活动的数据能被恢复出来。**

### 判据：什么必须做完才能放真人，什么可以边用边加

这是本阶段唯一重要的分界线，其余排期问题都由它推出来：

> **这件事不做，出的事可逆吗？**
> 不可逆 → **交付硬前置，做完才放人**。可逆 → **可后补**。

状态一列 2026-08-17 加。**✅ 做完并验过 · 🟡 代码做完，差一次真实验证 · ⬜ 未开工。**
⚠️ 一步只要还剩一次拿真账号 / 真收件人 / 真库的验证没走，它就是 🟡 ——
把 🟡 记成 ✅ 正是[那五处缺口](#phase-b-的五处缺口2026-07-31-发现)的成因。

| | 不做会怎样 | 可逆吗 | 归属 | 状态 |
|---|---|---|---|---|
| 备份 + **验证过的**恢复 | 数据没了找不回 | ❌ | 硬前置 | 🟡 脚本和本机演练做完了，真 R2 + 真生产库那一遍没走 |
| 权限复核（真账号越权） | A ministry 看到 B 的未成年人生日、地址、紧急联系人 | ❌ | 硬前置 | ⬜ |
| 生产加固（HTTPS / secure cookie / HSTS） | 会话被劫持 | ❌ | 硬前置 | ✅ 线上 `check --deploy` 零警告 |
| 密码重置 | 用户锁死在门外，且只能靠你手工救 | ❌（对用户而言） | 硬前置 | ✅ 线上走通「注册 → 收信 → 改密 → 登录」 |
| 首页 `/` | 分享出去的链接是 404 | ✅ | 硬前置（成本 1 小时，不值得推） | ✅ |
| Ministry 视图 / 组织架构图 | 「食物银行现在谁在管」得进 admin 翻 | ✅ | 可后补 | ⬜ |
| CSV 导出 | 要做表得手抄 | ✅ | 可后补 | ⬜ |
| 志愿者活跃排行 | 少一个看板 | ✅ | 可后补 | ✅ 2026-08-05 提前做了 |

⚠️ **四条硬前置里，做完的是两条。** 剩下三条中的两条（备份的真实演练、权限复核）
风险是乘法关系，缺一个另一个就白做 —— 而它们**都只能拿真账号真库做**，写不出代码来代替。

> 备份和权限复核这两条的风险是**乘法关系**（账号能删库 × 删了找不回），
> 所以它们不是「都很重要」，是「缺一个另一个就白做」。

### 考虑过并否决的：全量 React SPA

否决理由**不是** React 不好，而是：

**分离想买的东西，这个项目已经买到了，而且没付钱。** 分离的核心好处是「换前端时后端不用动」，
这靠的是业务逻辑不在界面层 —— 而本项目的 [D18 落点规矩](decisions/D18-admin-boundary.md)
已经强制了这件事：逻辑在 `services.py`、权限只在 `org/permissions.py`、
统计在 queryset 方法里、视图是薄壳，而且有 **12 条 grep 守卫在测试里盯着**没人破坏它。
`core/templates/core/base.html` 的注释里写的「替换这一个文件就能上样式，
views / forms / services 原样带走」不是愿望，是那 12 条守卫保证的。

**而分离要付的代价里最贵的一条，正好打在 [D20](decisions/D20-ministry-role.md) 上：
权限判断会变成两份。** 服务端那份是安全边界，必须留；但前端还要**再判断一次**
才知道该不该显示「签到」按钮，而它够不到 `permissions.py`。
D20 存在的全部理由就是「散落的权限判断迟早有一处忘了 `.active()`，
而漏掉的权限检查是静默的」—— React 会亲手把这个局面造出来。

其余代价：12 个页面各要一套 (endpoint + serializer + 前端状态 + loading 态 + error 态)，
同样功能约 3–4 倍代码；现有 334 个测试是端到端的（直接打 URL、断言 403），
改成 SPA 后它们只覆盖 API 那一半，UI 那一半要另起一套测试设施。

**颜值和这个选择无关** —— Tailwind 是 CSS，服务端渲染照样用。

**重启条件**已写进 [`deferred.md`](deferred.md)：真的要做手机 App，
或者真的有第二个人专职做前端时。那时加一层 DRF 是几天的事，**因为业务逻辑早就不在模板里**。

### 考虑过并否决的：AWS

**同一个规模下 AWS 更贵、更累。** Render 约 $14–20/月、半天搭好；
AWS 走 App Runner + RDS 约 $50–90/月、2–3 天，走 ECS Fargate 还要自己搭
VPC / 子网 / ALB / 安全组，单 NAT Gateway 一项就 ~$32/月。
AWS 便宜是**有专职运维、多服务共摊、上预留实例**之后的事。

这撞的是[一、终极目标](goal.md#一终极目标)那张表里的两行：「便宜：起步阶段月成本控制在几十美元内」
和「好维护：一个人能读完全部代码」。

**这不是锁定** —— [D3](decisions/D03-portable-postgres.md) 一直在保护这件事：
一个 `pg_dump` 带走全库，应用是标准 Django。用 Render 起步不会让以后搬去 AWS 变难。
**重启条件**同样写进 `deferred.md`。

## 三、落点规矩

> **这一节是本文件存在的主要理由。** 下面每条都不是「这次怎么做」，
> 是「以后每次改都要遵守」，同 [D18 的落点规矩](decisions/D18-admin-boundary.md)。

### 样式的落点：CSS 只许出现在两个地方

1. `core/templates/core/base.html` 的 `<head>`（引 `app.css`）与页面外壳；
2. 各模板标签上的 Tailwind class。

**不许出现在**：`views.py`（不返回 class 名）、`services.py`、`forms.py` 的
`widget attrs`（**唯一例外**：`type="date"` 这类**语义**属性，它不是样式）、
`models.py`、`admin.py`。

> **判据，和 D18 那条同源**：**把 `static/css/app.css` 删掉，页面必须仍然可用** ——
> 难看但每个按钮都在、每条信息都读得到。做不到，说明有信息只靠样式表达
> （靠颜色区分「已报名 / 未报名」就是典型），那不是样式，那是内容，得写成文字。

2026-08-03 补两条：

- **深色模式做，并且给手动开关。** 所以模板里每写一个 `bg-` / `text-`
  就当场写它的 `dark:` 对 —— 留到最后统一补等于把 20 个模板再扫一遍；
- **具体的色板 / 字号 / 间距 / 组件写法全部在
  [`design-system.md`](design-system.md)**，不写在这里。
  这一节管的是「能写在哪」，那一份管的是「写成什么」。

### JS 的落点：HTMX 和 Alpine 各管一层（2026-08-03 新增）

三层的分工和完整论证在 [D24](decisions/D24-htmx-alpine-tailwind.md#三层的分工)，
这里只留两条硬规矩：

**HTMX** —— ⭐ **每一个写操作都必须有一条完整的服务端表单路径，HTMX 只是它的快路。**
读操作（筛选、排序、展开详情）不受这条约束。
它保住的是现有那 404 个直接打 URL 的端到端测试：这条口径一破，
它们就退化成只覆盖片段端点那一半 ——
而那恰恰是[否决 React 时列出的代价之一](#考虑过并否决的全量-react-spa)，
换个技术栈把它请回来等于白否决。

**Alpine** —— 只管展开 / 收起 / 选中 / 模态 / 主题切换这类**纯 UI 状态**。
`x-` 属性里**不许出现**权限判断、工时或金额的计算、日期运算。

> **判据，和上面那条同一个句式**：
> 把模板里所有 `x-` 属性删掉，**每个写操作必须仍然能完成**。

⚠️ **Alpine 的越界不会报错。** 把一个权限判断写进 `x-show`，
页面照常渲染、测试照常绿，只是那个按钮对不该看见它的人也画出来了。
服务端仍然会 403，所以泄露的是**信息**不是权限 —— 但那也是泄露，
而且没有任何东西会告诉你它发生了。守卫测试就是为这一条存在的。

**守卫的执行方式改成两层**（2026-08-03）：本地 `.pre-commit-config.yaml`
+ CI 里的强制 workflow，守卫不过红灯、禁止合并。
在此之前那 12 条守卫只在有人主动跑 `manage.py test` 时才生效。

### 界面语言的落点：英文写在哪，中文允许留在哪

口径见 [D23](decisions/D23-i18n-interface-only.md)：**界面统一英文，不做双语，不引 `gettext`。**
分界线是「**这句话会不会出现在浏览器里**」，不是「它写在哪个文件里」。

| 必须是英文（用户看得见） | 中文照旧（用户看不见） |
|---|---|
| 模板里所有给人看的文案 | 代码注释、docstring —— 本项目的推理都写在这里，翻成英文是纯损失 |
| 表单的 `label` / `help_text` | 规划文档（`docs/planning/` 全部） |
| `messages.*()` 和 `ValidationError()` 的文案 | 日志、给开发者看的异常字符串 |
| `TextChoices` 的 **label**（**value 一个字不改** —— 它在库里，改了就是数据迁移） | 测试里的断言字符串（改英文只是让 diff 变大） |
| 模型的 `verbose_name` / 约束的 `violation_error_message`（会冒到表单上） | — |
| `org/permissions.py` 的 `SCOPED_DENIAL`（它是 403 页面上给人看的） | — |

2026-08-03 更正：**`seed_demo` 的演示数据从右列挪到左列**。原来写的是「演示数据中文照旧」，
上手验收时立刻发现行不通 —— 英文界面里满屏中文活动名，人没法核对页面对不对。
判据就是本节自己写的那条：**这句话会不会出现在浏览器里** —— 演示数据会，
而且是验收那一遍唯一出现在浏览器里的数据。

⚠️ **基金会自己录进去的值仍然不受这条约束，也管不了。** `Ministry.name` / `EventType.name` /
`ParticipationRole.name` / `EmploymentType.name` 是基金会自己录进去的，
录中文就显示中文。**要跟他们说清楚**：界面是英文，但活动名和 ministry 名是录入时那种语言。
不说清楚，第一个看到混排的人会以为坏了。

**守卫**：`core/tests.py` 加一条 grep —— 模板里不许出现中日韩字符
（`{% comment %}` 块除外，注释可以是中文）。它比双语方案里那条守卫更强：
那条只能查「没包 `{% trans %}`」，这条直接查「有没有中文」，**没有漏网的中间态**。

### 部署配置的落点：什么进环境变量，什么进 `render.yaml`

沿用 [`config/settings/base.py`](../../config/settings/base.py) 已有的 `env()` 口径：

| 进环境变量（平台上设，不进 git） | 进 `render.yaml`（进 git） |
|---|---|
| `DJANGO_SECRET_KEY`、`DATABASE_URL`、SMTP 凭据、对象存储密钥 | 服务形态、构建命令、健康检查路径、cron 时刻表 |
| `DJANGO_ALLOWED_HOSTS`（域名会变） | `DJANGO_SETTINGS_MODULE=config.settings.prod`（不是秘密，也不该变） |

⚠️ **生产的 `SECRET_KEY` 必须是新生成的。** 早先硬编码在仓库里的那个已经进了 git 历史，
按 [Phase A 的记录](progress.md#-已完成--phase-a-地基加固)**已经烧掉，永远不能再用**。
落地时用的是 `generateValue: true`：Render 现生成，不进任何文件，也不经过人的手。

2026-08-12 写 `render.yaml` 时补上这张表漏掉的一半 —— **右列不是「可以进 git 的」，
是「同步一次就会被写回平台一次的」**。三条推论，第三条最容易踩：

- 秘密走 `sync: false`：名字进 git，值第一次同步时由平台问你要。
  这一列因此不必是「名字也不能进 git」，只是值不能；
- `DJANGO_DEBUG=False` 值得写进右列，**正因为**同步会把它按回去 ——
  有人为查线上问题点成 `True`，下次同步自动收回；
- 而 `REGISTRATION_RATELIMIT_PER_IP` / `_SITE` 必须**留在左列且一个字都不写** ——
  [`.env.example`](../../.env.example) 承诺过「为一次注册活动调高它，重启即可，
  不用部署」，写进右列的话，面板上调高的值会在下一次同步时被静默按回去，
  而那一次同步恰好可能在活动当天。

### 备份脚本的落点

`pg_dump` 走**平台的定时任务 + 一个 shell 脚本**，不写成 Django management command。

> **判据**：备份必须在**应用起不来的时候**照样能跑。
> 写成 management command 就意味着它依赖 Django 能启动、依赖 settings 能加载 ——
> 而需要备份的那天，坏掉的往往正是这些。它只需要 `DATABASE_URL` 和 `pg_dump`。

## 四、验收口径

> 每条都是**能当场做的动作**，不是「检查一下」。
> 沿用本项目一贯的判定方式（见 [D18 的落点判据](decisions/D18-admin-boundary.md)）。

### 备份：什么叫「演练过」

⭐ **三样都做了才算，少一样就是没验证过**：

1. 从对象存储**取回**最新的 dump（不是本地那份）；
2. 灌进一个**空库**，`python manage.py migrate --check` 通过
   （证明 schema 和代码同代，不是半年前的）；
3. 对着这个恢复出来的库**跑一遍测试**。

⚠️ **只做第 1 步是最危险的状态** —— 文件在、看着有几十兆，
而它可能是一个空库的 dump、或者是用不同 Postgres 大版本导出的。
文件存在不等于能恢复，而这件事只有真的恢复一次才知道。

这一步同时是 [D3](decisions/D03-portable-postgres.md)「一个 `pg_dump` 就能带走」
第一次真正兑现 —— 在此之前它只是纸上承诺，没有任何脚本落地。

### 权限复核：拿真账号做的四件事

**不是读代码，是登录进去点。** Phase B 已经建好 [D20](decisions/D20-ministry-role.md)
和 [D21](decisions/D21-self-service-and-permissions.md)，这里做的是**验证**：

1. ⭐ 拿 A ministry 的 admin 账号，打 B ministry 的
   `/events/<id>/registrations/`、`/attendance/`、`/notify/` —— **三个都要 403**；
2. 志愿者账号打 `/admin/` —— **403，不是跳登录页**（`core/middleware.py` 的
   `StaffOnlyAdminMiddleware` 负责这条）；
3. 基金会的人**不用 superuser 登录**，且默认**不给 delete 权限** ——
   尤其 `delete_event`，它两级级联到 `Participation`（见 phase-b.md 的 `on_delete` 表）；
4. 未成年人的姓名 / 生日 / 地址 / 紧急联系人 / 同意记录，谁能看。

> **第 4 条 2026-08-03 改写。** 原文是「谁能看要逐个账号过一遍」——
> 那不是[本节开头要求的那种](#四验收口径)「能当场做的动作」，
> 而这类含糊的验收项**跑起来一定会被跳过**
> （和 2026-07-30 那条自相矛盾的 R1–R3 是同一个病）。
>
> 可执行版本：先认下这四个页面**分别暴露什么**，再拿三个角色各打一遍。

| 页面 | 暴露什么 | 谁应该看得到 |
|---|---|---|
| `event_notify` 的预览行 | 未成年人那几行显示的是**家长的邮箱 / 电话**（`row.to`） | 只有本 ministry 的 admin。这是 [D22](decisions/D22-event-notifications.md) 有意为之，不是泄露 —— 但要确认换个 ministry 的账号打同一个 URL 是 403。⚠️ **foundation tier 也进不来这一页** |

| `/admin/` | 全都看得到，包括同意记录和 simple-history | 只有 staff。所以「基金会的人不用 superuser 登录 + 不给 delete」那两条，是这一层唯一的闸门 |

> 2026-08-05 改写：新增了 foundation tier 这一档，**未成年人数据的可见范围跟着变大了**。
>
> 上面三行的「外加 foundation tier」是当天拍板的，**有意为之**：基金会全局角色能读
> 任何 ministry 的报名、签到和报表，但一个字都改不了。代价说清楚 ——
> 签到页上画着**未成年人的标记和紧急联系人电话**，所以这一档一开，
> 这些数据就从「本 ministry 的 admin」扩到了「基金会全局角色」。
>
> ⚠️ **「不能改」不是靠不画按钮。** `event_attendance` 是个写页面，
> 视图对只读身份的 **POST 直接 403** —— 藏按钮是界面，拒 POST 才是边界。
> 有一组测试专门发这些写请求（`events.tests.FoundationTierReadOnlyTests`），
> 因为读 HTML 证明不了这件事。
>
> **所以第 1 条验收要多打一遍**：拿 `foundation_admin` 账号
> **POST** 一次签到（`action=check_in`）—— 必须 403，且那个人**没有被签到**。

> ⚠️ 用 superuser 点这些页面会得到一串 403，看起来像坏了 —— 那是
> `org/permissions.py` 的设计（superuser 没有 ministry scope），
> 它的 `SCOPED_DENIAL` 文案就是为了让下一个人去改账号而不是改检查。**别照着「修」。**

| 🔴 深色模式的背景照片压得比 AA 要求的浅（2026-08-06 定） | 内页深色背景用的是**和首页同一份**两层渐变遮罩（`_hero_scrim.html`）。换掉的是照片自己的 `filter`，那一版每项指标都更好（最坏照片下卡外文字 6.68:1）但**观感太暗**。代价如实说，而且这一条比清单里其他几条都更容易被忽略：当前这张照片下，**卡片外的小字只有 4.03:1**（低于 AA 的 4.5，大标题不受影响 —— 大字判据是 3:1）。⚠️ **更要紧的是它跟着照片变**：换一张更亮的首页照片，这个数会继续往下掉且**不报错**；纯白照片下卡外只剩 1.73:1、连卡内正文也只剩 4.11:1。守卫只盯得住「遮罩还在、数值没被改」，盯不住「传了什么照片」 | **每次换首页照片都要重看一次**，而这件事没有任何东西会提醒你。眼下最便宜的补救是提高卡片自己那层黑（只影响卡面，照片一个像素不动），代价是玻璃变闷；真要两头都要，得让遮罩强度跟着上传的照片算出来 —— 品牌色已经是这么推的（[D26](decisions/D26-palette-from-the-hero.md)），同一条路走得通 |

| ⚠️ 企业 / 高校邮箱的志愿者可能收不到信（2026-08-17 记） | 发信的认证是齐的（`dkim=pass header.d=rolf-v.org` + `dmarc=pass`），但 `rolf-v.org` 是一个**全新的发信域名**，而 Brevo 免费档走共享 IP 池。实测第一封信被 UCSD 的 Proofpoint 网关**扔进隔离区** —— ⚠️ 隔离区不是垃圾箱：信**不会出现在收件人的邮箱里**，他只会在每日摘要里看到，或者根本不看。处置是**不做任何特殊处理**（换发件域名、加免责声明这类动作通常更可疑），靠持续发信把信誉养起来。⚠️ 代价：试点头几周，学校或公司邮箱的人可能拿不到密码重置信和活动通知，而**没有任何东西会报告这件事** —— 系统这边看到的是「已发送」。试点期有人说「我没收到」，第一句要问的是「你的邮箱是不是学校或公司的」 | 有人真的报告收不到时。⚠️ 那时先查的不是代码，是 Brevo 的投递日志 + 让对方看隔离区/垃圾箱。普通 Gmail / Outlook 宽松得多，而志愿者绝大多数在那儿 |
| ⚠️ 长度上限落在表单层，不是数据库层（2026-08-06 定） | 上限写在 `core/limits.py`，通过 model 的 `max_length` 传给每个 ModelForm。⚠️ **`TextField` 的 `max_length` 既不是数据库约束、也不给 model 加校验器** —— Postgres 那一列还是 `text`，`full_clean()` 也不看它。所以走页面和 admin 的输入都拦得住，`bulk_create` 和脚本拦不住。和 [D9](decisions/D09-rules-in-db-constraints.md) 那条「`save()` 不调 `clean()`」的老口径是同一件事 | 真的出现过一次「脚本灌进一段超长文本」时。那时的做法是把那一列改成 `CharField`（有真约束），而不是到处补 `full_clean()` |

### 2026-08-07 这一轮拍板的：现场扫码自助签到

起因是一句运营侧的话：**「有些 event 太大了，让 admin 来记录谁到了、做了多少工时，
太费时间了。」** 这不是一个功能请求，是一个**数据质量**问题 ——
一个不会被真的执行的流程，产出的不是「少一列数据」，而是
[D27](decisions/D27-ministry-report.md) 那张报表里已记录工时和缺勤率同时失真，
且失真方向跟着「哪个 admin 比较负责」走，不是随机的。

结论全文在 [D28](decisions/D28-qr-checkin.md)，实施步骤在
[C6](03-roadmap.md#c6--现场扫码自助签到)。这里只记这一轮**推翻了什么**：

| 原方案（需求原文） | 拍板结果 |
|---|---|
| 动态二维码是「防作弊核心」 | ❌ **它不是。** 它只把攻击成本从零抬到「需要一个现场的活人当中继」，而没有任何加密手段能关掉这个洞。定位改成「减少录入的工具」，权威仍是 admin 的 attendance 页。这一句是 D28 全部取舍的出发点 |
| Token 验证成功后标记为已失效 | ❌ **那是一个 bug。** token 是这 20 秒里所有人共用的，烧掉之后一百人的队伍里九十九个人打不上卡 |
| 允许前后浮动 1~2 个周期以容忍时钟误差 | ❌ **基于误解。** 志愿者手机和 admin 平板的时钟从不参与计算，只有服务器自己的时间进公式。真正要容忍的是扫码到提交的物理延迟。改成把签发时刻写进 payload，有效期是平的 90 秒 |
| `/checkin?event_id=X&token=Y`，收到就记 check-in | ❌ **GET 不能写** —— 链接预览抓取器和浏览器预取会替人打卡。改成 GET 显示确认页、POST 才写 |
| （没提）手机上没登录怎么办 | **新增，也是这一轮加的最大一块。** 把「你人在现场」（token，90 秒）和「你是谁」（正常登录，session 凭据 10 分钟）拆成两段，否则每个新志愿者的第一次都会卡在「打完密码回来 token 过期了」 |
| （没提）token 端点谁能调 | **新增，且是整套机制的命门：必须 `can_manage_event`。** 不检查的话任何志愿者在家里就能给自己发码，整套机制被绕过 |
| qrcode.js 走 CDN | ❌ 改走 npm + esbuild。现场是教堂大厅的 wifi，而这个脚本决定二维码里画哪个 URL。**客户端渲染这一半保留**，那部分原需求是对的 |

新增一列 `Participation.checked_in_method`（一次迁移）——
自助打卡这个洞[唯一真实的缓解](decisions/D28-qr-checkin.md#四checked_in_method一次迁移一列出事时想看的那一列)
是让它**在页面上看得见**，而不是试图堵住它。

⚠️ 它带来一个**已知的、系统性的**偏差，记在这里而不是只记在 D28 里：
志愿者手滑早签退会写进一个偏小的权威 `hours`，而 `mark_absent()` 从此拒绝那一行。
方向和原来「admin 忘了点签退」的偏差相同，
所以 D27 报表上「已记录工时」那个注脚的重要性因此上升了一级。

### 2026-08-17 这一轮拍板的：发信换成 Brevo

起因不是重新评估，是**申请被拒**：SES 的出沙箱申请没通过，
而沙箱里的 SES 只能发给已验证过的地址 —— 也就是对真实志愿者一封都发不出去。
定的是**先用 Brevo 跑，网站真的用起来一段时间之后再申请一次 SES**。
这不是「Brevo 比 SES 好」，是**一个申请要拿使用记录去写才写得赢**：
现在申请书里没有真实的发信用途、没有退信和投诉的处理办法，下一次会有。

| | 结论 |
|---|---|
| 代码要改多少 | ≈0。`EMAIL_HOST` / `PORT` / `USER` / `PASSWORD` 是供应商无关的 SMTP 凭据，`render.yaml` 的四个占位一个字没改。**这是 2026-08-03 那句「换家的成本≈0」第一次被兑现** |
| 域名白买了吗 | 没有。Brevo 一样要域名认证，**DKIM / SPF 那两条要换成它的**（DMARC 留着）。发件地址仍然钉在自己的域名上 —— 换回 SES 时收件人看到的地址不变，寄信地址一换，送达信誉从零开始 |
| 换回去的成本 | 环境变量四项，但**必须重跑 [C3.3](03-roadmap.md#c33-真实发信) 的验证**。免费档走共享 IP 池，和自己认证过的域名不是同一条送达路径，当成纯改配置会踩在「他说他没收到」上 |
| 新出现的风险 | ⚠️ **免费档有每日上限，而撞上它的会是 P6**：一场 100 人的活动点一次 Notify 就是 100 封，密码重置和邮箱验证只是零散量。这不是「慢一点」，是**一部分人收不到**，而当天发生的时候没有任何东西会说 |
| 解掉的那个堵点 | [C3.11 邮箱验证](03-roadmap.md#c311-邮箱验证注册--改-email) 当初被沙箱堵死（账号建出来是未激活的，而激活信发不出去，注册被整个锁死）。Brevo 通了之后这条链活了。⚠️ 换回 SES 那天这道墙会原样回来 |

同日修掉的一个真缺陷：`notify_event_change()` 把发信做在 `transaction.atomic()`
**里面**，额度在第 47 封断掉时事务整个回滚 —— 46 个人收到了信，
而库里那条「通知过谁」的记录**根本不存在**。经过和处置见
[`03-roadmap.md` 的计划外记录](03-roadmap.md#c33--发信在事务里而额度是会用完的)。
⚠️ 它一直都在，只是出了沙箱的 SES 基本撞不到上限，**换到免费档才变成一件会发生的事**。
