## 一、需求原文（第二批，不要转述）

> ① 有一类 ministry 的成员全是志愿者，但他们像员工一样 —— 有固定开会时间、
> 每个人有固定岗位。我想把他们当成 employees，但写成 unpaid。
>
> ② 我需要 make sure，员工可以很清楚地 tell，哪些是他自愿作为 volunteer 做的爱心活动，
> 哪些是工作安排而参加的 event 活动。同样，foundation 需要能很清楚地 tell，
> 哪些人（虽然也是员工）做的有些活动是出于自己的爱心，
> 哪些人他做的事看似是献爱心的 event，但实际上是工作。
>
> ③ 让 foundation 可以 track 到 employees / staff 的工时，
> 以及方便 employee 看到自己的排班 / 工时 / total hours，
> 帮助整个 foundation 更好地 function and cooperate。

**转述会丢东西**，这是 [`goal.md` 零](goal.md#零当前优先级2026-07-29-定)
用一整节买来的教训（R4 那个发现就藏在两句话的并列里）。这里同样：

- ② 里「同样」两个字之前和之后是**同一个事实被两侧读到** ——
  所以它必须是存下来的一个字段，不是任何一侧的页面自己去推（[D38](decisions/D38-served-as-volunteer-or-work.md)）；
- ③ 里「方便 employee 看到自己的」这半句是**一个交付物**，不是一句客套。
  ⚠️ 初版 roadmap 的十一个页面里**没有一个是给员工自己看的** ——
  见[第六节自查](#六自查这一轮砍掉和补上的东西)。

## 二、判据：这一阶段的东西该不该做

Phase C 之前的判据是「是不是那 14 条需求的前置条件」。
那条规则**在这一阶段换锚**（换锚的理由和手续见 [`goal.md`](goal.md#判定规则的第一次换锚2026-08-14)），
新的判据是两条，**两条都要过**：

> 1. **它是不是上面三段原文里某一句的前置条件？**
> 2. **这张表 / 这个字段 / 这个页面，哪条查询或哪个人会读它？**

第 2 条不是新的 —— 它是 `goal.md` 零末尾那句自查问题，
本轮**第一次被真的执行了一遍**，当场砍掉四个字段（[第六节](#六自查这一轮砍掉和补上的东西)）。

### ⭐ 配套的一条录入判据：谁该有 `Assignment`

需求原文 ① 的答案是「把他们当员工，写成 unpaid」——
但基金会里一定有一批人介于两者之间（偶尔来一次 vs 有固定岗位）。
判据不写下来的表现是：**名册慢慢长胖，R8 的名单跟着变，而没有人发现口径动过**。

> **有固定岗位 _且_ 机构对他的时间有承诺（一条 `WorkPattern`，或一个
> `agreed_hours_per_week`）→ 建 `Position` + `Assignment`。
> 只按场来的人，只有 `Participation`。**

这就是 [D32 轴一](decisions/D32-worker-axes-schedule-and-assignment.md)
（「他在组织架构里有没有一个格子」）落到操作层的说法。
⚠️ 它要写进演示脚本 —— 这件事是基金会自己录数据时每天都要判一次的，
而判错的成本不是一行数据，是**所有按"在编"分组的数字**。

## 三、落点规矩

[D18 的落点规矩](decisions/D18-admin-boundary.md)照旧：
逻辑进 `services.py`，权限只在 `org/permissions.py`，统计在 queryset，视图是薄壳。
本轮新增的**九条**守卫见 [`05-roadmap.md`](05-roadmap.md#本轮新增的守卫测试)。

本轮特有的七条「只有一处」：

| 规矩 | 唯一的实现处 | 不守会怎样 |
|---|---|---|
| 只有一处生成班次 | `org/services.py::generate_shifts()` | 第二个生成器的删／插规则和第一个不一样，两边都不报错 |
| 只有一处**改**班次 | `org/services.py::edit_shift()` | 没人翻 `source=edited`，下一次生成把人手工改过的班次删掉（[D33 第四节 ④](decisions/D33-work-schedule.md)） |
| 只有一处回答「某天谁在班」 | `org/services.py::on_duty()` | `status` 该数哪几档有两份口径，页面和报表对不上 |
| 只有一处算「实际投入」 | `org/services.py::staff_hours()` | 见 [D36](decisions/D36-two-hour-ledgers.md) |
| 只有一处删生成班次 | `org/services.py::_drop_generated_after()` | 撤销 / 任职结束 / 生成器各写一遍那两个条件，漏掉 `date__gt` 就是静默改写考勤史（[D40](decisions/D40-undo-a-pattern-batch.md)） |
| 只有一处检测冲突 | `org/services.py::conflicts_for()` | 报名页和指派页各写一套重叠判断，两边算出来的「撞没撞」不一样，而两边都不报错（[D39](decisions/D39-scheduling-conflicts.md)） |
| 只有一处写「这一次是志愿还是工作」 | `events/services.py::set_served_as()`<br>+ admin 里那两个字段 **readonly** | 三条写入路径各带一套默认规则；⚠️ 而 admin 是**不写代码就存在**的第四条，grep 拦不住它（[D38 第四节](decisions/D38-served-as-volunteer-or-work.md)） |

## ⭐ 四、页面与入口总表

**这张表是本阶段最重要的一张。** 理由是这个项目已经**三次**栽在同一件事上：

1. C0.2 的五处缺口 —— 四处是「服务层写好了、没有页面」；
2. C0.5 的 `LOGIN_URL` 和 403 模板 —— 代码和 URL 都在，缺把它们连起来的那一个设置；
3. [D35](decisions/D35-event-assignment-path.md) 说的 `sign_up()` ——
   注释里写着"admin 替人录入也走这里"，**而没有任何 URL 能走到它**，写完至今没人发现。

所以这一轮**每一个页面在写之前就要有一行**，五列缺一不可 ——
⚠️ **第五列（哪一批）是新加的**：初版有一个页面（我的请假）四列都写了、
却在三批步骤里一个落点都没有，而那正是这张表本身要防的病。

对外模板数会从 20 涨到 30 出头 —— 这是本项目单轮加页面最多的一次，比加表更值得盯。

两条要点，都是这张表**改口**的地方：

- ⭐ **「批量建例会模板」不是锦上添花，它是需求原文 ① 的第一道门槛。**
  那个 ministry 的人的共同点**恰恰是同一个固定开会时间**，
  而一条 `WorkPattern` 挂一个 `Assignment` —— 没有批量入口，
  就是让基金会把同一个「周二 19:00」敲三十遍。
  「第一次敲的过程就是想清楚怎么排班的过程」这句话对**排班**成立，
  对**同一个例会重复三十遍**不成立。做法：一个多选 + 一次 `bulk_create`，不是新结构。
  ⚠️ **但它前面必须有一屏确认** —— 勾 30 个人是约 390 行 `Shift`，
  是本轮单次影响面最大的一个动作（[D2a.8](05-roadmap.md#d2a8-班表管理页面)）；
- ⚠️ **请假的录入口在自助侧，不在管理侧**（[D34 第四节](decisions/D34-leave.md)）。
  录入的人必须选类型，所以录入口开在哪里，就等于"类型给谁看" ——
  开在 ministry admin 那里，权限表里那条「类型和备注他看不到」当场作废。
  管理侧只留一个 foundation tier 的代录口，给没有账号的在编人员用。

### My Schedule 的形状

需求原文 ② 和 ③ 都落在这一页上。

一页、两条泳道、三个数、永不求和：

```
┌ 本周 ─────────────────────────────────────────────┐
│ 周二 19:00–21:00  Food Pantry 例会      〔工作安排〕│
│ 周六 09:00–13:00  春季发放日 · 接待      〔工作安排〕│  ← 被派去的
│ 周日 14:00–17:00  秋季募捐晚宴 · 接待    〔志愿服务〕│  ← 自己报名的
└───────────────────────────────────────────────────┘

  本月                                                  〔本月 ▾〕
  排班工作时间          志愿服务时间          待确认
  32.0 小时             6.5 小时              8 小时
  ─────────────────    ─────────────────    ─────────────
  两个数不相加。「排班工作时间」是你岗位上的时间，
  「志愿服务时间」是你自己额外投入的。

  今年累计志愿服务 18.5 小时                    ← 单独一行，写明是全年
```

⚠️ **上面这张图里的中文标签是文档用语，不是 UI 文案**（2026-08-15 补）。
界面一律英文（[D23](decisions/D23-i18n-interface-only.md)），
而那两档的措辞只有一个落点：[D38 第六节](decisions/D38-served-as-volunteer-or-work.md)。
这里写中文只是为了让这张图读得懂 —— **不要照着它写模板**。

六条设计规矩，每一条都有出处：

1. **两条泳道用标签区分，不用两个 tab** —— 分成两页就答不出「我这周要做什么」，
   而那才是人真正会来这一页问的问题；
2. ⚠️ **两个数并排、明写不相加**（[D36](decisions/D36-two-hour-ledgers.md)）。
   页面上不许出现任何一处把它们加起来的地方，守卫盯着；
3. **每一行都带身份标签，且标签旁边写得出是谁定的** ——
   「你自己填的」/「由 Food Pantry 的管理员设置」
   （[D38 第四节](decisions/D38-served-as-volunteer-or-work.md) 的
   「看得见不可交易」就落在这一行字上）；
4. ⚠️ **两档的排版必须中性**：不许把「志愿服务」做得更醒目、更值得表扬。
   那会让这个字段变成一个大家都往一边填的字段，两个数字同时失真。
   这条**没有测试盯得住，只能靠 review**；
5. ⚠️ **并排的三个数必须是同一个时间窗**，而且窗口写在它们上面。
   初版是「本月 / 今年 / 上周」三个数三个窗 —— 并排放着，
   读的人只会去比大小，而它们**根本不可比**。
   「今年累计」是有用的，但它单独一行、自己写明年份。
   `my_timeline(contact, start, end)` 只收一个窗，页面上就只该有一个窗；
6. ⚠️ **「待确认」在排版上要退一格**（2026-08-15 加）。第 5 条把**时间窗**对齐了，
   但那三个数**不是同一类东西**：前两个是[两个账本](decisions/D36-two-hour-ledgers.md)，
   第三个是**第一个账本的质量指标**。等宽等重地并排，读的人会当成三个可比的量。
   做法：待确认用次级样式，底下跟一行「这些小时还没有人核实」。
   ⚠️ Track It Forward 是把 pending 和 approved 画在**同一条进度条**上、两种颜色 ——
   结构本身就说明了 pending 属于哪个数，这里做不到那么强，但至少不能画成第三个并列的量。

### 为什么是 `.ics` 而不是"再做几个班表页面"

排班要真的被人看到，得进他自己的日历。Deputy / When I Work /
Planning Center Services 全都有这个端点，它是这类系统里性价比最高的一个功能：
**几十行、零依赖**（拼字符串，不引库），而它比任何一个班表页面都更接近
「方便 employee 看到自己的排班」这句原文。

⚠️ 订阅链接带一个不可猜的 token，**并且要能撤销** ——
一个泄漏出去的日历链接会一直泄漏下去。

### ⚠️ 「可撤销」意味着它**不能**照抄 D28 的做法

[D28](decisions/D28-qr-checkin.md) 的签到 token 是
`salted_hmac(SECRET_KEY, …)` 的**纯函数**（`events/tokens.py` 的 docstring
第一句就是「没有数据库」）。**纯签名的 token 撤销不了** ——
唯一的办法是换 `SECRET_KEY`，而那会同时废掉签到、会话和密码重置。

所以这里必须**存**一个东西：

```
Contact.calendar_token   随机串，可空；「撤销并换一个」= 重新生成这一列
```

⚠️ 它是本轮**唯一一个不在 [D37](decisions/D37-hris-fields-and-credentials.md)
那张字段表里的新字段**，因为它不是 HRIS 字段，是这个端点自带的成本。
记在这里，免得以后有人拿 D37 的字段表当"本轮加了哪些列"的全集。

⚠️ **它输出两条泳道，不是只有班次**（2026-08-15 改）。初版只拼 `Shift`，
而这一节自己的论证是「排班要真的被人看到」—— 那么**志愿服务那条更需要进去**：
它是自己选的、一次性的、没有周模式可以记住，最容易忘的就是它。
做法是多收一个 queryset，零新结构（[D2a.7](05-roadmap.md#d2a7-ics-订阅)）。

另外三件 `.ics` 的实事，省一件都会在手机上出问题：

1. **`UID` 必须稳定**，且**两条泳道前缀分开**（`shift-<pk>@<域名>` /
   `participation-<pk>@<域名>`）。不稳定的话，日历每次刷新
   都把同一个班次当成新事件，一周之后手机上是一堆重影；
   ⚠️ 前缀不分开的话，两张表的 pk 撞上就是同一个事件 —— 同一个病，每天都发作；
2. **时间用 floating（不带 `TZID`、不带 `Z`）** —— 和
   [D33 第二节](decisions/D33-work-schedule.md) 选墙钟时间是同一个理由，
   而带 `TZID` 就得连 `VTIMEZONE` 一起手写，那和"拼字符串不引库"是两码事；
3. **这个端点同样带时间窗**（前 4 周 + 后 13 周）。
   「不许有列出全部班次的入口」那条规矩（[D33 代价 1](decisions/D33-work-schedule.md)）
   对它一样成立 —— 它恰恰是最容易被写成"把这个人所有的班次拼出来"的那一个。

## 五、权限第一次真正吃紧

[`goal.md` 待定表第 4 条](goal.md#还没定的哪些阻塞哪些不阻塞)和
[`phase-c.md` 待定表第 6 条](phase-c.md#六还没定的哪些阻塞哪些不阻塞)都写着
「`MinistryRole` 先只做 `admin` 一档」。

⚠️ **那个结论是在「只有活动管理」的世界里下的，本轮照抄是错的。**
Phase D 之后，一个 ministry admin 会一次性获得：谁拿钱、拿哪一档、
谁请了什么假、谁离职原因是什么、谁的证照过期、谁标着不可再雇。

**处置：不加档位（那要改 `permissions.py` 的判断和一整套 UI），
改成把最敏感的东西收进 foundation tier。**
⚠️ **而"最敏感的"实际上只有一样 —— 请假的类型和备注。**
本轮最敏感的另外两个（`is_rehirable` / `end_reason`）已经在
[D37 第二节](decisions/D37-hris-fields-and-credentials.md) 整个推迟掉了，
所以这里不要写成"收窄了三样"：**收窄的是一样，另外两样是根本没做。**
（`compensation` / `fte` 这些，本部门的 admin 该看得见 —— 他要排班、要招人，
专业系统也是这么分的。把它们一起收进 foundation tier 会让 ministry admin
做不了自己的事，那是另一种失败。）

| 数据 | ministry admin（限自己的 ministry） | foundation tier |
|---|---|---|
| 姓名 / 岗位 / 汇报线 / 在职状态 | ✅ | ✅ |
| 班表 · 出勤 · 工时三个数 | ✅ | ✅ |
| 请假的**日期**和「请假」这个事实 | ✅ | ✅ |
| 请假的**类型和备注** | ❌ | ✅ |
| 请假的录入 | ❌ —— 录入的人必须选类型，开给他就等于让他看见（[D34 第四节](decisions/D34-leave.md)） | ✅ 但只给没有账号的人代录；有账号的一律本人在 `/me/leave/new/` 提交 |
| `compensation` / `employment_type` / `fte` / `agreed_hours_per_week` | ✅ | ✅ |
| 证照 | ✅ | ✅ |
| `is_rehirable` / `end_reason` | — 本轮不做（[D37 第二节](decisions/D37-hris-fields-and-credentials.md)） | — |
| 组织架构图 | 全体登录用户可见（汇报线不是秘密） | |

### 更正的一处推理

D32 原文说「未确认这个数消不掉，唯一能消掉它的办法是打卡」。
**那是错的**：稀疏表示里没有「未确认」这个状态，因为没有行就是没有偏离。
所以它是**选了稠密的代价**，不是不打卡的代价 —— 更正写在
[D33 第一节](decisions/D33-work-schedule.md)。

稠密仍然是对的选择（理由在那张对比表里），但归因写错的后果很具体：
将来复盘「为什么我们有一堆未确认工时」时，会有人跑去做打卡，
**而那件事解决不了这个问题**。

## 九、第二次自查：对着行业标杆和法规量了一遍（2026-08-15）

第六节那一轮自查是**对着自己的三份文档 + 代码**做的。这一轮换了尺子：
按 DOL / FLSA（29 CFR 516 · 553）、Planning Center Services、
Volgistics · Track It Forward、NTEN / TechSoup 类的需求清单、
NN/g 的复杂应用启发式和 ECFA 的治理标准，
先立了一套 29 条的判据，再拿 D32–D38 逐条量。

**结论一句话**：这套设计防「代码悄悄算错」防得很好，
**几乎不防「人当场做错」**—— 而排班系统的日常故障全在后一类。

### 改了什么

| 改的 | 不改会怎样 |
|---|---|
| 新增 [D39](decisions/D39-scheduling-conflicts.md)：四类冲突、一处实现、一律提示不拦截 | 三类调度冲突一类都不检测。⚠️ 而其中一半的检测 [D36 第五节](decisions/D36-two-hour-ledgers.md) 早就写好了，只是**挂错了条件**（只认 `volunteer`）**也出现在错的时候**（事后的报表上）。[D33 第十节](decisions/D33-work-schedule.md) 那条推迟推的不是主冲突 —— 结论没错，前提没了 |
| [D33 第七节](decisions/D33-work-schedule.md) 补工作周：`WORKWEEK_STARTS_ON` + `workweek_totals()` + 名册上的超阈提示 | 例外记录法只做了一半。29 CFR 516 要的是每一天**和每一周**，而系统答得出「他 3 月 168 小时」，答不出「他 3 月第二周 43 小时」。⚠️ 顺带给了 `flsa_status` 第二个读者 —— 一个法律状态字段只被一条 UI 提示读，本身就是信号 |
| [D38 第七节](decisions/D38-served-as-volunteer-or-work.md) 那个可印的志愿小时数补一格「未计入的 N 人」 | `agreed` / `not_tracked` 的无薪成员**一行 `Shift` 都不生成**，于是需求原文 ① 那批人的一部分完全不进年报和 grant 申请里的那个数。⚠️ 不报错，只是系统性偏低。🔴 补法**不是**把约定值折算加进去 —— 那是 [D36 第四节](decisions/D36-two-hour-ledgers.md) 拒绝过的形状 |
| **整批撤销**（[D40](decisions/D40-undo-a-pattern-batch.md)）：`PatternBatch` + `undo_pattern_batch()` + 两个入口 | 一次点击建 30 条模板、约 390 行班次，**而它原来不可逆**。⚠️ 撤销**不是回到从前** —— 过去的行和人碰过的行都留着，留得下班次的模板改「即日停止」，这句话必须写在确认屏上。⚠️ 而它顺带把生成器那两个删除条件抽成了一处（`_drop_generated_after()`），**比给守卫白名单加一条更硬**；`generated_from` 也从 `SET_NULL` 改成了 `PROTECT`，因为孤儿班次没有任何生成器会去收 |
| 批量建例会模板加一屏确认（人数 · 周数 · 班次数 · 跳过谁） | 勾 30 个人是约 390 行 `Shift`，一次点击，而初版没有任何预览。NN/g 第 5 条 |
| 每批验收各加两条「错了之后」 | 六十多条验收全是正向路径和静默错误的防线，没有一条测「操作的人搞错了救不救得回来」。⚠️ 它还会**反向逼出缺失的入口** —— 本项目三次栽的那个病，每次都是走查抓出来的 |
| `.ics` 输出**两条泳道** | 建它的理由是「排班要真的被人看到」，而 My Schedule 有两条泳道、日历只有一条 —— 少的那条恰恰是最容易忘的 |
| My Schedule 的「待确认」排版退一格 | 第五条规矩把**时间窗**对齐了，但那三个数不是同一类东西：两个是账本，第三个是其中一个账本的质量指标 |
| 「你被排进了一条新的例会」进通知清单 | `WorkPattern` 的录入全在管理侧，而这一轮的对象**是志愿者不是雇员** —— 单方面排班且不告诉他，是这类系统最容易掉人的地方 |
| `stipend` 那句法律断言改成政策口径（[D32 第二节](decisions/D32-worker-axes-schedule-and-assignment.md)） | 29 CFR 553.106 那条「nominal fee 不破坏志愿者身份」**只管公共部门**，私营非营利是事实判断。把政策选择写成法律事实，下一个人就不会再去问律师 |
| 已知缺口表补「名册上没有背景审查状态」 | 这是员工名册上唯一一个「会出事」的空格，而这个基金会有未成年志愿者。⚠️ 本轮**仍然不建表**（判据第 1 条过不了），但把**遗漏**变成**主动接受** |
| [D36 第九节](decisions/D36-two-hour-ledgers.md) 补 ECFA 半句 | 薪酬入库那天要回答的不只是「谁能看」，还有「这条记录是谁批的」—— ECFA 的治理标准和 IRS 的 rebuttable presumption 问的是同一件事 |
| 措辞收进 [D38 第六节](decisions/D38-served-as-volunteer-or-work.md) 一处 | 同一批标签三份文档三种口径，**在还没开工的时候就已经有三份了**，而那一节自己刚说完措辞是承重的 |

   这类错**只有守卫抓得住**，因为它每次都是在拆决策的那一刻批量产生的，
   而那正是人最没空回头核对旧引用的时候；
2. 「四条设计规矩」下面列着五条（现在是六条）—— 同 `goal.md` 那个「14 条」，
   一个数字被复制之后没跟着改。

> **这一轮学到的**：第六节那一轮自查问的是「**这个字段谁读它**」，
> 它筛掉了一批没有读者的东西，非常有效。
> 但它**问不出本轮这九条** —— 因为这些东西的读者是**人**，
> 而人在做决定的那一刻需要什么，只有拿别人做过的系统来对照才问得出来。
> 两把尺子都要用：一把量**这行数据有没有人读**，一把量**这个人做错了会怎样**。
